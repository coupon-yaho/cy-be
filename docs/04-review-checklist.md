## 1. 판정 4종 — "괜찮다"와 "안 봤다"를 섞지 않는다

| 판정 | 언제 |
|---|---|
| **위반** | 위반을 확인했다 |
| **확인함** | 충족을 확인했다 |
| **해당없음** | 이 변경과 무관하다 |
| **확인못함** | 판정에 필요한 파일을 못 읽었다 |

**안 본 걸 봤다고 하지 마라.** 근거를 직접 확인 안 했으면 **확인못함** 이다.

이게 섞이면 리뷰 결과가 통째로 쓸모없어진다. 통과한 건지 그냥 안 본 건지 아무도 구분할 수 없으니까.
같은 항목이 계속 **확인못함** 으로 나온다면 코드가 어려워서가 아니라 **3절에서 열어줄 파일이 모자란 것**이다.

### ⚠️ 파일이 없는 것과 파일을 못 읽은 것은 다르다

**둘을 섞으면 blocker 를 놓친다.** 이게 이 목록에서 제일 헷갈리기 쉬운 지점이다.

| 상황 | 판정 |
|---|---|
| Glob 으로 찾았는데 **저장소에 그 파일이 없다** | **부재를 확인한 것** — 그 자체가 판정 근거다 |
| 파일은 있는데 **읽지 않았다 / 읽지 못했다** | **확인못함** |

마이그레이션 SQL 을 전부 읽었는데 `UNIQUE(campaign_id, member_id)` 가 없다 → **위반**이다. 확인못함이 아니다.
`application.yml` 이 저장소에 아직 없다 → 타임아웃 설정도 **없는 것**이다. 다만 **아직 만들 차례가 아니라면 해당없음**이다.

판단 기준: **이번 PR 이 그 파일을 만들었어야 하는가?**
- 그렇다 → **위반**
- 아니다 (아직 그 단계가 아니다) → **해당없음**
- 판단이 안 선다 → **확인못함** 에 넣고 이유를 적어라

`부재` 23개 중 상당수가 여기서 갈린다. **"없어서 못 봤다" 로 넘기면 이 목록은 있으나 마나다.**

## 2. 점검 목록

`부재` 표시가 붙은 항목은 **함께 볼 파일(3절)을 읽어야만 판정된다.** 나머지는 diff 만으로 판정된다.

### 재고와 발급 원자성 — blocker ① 초과 발급

- 재고 컬럼이 `active_count` 인가 — `issued_count` 는 누적으로 읽혀 판정이 통째로 어긋난다
- `active_count` 가 취소·만료 시 **감소**하는가 (누적 카운터가 아닌가)
- 잔여 계산이 `total_quantity − active_count` 인가
- 재고 확인과 차감이 **원자적**인가 (조회 → 판단 → 갱신으로 갈라지지 않았는가)
- v1 비관 락의 범위가 **캠페인 재고 행 하나**인가 (테이블·넓은 범위 락이 아닌가)
- `부재` 락 보유 구간에 외부 호출(HTTP, Kafka 발행, 알림)이 **없는가**
- `부재` 조건부 UPDATE 의 **affected rows 를 검사**해 0건을 실패로 처리하는가
- Redis Lua 가 재고 확인·차감·회원 등록을 **한 스크립트 안에서** 처리하는가
- Lua 가 키를 `KEYS` 로 받는가 (문자열 연결로 키를 조립하지 않는가)
- `부재` Redis 선점 성공 후 DB 반영이 실패했을 때 **재고를 되돌리는 경로**가 있는가

### 1인 1매 — blocker ② 1인 다매

- `부재` **`UNIQUE(campaign_id, member_id)` 제약이 존재하는가**
- 그 제약을 삭제·완화·우회하는 변경이 없는가 (→ 함정 1. 불편해져도 지우지 않는다)
- 애플리케이션 선점검이 DB 제약을 **대체**하고 있지 않은가 (둘 다 있어야 한다)
- `부재` UNIQUE 위반 예외를 삼키지 않고 **정해진 응답 코드**로 변환하는가

### 멱등성 3계층

- `부재` `Idempotency-Key` 를 받아 저장하는가
- 같은 키 재요청이 **첫 결과를 그대로 반환**하는가 (재발급하지 않는가)
- 상태 변경이 조건부 UPDATE(`WHERE status = 'ISSUED'`) 인가
- `부재` 멱등 레코드에 UNIQUE 제약이 있는가 (3계층의 마지막)
- `부재` **처리 중인 키에 동시 요청**이 왔을 때의 규칙이 정해져 있는가 (→ 함정 5)

### 상태 전이

- 상태 전이가 `CouponStateMachine` 을 경유하는가 (조건문 하드코딩이 아닌가)
- `부재` **검증 배치도 같은 클래스**를 쓰는가 — 두 벌로 갈라지면 검증이 검증이 아니다
- 상태가 4종(`ISSUED` `USED` `CANCELLED` `EXPIRED`) 밖으로 늘어나지 않았는가
- `부재` 만료된 `USED` 의 사용취소 규칙이 명시돼 있는가 (→ 함정 3)

### 검증 결정론 — blocker ③ 비결정론

- 배치 코드에 `now()` / `LocalDateTime.now()` / `Instant.now()` 가 **없는가**
- `부재` 기준 시각이 `asOf` 파라미터로 **주입**되는가
- `부재` 정렬에 `(created_at, id)` **타이브레이커**가 있는가 (동시각 이력의 순서 고정)
- `부재` 같은 `(asOf, dataset)` 재실행이 같은 결과를 내는가 — `findings_checksum` 으로 증명되는가
- `부재` 검증이 `asof_state.state` ↔ `issuances.status` ↔ `issuance_usages` **3축을 모두** 대조하는가
- 오염 데이터셋이 정상 데이터셋과 **분리**돼 있는가 (→ 함정 1)
- `부재` `verification_findings` 가 위반 유형별 식별자(`campaign_id` `member_id` `history_id`)를 담는가 (→ F1)

### 개인정보 마스킹 — blocker ④ · 과제가 명시한 유일한 보안 요건

- 로그에 이름·연락처·이메일이 **원문으로** 나가지 않는가
- API 응답에 PII 가 없는가 (`member_id` 와 마스킹값만)
- 예외 메시지·스택트레이스에 PII 가 실리지 않는가
- **검증 리포트와 통계 산출물**에 PII 가 없는가 — 여기가 제일 자주 샌다
- 대시보드 이벤트 스트림에 PII 가 없는가
- `부재` 시드 산출물·JWT CSV 가 커밋되지 않는가 (`.gitignore` 확인)
- `부재` 마스킹이 **한 곳**에 구현돼 있는가 (호출부마다 중복하면 한 곳을 반드시 빠뜨린다)

### 측정 기준

- 측정 기준점이 **클라이언트가 성공 응답을 받은 시점**인가 (Redis 선점 시점이 아닌가)
- 응답 코드 규약을 임의로 바꾸지 않았는가 — k6 집계와 Chaos 자동 판정의 근거다
- `부재` 임계치가 `application.yml` 로 외부화돼 있는가 (부하 중 재기동 없이 튜닝해야 한다)

### 설정과 복원력

- `부재` 모든 외부 호출에 **연결·읽기 타임아웃**이 설정돼 있는가
- `부재` 서킷브레이커(`redisCB` `dbCB` `kafkaCB`)의 **폴백 동작**이 정의돼 있는가
- `부재` Redis 장애 시 v1 경로가 **함께 죽지 않는가** (→ 함정 6)
- `부재` `/actuator` 노출 엔드포인트가 명시적으로 제한돼 있는가 (`env` `beans` 차단)
- 시크릿이 코드·설정에 하드코딩돼 있지 않은가

### 컨벤션

- 용어가 고정표를 따르는가 — **누적 발급률**(누적 ISSUE/total)과 **재고 점유율**(active/total)을 섞지 않았는가
- 도메인 로직이 컨트롤러에 들어가 있지 않은가
- `부재` 동시성 코드 변경에 **동시성 테스트**가 함께 있는가 (재고 N 에 2N 스레드)

**48항목. 그중 `부재` 23개** — 절반은 diff 밖을 열어보지 않으면 손도 못 댄다는 뜻이다.

## 3. 함께 보기 규칙 — diff 에 없어도 열어야 하는 파일

`부재` 항목은 diff 만 봐서는 답이 안 나온다.
**"타임아웃이 없다"를 말하려면 타임아웃이 있을 법한 자리를 직접 봐야 한다.**

변경 파일이 아래 트리거에 걸리면 → 오른쪽 파일을 **diff 에 없어도** 열고 → 해당 절을 하나씩 본다.
여러 줄에 걸리면 전부 적용한다. 아무것도 안 걸리면 컨벤션·개인정보 두 절만 본다.

> **패턴은 전부 `**/` 로 시작한다.** 우리 자바는 `src/main/java/com/…/` 아래 깊이 들어가 있어서,
> `*Issu*` 처럼 쓰면 최상위 파일에만 걸리고 **아무것도 매칭되지 않는다.** 실제로 리허설에서 확인했다.

| 트리거 | 함께 열 것 (diff 밖이어도) | 볼 절 |
|---|---|---|
| 발급 서비스 · 락 · Lua<br>`**/*Issu*` `**/*Stock*` `**/*Lock*` `**/*Redis*` `**/*.lua` | 재고 엔티티, 마이그레이션 DDL 전체, `CouponStateMachine`, 멱등성 클래스 | 재고 · 1인1매 · 멱등성 · 상태전이 · 개인정보 |
| 검증 · 배치 · 시드<br>`**/*Verif*` `**/*Batch*` `**/*Seed*` `**/*Corrupt*` `**/*Stats*` | `CouponStateMachine`, 검증 엔티티, 오염셋 정의, 마이그레이션 DDL | 검증결정론 · 상태전이 · 개인정보 |
| 마이그레이션<br>`**/db/migration/*.sql` `**/schema*.sql` | **마이그레이션 이력 전체** (이전 것과의 순서가 판정에 필요), 대응 엔티티 | 재고 · 1인1매 · 멱등성 · 검증결정론 |
| 도메인 · 상태전이<br>`**/domain/*.java` `**/coupon/*.java` `**/*StateMachine*` `**/*Campaign*` `**/schedule/*.java` | 마이그레이션 DDL, 발급 서비스, 검증 배치 | 재고 · 상태전이 · 검증결정론 |
| 컨트롤러 · DTO<br>`**/controller/*.java` · `**/api/*.java` `**/dto/*.java` `**/*Api.java` | 마스킹 유틸, 응답 코드 정의, 대상 서비스 | 개인정보 · 측정 · 1인1매 · 컨벤션 |
| 설정<br>`**/application*.yml*` `**/logback*.xml` `**/build.gradle` | **전 프로파일 yml** (하나만 보면 값 차이를 모른다), `build.gradle` | 설정복원력 · 개인정보 · 측정 |
| 대시보드 · 부하 · Chaos<br>`**/static/**` `loadtest/**` `chaos/**` | 응답 코드 정의, 마스킹 유틸 | 개인정보 · 측정 · 컨벤션 |
| 인프라 · 비동기<br>`**/entry/*.java` `**/queue/*.java` `**/kafka/*.java` `**/resilience/*.java` | `application*.yml`, 발급 서비스 | 설정복원력 · 측정 · 개인정보 |
| 그 외 `src/main` 자바 | — | 컨벤션 · 개인정보 |

**파일이 있는데 안 열었다면 거기 걸린 항목은 확인못함이다.** "확인함" 으로 통과시키지 마라.
**파일이 아예 없다면 그건 "없음" 이다** — 1절 표를 따른다. 확인못함이 아니다.

> 열 파일이 20개를 넘으면 **최근 것부터 20개까지만** 보고, 다 못 봤다는 걸 총평에 적는다.
> 마이그레이션 이력이 쌓이면 여기가 제일 먼저 커진다.

> ⚠️ 이 표의 트리거 패턴은 **패키지 구조가 확정되기 전에 쓴 것이라 아직 실제 파일에 맞춰본 적이 없다.**
> 첫 코어 PR 에서 매칭 여부를 확인하고, 안 맞으면 이 표부터 고친다.
> `docs/03-collaboration.md` 5절 검증 4b 가 그 확인 지점이다.

## 4. 이 목록을 어떻게 관리하나

**항목을 늘리는 것보다 죽은 항목을 빼는 게 중요하다.** 판정되지 않는 항목이 남아 있으면
나머지 항목의 신뢰도까지 떨어진다.

- 한 번도 위반이 안 잡힌 항목 → 트리거가 잘못됐는지 확인 (3절 점검)
- 반복해서 **확인못함** 인 항목 → 코드가 어려운 게 아니라 함께 볼 파일이 부족한 것
- 오탐이 반복되는 항목 → 문구를 조이거나 **삭제한다**

D5·D10 게이트 점검 때 위 셋을 같이 본다. 3주 프로젝트라 별도 주기는 두지 않는다.
