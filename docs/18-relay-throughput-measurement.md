# 알림 릴레이 — 워커 수를 정한 근거와 분리 판단

CY-906 이 남긴 처리량 표는 **발행 대상이 `sleep(20ms)` 스텁**이었다. 그래서 그 표는
*"배치 클레임만으로는 30% 밖에 못 얻는다"* 까지만 말했고, **워커를 몇으로 둘지**는
말하지 않았다. 이 문서는 그 자리를 **진짜 Kafka 로 다시 재고** 두 가지를 판정한 기록이다.

- 워커 기본값 8 을 유지할 것인가
- 릴레이를 접수 API 프로세스에서 **분리**할 것인가

---

## 결론 먼저

| 질문 | 답 | 근거 |
|---|---|---|
| 워커 8 을 유지하나 | **유지한다** | 요청 지연이 **8 까지는 안 변하고 16 부터 무너진다** |
| 곡선이 어디서 평평해지나 | **처리량은 32 까지도 안 평평하다** | 되레 **요청 스레드가 먼저 무너진다** |
| 릴레이를 분리하나 | **지금은 아니다** | 8 에서 요청 p99 ≈ 2ms — 분리해서 되찾을 것이 거의 없다 |

**CY-906 이 적어 둔 예상이 빗나갔다.** 거기에는 *"진짜 Kafka 프로듀서에서는 브로커
왕복이 먼저 평평해진다"* 고 적혀 있었는데, 실제로 먼저 무너진 것은 **브로커가 아니라
같은 JVM 의 요청 스레드**였다.

---

## 잰 값

`seed=5000`, 배치 64, 인플라이트 64, 실제 MySQL + 실제 Kafka(`apache/kafka:3.8.0`),
프로듀서 설정은 운영과 같다(`acks=all`, 멱등, `linger.ms=5`).
**`availableProcessors = 11`** — 아래 판정이 이 숫자에 달려 있다.

두 회차를 돌렸다. `요청` 은 같은 JVM · 같은 커넥션 풀에서 도는 프로브 스레드의 지연이다.

| 워커 | 처리량 #1 | 처리량 #2 | 요청 p50 #1 / #2 | 요청 p99 #1 / #2 |
|---:|---:|---:|---:|---:|
| 1 | 98.1건/s | 102.4건/s | 362µs / 353µs | 2,089µs / 1,871µs |
| 2 | 202.6건/s | 246.8건/s | 352µs / 218µs | 1,277µs / 555µs |
| 4 | 399.9건/s | 459.1건/s | 320µs / 231µs | 1,133µs / 587µs |
| **8** | **581.9건/s** | **703.9건/s** | **630µs / 410µs** | **2,633µs / 1,925µs** |
| 16 | 1,122.3건/s | 1,098.4건/s | 1,178µs / 1,971µs | 10,383µs / 12,827µs |
| 32 | 1,438.8건/s | 1,495.7건/s | 3,934µs / 4,047µs | 18,432µs / 19,410µs |

### 읽는 법

- **처리량은 32 까지 계속 는다.** 배수는 줄지만(×2.2 → ×1.9 → ×1.5 → ×1.6 → ×1.3)
  평평해지지 않는다. **"브로커가 먼저 막는다" 는 예상은 틀렸다.**
- **요청 지연은 8 까지 평평하다.** p99 가 1~2.6ms 대에 머문다 — 워커 1 과 워커 8 이
  같은 수준이다.
- **16 에서 무너진다.** p99 가 ~2ms → ~10~13ms 로 **다섯 배**가 된다. 32 에서 다시 두 배.
- 그래서 8 → 16 은 **처리량 ×1.6 을 사려고 요청 p99 ×5 를 낸다.**

### 왜 하필 16 인가 — 코어 수다

이 기계는 코어가 **11** 이다. 워커 8 + 스케줄러 + 프로브면 열 남짓이라 아직 안 넘는다.
16 은 넘는다. 무너지는 자리가 브로커 왕복이 아니라 **CPU 초과 예약**에 있다.

> ⚠️ **그래서 8 은 절대값이 아니다.** 코어가 4 인 기계에서는 8 도 이미 초과 예약이다.
> 이 표를 다른 배포 대상에 그대로 옮기지 말 것 — 옮기려면 그 기계에서 다시 재야 한다.

---

## 분리 판단

지금 릴레이 워커 풀은 **접수 API 와 같은 JVM** 에 있다. 분리하면 요청 스레드가 CPU 를
안 뺏기지만, 프로세스가 하나 늘고 배포·관제가 그만큼 는다.

**숫자가 말하는 것** — 기본값 8 에서 요청 p99 는 1.9~2.6ms 로 워커 1 과 사실상 같다.
**분리해서 되찾을 것이 거의 없다.** 그래서 지금은 분리하지 않는다.

**분리가 필요해지는 조건은 정해 둔다.** 필요 처리량이 **8 워커가 내는 값(~600~700건/s)을
넘을 때**다. 그때는 16 이상이 필요한데, 그 지점이 정확히 요청 지연이 무너지는 자리다 —
같은 JVM 에서는 **처리량과 접수 지연 중 하나를 포기해야** 하고, 분리는 그 교환을 없앤다.

## 재현

하네스는 **커밋하지 않는다.** 분 단위 타이밍 측정을 CI 에 올리는 쪽이 더 나쁘고,
이 저장소에 `@Disabled`·`@Tag` 선례가 없다(CY-906 과 같은 판단).

1. `api/build.gradle` 의 test 의존성에 두 줄을 임시로 넣는다.
   ```groovy
   testImplementation 'org.testcontainers:testcontainers-kafka'
   testImplementation 'org.springframework.kafka:spring-kafka'
   ```
2. `api/src/test/.../RelayThroughputHarness.java` 를 만든다. 뼈대는
   `@RepositoryTest` + `NotificationOutboxRepositoryImpl`·`NotificationRepositoryImpl`·
   `NotificationRetryBackOffConfig` 임포트, `org.testcontainers.kafka.KafkaContainer`,
   운영과 같은 프로듀서 설정.
3. 워커 수를 바꿔 가며 `NotificationOutboxRelay` 를 새로 만들고
   `while (published() < SEED) relay.poll();` 로 다 뺄 때까지 잰다.
4. 같은 회차에 프로브 스레드를 띄워 요청 지연을 함께 잰다.

### ⚠️ 이 측정에서 **세 번 헛쟀다**

같은 실수를 반복하지 않도록 남긴다.

| 헛잰 것 | 증상 | 원인 |
|---|---|---|
| 워밍업 없이 잼 | 릴레이 **정지**가 워커 8 보다 느림 | 정지 구간이 프로브의 첫 실행 — JIT 를 잰 것 |
| 릴레이가 쓰는 테이블을 프로브가 읽음 | 워밍업 뒤에도 뒤집힌 채 | `seed()` 의 DELETE·INSERT 가 남긴 **테이블 상태**를 잰 것 |
| 유휴 구간을 기준선으로 씀 | 프로브 테이블을 분리해도 뒤집힘 | 유휴 구간은 CPU·커넥션이 식어 **깨어나는 비용**이 지배 |

**세 번 다 "릴레이가 도는 쪽이 더 빠르다" 는 불가능한 값으로 드러났다.** 그것을 그대로
문서에 옮겼으면 "릴레이는 요청을 안 방해한다" 는 반대 결론이 나왔을 것이다.
지금 기준선은 **유휴가 아니라 워커 1** 이다 — 같은 조건에서 릴레이만 가장 얕다.
