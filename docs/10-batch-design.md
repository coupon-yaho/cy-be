## 0. 배치 서버는 문서에 없던 구조다

전 문서를 grep 하면 `Spring Batch` 도 `배치 서버` 도 **0회** 나온다. PRD 의 L2 기준 환경(Boot 1대 · Redis 1대 · MySQL 1대 · k6 같은 머신)에도 배치가 없다.

## 1. 인터뷰가 정한 것 — 5개 중 3개는 게이트가 반박했다

| | 결정 | 게이트 판정 |
|---|---|---|
| ① | verify 2모드 | ✅ 반박 없음 |
| ② | 시간 상한 없음 | ⚠️ 발동 트리거도 결정자도 없음 (MEDIUM) |
| ③ | Job 안 죽임 | 🔴 **`stop()` 이 집계 쿼리 폭주에 무력** (HIGH) |
| ④ | `run_id` 스냅샷 | 🔴 **영상 오염 구간에 통계 패널이 빈다** (HIGH) |
| ⑤ | attempt / checksum | 🔴 **`asOf` 결정론에 스냅샷 근거 없음** (HIGH) → **4절 ③에서 해소** ✅ |

**구조는 맞았지만 ③④는 이대로 구현하면 안 된다.** 각 절의 ⚠️ 를 반드시 같이 읽을 것.

⑤(결정론)는 **해소안이 나왔다** — 이력 재구성 + 데이터 지문 + 판정 시점 동결의 3층. `4절 ③` 참조.


### ① 검증 계층은 둘이고, 세 번째를 만들지 않는다

```
verify(asOf, dataset, scope)
  scope = FULL         300만 전수. 합격 판정은 여기서만
        = INCREMENTAL   증분. 관측용
```

**근거** — ①의 1초 드리프트는 `Redis 카운터 ↔ DB 집계` **합계 비교**라 오염 유형을 하나도 식별하지 못한다. 전수는 유형까지 잡지만 300만이라 상시로 못 돈다. 그 사이 공백이 "준실시간"의 실체이고, 새 파이프라인이 아니라 **기존 검증의 조회 범위를 좁힌 것**이다.

잡을 둘로 나누면 규칙 구현이 두 벌이 되어, 두 배치 결과가 갈릴 때 진실 판단 근거가 사라진다.

**증분 윈도우는 절대 구간 `(from_ts, as_of_ts)` 만 받는다.** `최근 N분` 같은 상대 윈도우는 `now()` 기준이라 같은 파라미터 재실행이 재현되지 않는다.

**집계 규칙은 윈도우 안의 *행*이 아니라 윈도우에 등장한 *키의 전체 이력*을 스캔한다.** 행 윈도우로 자르면 경계 밖 짝을 놓친다. 타협 불가.

### ② 시간 상한을 두지 않는다

`FULL` 에 "몇 분 안에 끝나야 합격"이라는 캡을 두지 않는다. **시간은 판정이 아니라 관측치다.**

**근거 셋.**

**하나** — `PRD:1727` 이 못박았다. *"L1에서 나온 숫자는 기록만 하고 비교하지 않습니다. 정합성은 어디서 돌려도 같아야 하므로 **L1은 정합성 전용**입니다."* 검증 배치는 정확히 그 L1 용도로 돈다. L1 실측을 합격 기준으로 삼으면 프로젝트 자체 측정 헌장과 충돌한다.

**둘** — 시연은 사전 녹화다(`PRD:1173`). 영상 `3:30–5:00` 이 오염 검출 구간이고 편집된다. 실행 시간이 발표 20분 하드캡을 gate 하지 않는다.

**셋** — `R4` 의 감지 신호는 *"D4까지 적재가 안 끝남"* 으로 **적재 단독**이다(`PRD:1270`). 검증 duration 을 R4 트리거로 붙이면 **가장 싼 원인**(GROUP BY 인덱스 미스, 청크 사이즈)에 **가장 비싼 대응**(300만 전수 포기)을 매핑하게 된다.

> 그리고 타이트한 캡은 집계 규칙을 샘플링하도록 압박하는데, 그건 D10 게이트가 보호하려는 바로 그 규칙이다.

**느릴 때 조치 순서를 미리 고정한다.**

```
1순위  인덱스 · 청크 사이즈 · 집계 쿼리 튜닝
2순위  통계 집계를 별도 Job 으로 분리
3순위  그제서야 데이터 축소를 논의
────────────────────────────────
규칙 삭제 · 샘플링은 어느 순위에도 없다
```

참고 예산은 **D6 첫 300만 실측 후 `실측치 × 2.0`** 으로 확정한다. 그전에는 숫자를 박지 않는다.

### ③ Job 을 죽이지 않는다 — 대신 멈출 수 있어야 한다

예산 초과도 폭주 수준도 Job 을 종료시키지 않는다. **경고만 남기고 계속한다.**

*"오염 700건을 정확히 검출했는데 시간 때문에 FAILED"* 라는 읽을 수 없는 상태를 만들지 않기 위해서다.

**대신 수동 중단 경로가 필수다.** 검증 Job 구현과 **같은 티켓**에 넣는다.

> 🔴 **게이트 지적 — 이 결정은 자기모순이다.**
>
> `JobOperator.stop()` 은 **청크 경계에서만 반응하는 협조적 중단**이라, 폭주 대상이 집계 단일 쿼리면 중단 요청이 안 걸린다. 유일하게 실효 있는 수단은 쿼리 레벨 상한(`MAX_EXECUTION_TIME`)인데 **그건 자동 종료다.** "경고만 남기고 계속"과 양립하지 않는다.
>
> ```
> statement timeout 없음  →  폭주 시 커넥션을 물고 늘어진다. L2 공유면 팀 전체가 막힌다
> statement timeout 있음  →  쿼리가 죽고 Step 이 FAILED. "경고만" 이 아니다
> ```
>
> **해소안** — `FULL` Job 자체는 죽이지 않되 **쿼리 단위 상한은 둔다.** 쿼리가 죽으면 해당 Step 이 `FAILED` 로 남지만 `verdict` 는 이미 앞 Step 에서 확정돼 있으므로 *"검증은 됐고 마지막이 죽었다"* 가 표현된다. 원래 피하려던 상태(*"700건 검출했는데 시간 때문에 불합격"*)와는 다르다.
>
> **검증 전용 커넥션 풀 분리**도 같이 넣는다. 안 넣으면 `HikariCP` 사용률이 v1 병목의 증거인데 배치가 나눠 써서 증거가 흐려진다.

### ④ 통계 3테이블은 `run_id` 스냅샷

```sql
campaign_stats  PK (campaign_id)          → (run_id, campaign_id)
grade_stats     PK (campaign_id, grade)   → (run_id, campaign_id, grade)
hourly_stats    PK (day_of_week, hour)    → (run_id, day_of_week, hour)
```

대시보드는 **`status=COMPLETE` 이고 `dataset=CLEAN` 인 최신 `run_id`** 만 읽는다. 이 필터를 **뷰로 한 번만 정의**하고 각 화면이 그 뷰를 쓴다 — 화면이 늘어날 때 필터를 빠뜨릴 수 없게.

**단일 트랜잭션**은 undo log 가 크고 롤백하면 검증 결과와 통계 시점이 어긋난다. **STALE 플래그**는 부분값이 실제로 남아 규율에 의존한다. **`run_id` 는 틀린 값이 물리적으로 조회되지 않는다.**

저장 부담은 없다 — `147 × run` + `588 × run` + `168 × run`. run 100번이면 9만 행.

```
verdict        PASS / FAIL                    규칙 기준. D10 게이트가 읽는다
stats_status   COMPLETE / PARTIAL / SKIPPED   대시보드가 읽는다
```

**`CORRUPT` run 은 통계 Step 을 아예 실행하지 않는다.** 오염 데이터 위의 집계는 의미가 없고, 대시보드가 어차피 안 읽는다. `JobExecutionDecider` 로 분기해서 "건너뛴 사실"이 배치 메타에 기록되게 한다 — `if` 문으로 감추면 실행 이력에서 추론해야 한다.

> 🔴 **게이트 지적 — 영상 오염 구간에 통계 패널이 빈다.**
>
> 영상 `3:30–5:00` 이 정확히 **`CORRUPT` run 구간**인데, 그때 `hourly_stats` · `grade_stats` · `campaign_stats` 를 원천으로 쓰는 패널들이 갱신을 멈춘다. **오염을 보여주는 바로 그 장면에서 통계 화면이 죽는다.**
>
> **해소안** — 대시보드 뷰가 `dataset=CLEAN` 인 **직전 완결 스냅샷을 고정 표시**한다. `run_id` 스냅샷 구조라 이게 자연스럽게 된다(직전 CLEAN run 이 그대로 살아 있으므로). 영상에서 통계 패널은 *"오염 검출과 무관하게 마지막 정상 집계를 보여주는 중"* 이 된다.
>
> 그리고 **PK 3개 변경은 ⑤의 쿼리 계약 변경**이라 D1~D2 전원 합의를 통과해야 한다. 부결되면 대안은 `run_id` 를 PK 가 아닌 일반 컬럼으로 두고 `latest` 뷰로만 거르는 것 — 방어가 한 겹 약해진다.

### ⑤ 결정론 — Spring Batch 두 가지 함정

**JobParameters 가 동일 파라미터 재실행을 차단한다.** 결정론 검증은 같은 `asOf` 로 두 번 돌려야 하므로 `attempt` 를 식별 파라미터에 포함한다.

```java
.addString("asOf",    asOf,    true)
.addString("dataset", dataset, true)
.addString("scope",   scope,   true)
.addLong  ("attempt", n,       true)   // ← 이게 있어야 재실행이 된다
```

**`findings_checksum` 은 삽입 순서와 무관해야 한다.** findings 전량을 정렬한 뒤 해시한다. 정렬 없이 해시하면 같은 데이터인데 checksum 이 달라져 **거짓 실패**가 난다.

> ⚠️ **정렬만으로는 부족하다** — 정렬은 **순서 문제만** 푼다. 규칙이 `coupons.status` 나 `coupon_stocks.active_count` 현재 행을 읽으면 그 아래 데이터가 계속 바뀌므로 `asOf` 가 장식이 된다.
>
> **→ `4절 ③` 에 해소안이 있다.** 이력 재구성으로 규칙 6개 중 3개를 완전 결정론으로 만들고, 나머지 셋(V1·V3·V6)은 **데이터 지문**으로 *"데이터가 바뀐 것"* 과 *"검증기가 비결정적인 것"* 을 구분한다.

## 2. 잡 10개와 컷 순서

**PRD 가 `D6~D10 · ④는 4개가 몰림` 이라고 이미 경고한 구간이다.** 10개를 유지하되 자를 순서를 지금 못박는다.

```
못 자름 ─────────────────────────────────────────
 1  시드 적재         유저 100만 + 이력 300만       D5 게이트
 2  오염셋 주입       제약 없는 CORRUPT 스키마      D10 게이트
 3  verify FULL       합격 판정을 지는 유일한 잡    D10 게이트
 4  통계 집계         대시보드 3테이블의 유일 원천
 5  리포트 생성       ★ 과제 필수요건 (PRD:91)
───────────────────────────────────────────────
 6  만료 배치         재고 복원 + 동시성 테스트 5번의 재료
 7  verify INCREMENTAL
 8  Kafka DLT 재처리
 9  idempotency 24h 정리
10  대기열·Entry-Token 정리
───────────────────────────────────────── 컷 ↑
```

**자르는 순서는 10 → 6.** 근거는 이렇다.

| # | 자르는 근거 |
|---|---|
| **10** | `entryToken` 은 **Redis TTL 180초가 이미 처리한다.** TTL 만료가 곧 슬롯 반납이라 정리 배치가 하는 일이 거의 없다 |
| **9** | 24시간 경과분 정리인데 **15일짜리 데모에서는 트리거조차 잘 안 된다.** 테스트하기도 어렵다 |
| **8** | ③의 Kafka 계약(토픽명·DLT 페이로드·오프셋 의미)에 종속적이다. **`R1`(D8 v3 축소)이 발동하면 통째로 사장된다** |
| **7** | FULL 이 합격 판정을 지므로 없어도 게이트는 통과한다. **부하 중 실행은 성립하지 않는다** (4절 ⑧) |
| **6** | 마지막까지 지킨다. **이 잡의 실제 값어치는 재고 복원이 아니라 동시성 테스트 5번**이고, PRD 가 *"테스트 전략 자체가 득점 요소"* 라고 명시했다 |

> **6번을 7번보다 뒤에 자르는 이유** — 만료 배치를 ④가 가져온 근거는 *"재고를 움직이는 잡과 검증하는 잡을 한 사람이 본다"* 였다. 그런데 자를 수 있는 것 중 1순위에 놓으면 **압력이 오는 순간 그 근거가 증발하고**, ①이 갑자기 받아야 한다.
>
> 그리고 검증 대상 `EXPIRED` 데이터는 **시드가 직접 심으므로** 만료 배치가 없어도 만들어진다. 즉 이 잡의 값어치는 데이터 생성이 아니라 **`발급 + 만료 배치 동시 실행 → 불변식 유지`** 라는 배치-런타임 경합 시나리오 하나다. 그게 이 프로젝트에서 유일한 배치 관련 동시성 증거다.

**컷 신호** — `D8` 시점에 6~10 중 **착수도 못 한 잡이 2개 이상**이면 그 자리에서 아래에서부터 자른다. **결정자는 ④ 본인이고, 자른 사실을 그날 팀에 공유한다.** 밀린 채로 D10 을 맞지 않는다.

> `R9`(⑤ 과부하)에는 사후 대응이 있는데 **④ 과부하에는 리스크 항목조차 없다.** 위 컷 순서를 `R13` 으로 리스크 표에 등록할 것.

## 3. 문서에서 답이 나온 것 — 채워 넣었다

인터뷰가 미결로 남겼지만 우리 문서에 이미 답이 있던 것들이다. **D1~D2 안건에서 빼도 된다.**

### 검증 규칙은 6개고, 오염 유형과 1:1이 아니다

**이게 인터뷰의 가장 큰 오독이었다.** "오염 유형 = 검증 규칙"이라고 잡고 Step 을 `행순회 4 / 집계 2` 로 나눴는데, 실제 규칙 목록(`02-erd-decisions.md:49-56` + F3)은 이렇다.

| 규칙 | 위반 발생 단위 | `finding_type` | Step |
|---|---|---|---|
| **V1** 재고 정합 | **캠페인** | `STOCK_MISMATCH` | **집계** |
| **V2** 1인 1매 위반 | **(캠페인, 회원)** | `DUP_PER_MEMBER` | **집계** |
| **V3** 이력 리플레이 | 쿠폰 | `REPLAY_MISMATCH` | 행 순회 |
| **V4** 불법 전이 | **이력 행** | `ILLEGAL_TRANSITION` | 행 순회 |
| **V5** 사용 실적 정합 | 쿠폰 | `USAGE_MISMATCH` | 행 순회 |
| **V6** 등급 자격 위반 | 쿠폰 | `GRADE_VIOLATION` | 조인 |

**Step 분할은 `집계 2 / 행 순회 3` 이다.** `4 / 2` 가 아니다.

> 오염 유형은 *주입하는 데이터의 종류*이고 검증 규칙은 *잡아내는 로직의 종류*다. 하나의 규칙이 여러 오염 유형을 잡는다. 예: `V1 재고 정합` 하나가 오염 유형 1(재고는 줄었는데 ISSUE 이력 없음)과 3(CANCEL_USE 이중 복원)을 모두 잡는다.

### `verification_findings` 는 다형 키다 — F1 확정

```sql
verification_findings(
  id           BIGINT PK,
  run_id       BIGINT FK,
  finding_type VARCHAR(40),
  campaign_id  BIGINT NULL,      -- V1
  member_id    BIGINT NULL,      -- V2
  coupon_id    BIGINT NULL,      -- V3 · V5
  history_id   BIGINT NULL,      -- V4

)
```

**`coupon_id` 하나로는 5개 규칙 중 3개가 표현이 안 된다.** `expected`/`actual` 은 어느 형태로 가든 넣는다 — 없으면 리포트가 *"쿠폰 812934가 이상함"* 까지만 말한다.

### 더미데이터 분포 — 11종 전부 `PRD:262~293` 에 있다

```
유저        100만 · VIP 5 / GOLD 15 / SILVER 30 / WELCOME 50%
활동 분포   파레토 — 상위 30만이 이력의 80%
캠페인      과거 144 + 현재 3 = 147
이력        300만 (쿠폰 300만 · 이력 약 520만 — 02-erd-decisions.md:281)
상태 분포   ISSUED 40 / USED 35 / EXPIRED 15 / CANCELLED 10 %

만료 임박   1%가 24시간 내 만료
시간축      최근 1~2개월 ISSUED 우세 / 3~6개월 USED / 7~12개월 EXPIRED
결정론      고정 난수 시드 + as-of 기준시각
```

**`CANCELLED 10%` 가 없으면 `active_count` 누적 오탐 서사가 죽는다**(`PRD:958`). **소진율 60~100% 흩뿌림이 없으면 "잔여재고 > 0" 분기가 한 번도 안 돈다.** 비율 기반 생성기로 짜야 `R4` 폴백의 *"분포 비율은 유지"* 가 코드로 성립한다.

### CLEAN / CORRUPT 는 물리적으로 분리된 스키마

`01-what-we-build.md:98-108` 이 이미 결정했다. 오염 유형 5·6이 `code UNIQUE` 와 `uk_campaign_member` 에 걸려 `INSERT` 가 거부되기 때문에 **제약 없는 별도 스키마**를 쓴다.

### 검증하지 않는 것 — F6

`coupon_templates.stock_per_occurrence` ↔ `coupon_stocks.total_quantity` **불일치는 정상이다.** 과거 캠페인 144개의 재고를 `18,000~34,000` 으로 흩뿌리므로 전부 어긋난다.

**Seed 에 "검증하지 않는 것" 섹션을 반드시 둔다.** 안 적으면 구현자가 이걸 규칙으로 추가하고, 그러면 **정상셋 0건이 원천적으로 불가능해진다.**

### 정렬 타이브레이커

이력 리플레이의 `ORDER BY` 를 **`(created_at, id)`** 로 고정한다. 같은 시각 이력 2건의 순서가 안 정해지면 리플레이 결과가 실행마다 달라져 checksum 이 흔들린다.

> `04-review-checklist.md:91` 은 `occurred_at` 으로 적혀 있는데 스키마 컬럼명은 `created_at` 이다. 체크리스트 쪽을 정정한다.

### 리포트의 PII 규칙 — `PRD:2062` 가 이미 정했다

> 집계값만. **`member_id` 는 남기되 이름·연락처 금지.**

`member_id` 는 내부 식별자라 마스킹 대상이 아니다 — 마스킹하면 *"어느 회원이 중복 발급됐는지"* 를 쓸 수 없다. 다만 `DUP_PER_MEMBER` finding 이 `member_id` 를 담으므로 **`members` 테이블 조인 유혹이 구조적으로 존재한다.** 리포트·통계 쿼리에서 `members` 조인 금지를 규칙으로 박는다.

### ② 등급 자격 위반 — 해소됨 ✅ 검증 배치 소관이다

문서가 이미 명시했다.

> `02-erd-decisions.md:38` — *"발급 경로는 JWT 클레임으로 DB를 안 타고, **검증 배치만** 4행짜리 테이블을 조인해 `(mask & bit_value) = 0` 으로 위반을 잡는다. **뜨거운 경로와 차가운 경로를 다르게 다룬 것**이 정확하다."*

**`V6 GRADE_VIOLATION` 으로 규칙에 넣는다.**

```sql
V6  등급 자격 위반
    coupons JOIN campaigns JOIN members JOIN grades
    WHERE (campaigns.eligible_grades_mask & grades.bit_value) = 0
    위반 단위: 쿠폰
```

`PRD:930` 의 정합성 지표 5개 중 **4개가 검증 배치 산출물**이다(초과 발급 · 1인 초과 · 이력↔재고 불일치 · 등급 위반). 나머지 하나(미영속 발급)만 드리프트 영역이다. **하나만 빼면 지표표에 구멍이 난다.**

**단, 오염 유형 추가 여부는 판단이 필요하다.** V5 때 F3 가 유형 7을 추가한 것과 같은 논리를 적용하면 유형 8이 생기고 오염셋이 **800건**이 된다. 안 넣으면 V6 가 오염셋으로 검증되지 않는다 → **안건 ① 과 묶어서 결정한다.**

### ③ `asOf` 결정론 — 해소안 ✅

> 게이트가 `HIGH` 로 막았던 항목. **아래 3층으로 해소한다.**

#### 먼저 — 규칙별로 무엇을 읽는지 가른다

| 규칙 | 읽는 것 | `asOf` 재구성 |
|---|---|---|
| **V4** 불법 전이 | `coupon_histories` 만 | ✅ **순수 append-only** |
| **V2** 1인 1매 | 쿠폰 존재 여부 | ✅ 이력의 `ISSUE` 이벤트로 재구성 |
| **V5** 사용 실적 | 상태 ↔ `coupon_usages` | ✅ `used_at`·`canceled_at` 이 둘 다 시각이다 |
| **V3** 이력 리플레이 | 리플레이 ↔ `coupons.status` | ❌ **정의상 현재를 봐야 한다** |
| **V1** 재고 정합 | 집계 ↔ `coupon_stocks.active_count` | ❌ **카운터는 현재값만 존재한다** |
| **V6** 등급 자격 위반 | `members.grade` (현재) | ⚠️ **등급이 변하면 오탐** — 아래 참조 |

**현재 행을 읽어야 하는 건 V1·V3·V6 셋이고, V1·V3는 그게 규칙의 정의다.** V3는 *"현재 상태가 이력과 맞나"*, V1은 *"현재 카운터가 맞나"* 를 묻는다. 현재를 안 읽으면 규칙이 성립하지 않는다.

> **V6 만 성격이 다르다.** 등급 자격은 **발급 시점** 기준이어야 하는데 `members.grade` 는 현재값이다. 회원이 `GOLD → SILVER` 로 강등되면 정상 발급이 위반으로 잡힌다.
>
> **이번 범위에서는 안전하다** — 더미데이터에 등급 변경 이력이 없고 등급 변경 기능도 만들지 않는다. 다만 `PRD:1677` 이 `discount_amount` 를 *"스냅샷은 시점 고정이라 애초에 변하지 않으므로 검증 대상이 아니다"* 로 처리한 것과 **같은 논리로 `coupons.issued_grade` 스냅샷 컬럼이 정석**이다. 등급 변경이 생기는 순간 필요해진다.

#### 층 1 — 이력 재구성 결과를 재사용한다 (구조)

**V3가 이미 `asOf` 시점 상태를 재구성한다.** 그 산출물을 버리지 말고 테이블로 남기면 나머지 규칙이 공짜로 쓴다.

```
Step 0   이력 리플레이 → asof_state (쿠폰별 asOf 시점 상태)
           WHERE coupon_histories.created_at <= asOf
           ORDER BY (created_at, id)          ← 타이브레이커
────────── 여기부터 완전 결정론 ──────────
Step 1   V4  불법 전이       이력만
Step 2   V2  1인 1매         asof_state 집계
Step 3   V5  사용 실적       asof_state ↔ usages
                             활성 사용 = used_at <= asOf
                                      AND (canceled_at IS NULL OR canceled_at > asOf)
────────── 여기부터 현재 행을 읽음 ──────────
Step 4   V3  리플레이 대조   asof_state ↔ coupons.status
Step 5   V1  재고 정합       asof_state 집계 ↔ coupon_stocks.active_count
Step 6   V6  등급 자격       coupons ⋈ campaigns ⋈ members ⋈ grades
────────────────────────────────────
Step 7   통계 집계 (CLEAN 만)
```

**`asof_state` 는 추가 비용이 아니다.** V3가 어차피 만드는 중간 산출물을 테이블로 내보내는 것뿐이다.

**현재 상태에 의존하는 V1·V3를 마지막에 둔다.** 앞의 결정론적 규칙이 먼저 끝나므로, 폭주로 중단돼도 결정론적 부분은 이미 확보된다.

#### 층 2 — 데이터 지문으로 "같은 데이터"를 증명한다 (감지)

과제 요구는 *"**같은 데이터 기준으로** 재실행하면 같은 결과"* 다. **데이터가 바뀌었으면 결과가 달라지는 게 정상이다.** 문제는 *"데이터가 안 바뀌었는데 결과가 다른 것"* 이고, 지금은 그 둘을 구분할 수단이 없다.

```sql
verification_runs
  as_of                DATETIME
  dataset_fingerprint  CHAR(64)   -- ★ 신규
  findings_checksum    CHAR(64)
```

```
dataset_fingerprint = SHA256(
    max(coupon_histories.id)    WHERE created_at <= asOf,
    count(coupon_histories)     WHERE created_at <= asOf,
    count(coupons),
    sum(coupon_stocks.active_count),
    max(coupons.updated_at)                    -- F7 이 추가한 컬럼
)
```

| 지문 | checksum | 판정 |
|---|---|---|
| 같음 | 같음 | ✅ **결정론 증명** |
| 같음 | 다름 | 🔴 **검증기 버그** — 이게 진짜 잡고 싶던 것 |
| 다름 | — | 데이터가 바뀜. **비교 대상이 아니고, 그걸 안다** |

**지문이 없으면 세 번째 경우가 두 번째로 오인된다.** 만료 배치가 한 건 돌았을 뿐인데 "검증이 비결정적"으로 보고된다.

#### 층 3 — 판정하는 순간에만 얼린다 (운영)

*"언제나 결정론"* 은 과잉이다. **판정 시점에만 결정론이면 충분하다.**

```
D10 게이트 · 영상 녹화 · 제출 시
  1  부하 종료 확인
  2  만료 배치 정지          ← ④ 소유라 우리가 끈다
  3  INCREMENTAL 스케줄 정지
  4  오염 주입 완료 확인
  5  FULL 2회 연속 실행 → 지문·checksum 일치 확인
```

개발 중에는 지문이 달라도 신경 쓰지 않는다. **얼리는 건 판정할 때뿐이다.**

#### 덤 — 안건 ⑦(만료 지연)이 같이 풀린다

`expires_at < asOf` 인데 `status = ISSUED` 인 쿠폰(만료 배치가 아직 안 돈 것)이 이력 재구성에서는 이렇게 처리된다.

```
이력에 EXPIRE 이벤트 없음  →  asof_state = ISSUED
coupons.status             =  ISSUED
                              일치 → finding 아님 ✅
```

**오탐이 원천적으로 안 생긴다.** "만료 지연 건수"는 finding 이 아니라 **별도 관측 지표**로 둔다 — 지연 자체는 결함이 아니라 배치 주기의 함수다.

### ④ 리포트 — 해소됨 ✅ 두 얼굴이 있다

문서에 흩어져 있던 단서를 모으면 리포트는 **하나가 아니라 둘**이다.

| | 근거 | 무엇 |
|---|---|---|
| **개발용 화면** | `02-erd-decisions.md:63` — *"검증 리포트 자동화가 선택사항이라도 이건 있어야 한다 — **우리가 개발 중에 제일 많이 볼 화면**이니까"* | run 하나의 findings 목록. `expected`/`actual` 이 보여야 뭐가 어떻게 틀렸는지 읽힌다 |
| **제출 문서** | `PRD:1078` — D13 산출물이 *"측정 데이터 확정, **리포트**, 기획 서사 문서, 발표 자료"* 로 묶여 있다 | 최종 run 의 요약. 발표·제출물 |

**같은 데이터원에서 나온다** — `verification_runs` + `verification_findings`. 형태만 다르다.

```
개발용   GET /api/v1/admin/verify/runs/{runId}    JSON
         → ⑤가 "검증 실행 이력" 패널에서 렌더링
제출용   최종 run 을 Markdown 으로 덤프           D13에 1회
```

**PII 규칙은 `PRD:2062` 가 이미 정했다** — *"집계값만. `member_id` 는 남기되 이름·연락처 금지."* `members` 조인 금지를 코드 규칙으로 박는다.

**저장 위치 충돌도 해소된다** — 개발용은 API 라 파일이 없고, 제출용 Markdown 은 `.gitignore` 의 `*.csv` 에 안 걸린다. `docs/` 아래 커밋한다.

> **④에게 남는 일은 API 하나뿐이다.** 렌더링은 ⑤ 소관이고, 제출 문서는 D13에 최종 run 을 한 번 덤프하면 된다.

### ⑤ 정답 매니페스트 — 해소됨 ✅ 주입 잡이 정답을 낳는다

문서에 답은 없지만 설계가 기계적이다. **오염을 심는 잡이 자기가 뭘 심었는지 알고 있으므로**, 심으면서 정답을 같이 쓰면 된다.

```sql
expected_findings(
  seed_run_id   BIGINT,        -- 어느 주입 실행이 만든 정답인가
  finding_type  VARCHAR(40),   -- V1~V6 상수와 동일
  campaign_id   BIGINT NULL,   -- verification_findings 와 같은 다형 키
  member_id     BIGINT NULL,
  coupon_id     BIGINT NULL,
  history_id    BIGINT NULL,
  corrupt_type  TINYINT,       -- 오염 유형 1~7(8)
  UNIQUE (seed_run_id, finding_type, campaign_id, member_id, coupon_id, history_id)
)
```

**판정은 count 비교가 아니라 집합 비교다.**

```sql
누락 = expected_findings  MINUS  verification_findings   -- 못 잡은 것
오탐 = verification_findings  MINUS  expected_findings   -- 잘못 잡은 것

합격 = 누락 0건 AND 오탐 0건
```

**`findings_checksum` 만으로는 `run1 == run2` 밖에 증명하지 못한다.** *"검출된 700건이 주입한 그 700건인가"* 는 다른 질문이고, **오탐 350 + 미검출 350 도 count 는 700이다.**

| 수단 | 증명하는 것 |
|---|---|
| `findings_checksum` | 재실행 결정론 (`run1 == run2`) |
| `dataset_fingerprint` | 두 run 이 같은 데이터를 봤는가 |
| **`expected_findings` 집합 비교** | **검출이 정확한가** (D10 게이트) |

**셋이 서로 다른 것을 증명한다.** 하나도 뺄 수 없다.

> 정답 매니페스트는 `CORRUPT` 스키마에만 있으면 된다. `CLEAN` 셋의 기대값은 *"0건"* 이라 테이블이 필요 없다.

### ⑥ 배치 서버 토폴로지 — 해소됨 ✅ 검증 배치는 L1에서 돈다

`PRD:1705-1712` 의 3층 정의가 답이다.

| 층 | 환경 | 목적 | 비교표 |
|---|---|---|---|
| **L1** | 각자 노트북 · Docker Compose | **정합성만 확인.** 1,000 동시 | **절대 안 됨** |
| **L2** | 팀 공용 지정 1대 · 2 vCPU / 8GB | 비교표를 여기서만 채움 | 여기 수치만 |
| L3 | 별도 서버 | 10만+ 트래픽 | 별도 표 |

**L1의 목적이 문자 그대로 "정합성만 확인"이다.** 검증 배치는 정확히 그 용도이므로 **L1에서 돈다.**

**그래서 L2에는 배치가 없다.** `L2 기준 환경` 이 `Boot 1대 · Redis 1대 · MySQL 1대 · k6 같은 머신` 으로 고정돼 있고, 여기에 배치를 얹으면 *"팀원 노트북 수치를 비교표에 넣으면 오염된다"* 는 것과 **같은 이유로** 비교표가 오염된다.

```
검증 배치      L1 · 별도 프로세스 (Docker Compose 서비스 하나 추가)
부하 측정      L2 · 배치 없음
```

**커넥션 풀은 L1에서도 분리한다.** 같은 노트북에서 앱과 배치가 같은 MySQL 을 물기 때문에, 검증 전용 풀을 두지 않으면 개발 중 앱이 멈춘다.

### ⑦ 만료 3계층 — 해소됨 ✅ 흩어진 조각을 모으면 나온다

단어 자체의 정의는 문서에 없지만, 만료 관련 조항이 정확히 **3개** 있다.

| 계층 | 근거 | 하는 일 | 소유 |
|---|---|---|---|
| **1. 배치** | `PRD:799` — `ISSUED → EXPIRED 만료 배치` | 주기적으로 `expires_at < now` 인 `ISSUED` 를 `EXPIRED` 로. **재고 +1 복원** | **④** |
| **2. 사용 시점 거부** | `PRD:664` — 만료 쿠폰 사용 → `409 COUPON_EXPIRED` | 배치가 아직 안 돌았어도 사용을 막는다 | ① |
| **3. 조회 시점 판정** | `PRD:376` — *"`expires_at` 은 만료 판정의 **유일한** 기준"* | 쿠폰함에서 `expires_at < now` 면 만료로 표시 | ① |

**2·3 계층이 존재하는 이유가 1계층의 지연 때문이다.** 배치가 늦게 돌아도 사용은 거부되고 화면엔 만료로 보인다.

**④가 가져온 건 1계층뿐이다.** 2·3은 런타임 경로라 ① 유지.

> **그래서 "만료 지연"은 결함이 아니다.** 2·3 계층이 사용자를 보호하므로 지연의 유일한 영향은 *"재고가 아직 안 돌아왔다"* 뿐이고, 그건 배치 주기의 함수다. 검증에서는 `4절 ③` 의 이력 재구성으로 오탐이 원천 차단된다.

### ⑧ 부하 중 INCREMENTAL — 해소됨 ✅ 돌릴 수 없다

**인터뷰에서 "돌린다"로 정했으나 근거가 무너졌고, 문서상으로도 불가능하다.**

당시 근거는 *"v3는 비동기라 부하 중 격차가 정상적으로 발생하는데, 그게 시간에 따라 수렴하는 걸 실시간으로 보이는 게 핵심 서사"* 였다. **그런데 그 일은 이미 ①의 1초 드리프트가 한다.** `패널 19`가 정확히 `Redis↔DB 격차`를 부하 중 실시간으로 그린다.

즉 부하 중 INCREMENTAL 이 추가로 얻는 것은 "격차의 *유형*까지 식별" 하나뿐인데, `PRD:304` 가 *"부하 중 일시적 차이는 **v3의 비동기 특성상 정상**"* 이라고 못박았으므로 **그 유형 정보 자체가 의미가 없다.**

```
얻는 것   유형 식별          ← 부하 중 격차는 "정상"이라 유형이 무의미
잃는 것   verification_findings 오염 — "위반 0건" 발표 화면에 위반이 뜬다
          측정 간섭 — OFF/ON 2회 측정이면 부하 시나리오가 2배
          L2 슬롯 경합 — ②⑤의 k6 일정을 밀어낸다
```

**그리고 안건 ⑥이 이걸 문서 차원에서 닫는다.**

부하는 **L2** 에서 돌고 검증 배치는 **L1** 에서 돈다. *"부하 중에도 INCREMENTAL 을 돌린다"* 는 것은 **L2 에 배치를 얹는다는 뜻**인데, `PRD:1705` 가 L2 를 *"비교표의 유일한 출처"* 로 못박았다. 배치를 얹는 순간 그 수치를 못 쓴다.

```
L1 에서 돌린다  →  부하가 L2 에 있으므로 "부하 중"이 아니다. 관측할 대상이 없다
L2 에서 돌린다  →  비교표가 오염된다. L2 의 존재 이유가 사라진다
```

**어느 쪽도 성립하지 않는다.**

**결론: 부하 구간에는 INCREMENTAL 을 멈추고 부하 종료 직후 1회만 돌린다.** 실시간 관측은 ①의 드리프트 패널(`패널 19`)에 맡긴다 — 그게 애초에 그 패널의 일이다.

> 인터뷰에서 "돌린다"로 정했던 것을 뒤집는다. 당시 근거로 내가 제시한 *"격차 수렴을 실시간으로 보이는 게 핵심 서사"* 는 **①의 드리프트가 이미 하는 일**이었다. 남의 잡의 목적을 근거로 삼은 것이 오류였다.
