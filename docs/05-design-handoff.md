이 문서 하나로 화면을 그릴 수 있게 썼다. 앞선 대화나 다른 문서를 안 봐도 된다.

**출처 세 곳** — `docs/PRD-v4.15.md`(요구사항 원본), `docs/01-what-we-build.md`(흔들리지 않는 축), 그리고 **이미 만들어진 프론트엔드** `world-to-code/coupon-magic-96`(TanStack Start + TS, 라우트 11개, 전부 목업).

## 1. ⚠️ 용어가 앞뒤로 어긋나 있다 — 제일 먼저 읽을 것

**PRD/백엔드와 프론트가 같은 것을 다른 이름으로 부른다.** 이걸 모르고 붙이면 통합에서 반드시 사고가 난다.

| PRD · 백엔드 | 프론트 | 무엇인가 |
|---|---|---|
| **`campaign`** | **`Coupon`** | 발급 **대상 이벤트**. 재고·오픈시각·등급조건을 가진다 |
| **`coupon`** | **`Issuance`** | **발급된 개별 쿠폰**. 상태 4종을 가진다 |
| `campaign_id` | `couponId` | |
| `member_id` | `userId` | |

```
PRD    POST /api/v1/campaigns/{id}/issue   →  coupon 이 만들어진다
프론트  postIssue(couponId)                 →  Issuance 가 만들어진다
                     ↑ 같은 것을 가리킨다
```

**둘 중 하나로 통일하지 않는다.** 프론트를 다 고치는 비용이 크고, PRD 용어는 채점 문서라 못 바꾼다. 대신 **API 경로는 PRD(`/campaigns`)를 따르고, 프론트가 어댑터에서 이름을 바꾼다.** `src/lib/api.ts` 한 파일만 손대면 된다.

### 그리고 재고 카운터의 의미가 위험하다

`docs/01-what-we-build.md` 의 **1번 축**:

```
active_count = 현재 ISSUED + USED 개수   (취소·만료 시 감소)
잔여 = total_quantity − active_count
```

> `issued_count` 라고 쓰는 순간 **누적 발급 수**로 읽히고, 초과 발급 판정이 통째로 어긋난다.

**그런데 프론트가 정확히 그 이름을 쓴다.**

```ts
interface Coupon { totalStock, issuedCount, usedCount }
remaining = Math.max(0, c.totalStock - c.issuedCount)   // ← 취소가 일어나면 어긋난다
```

**백엔드는 `active_count` 를 유지하고, 응답 필드명을 `issuedCount` 로 내리되 값은 "현재 보유량"이어야 한다.** 아니면 프론트가 `activeCount` 로 이름을 바꾼다. **둘 중 하나를 지금 정해야 한다** — 더미데이터에 `CANCELLED` 가 10%(30만 장) 있어서 누적으로 재면 정상 데이터가 대량 오탐된다.

## 2. 브랜드 자산

로고는 두 종이고 **역할이 갈린다. 섞어 쓰면 안 된다.**

### A — 가로형 로고 (캐릭터 좌 + 타이포 우)

요소가 적고 좌우로 길다. 캐릭터가 타이포를 가리키는 구조라 시선이 오른쪽으로 흐른다.
**UI 의 일부**로 취급한다 — 어느 화면에나 붙을 수 있다.

| 쓸 곳 | 크기 |
|---|---|
| 글로벌 헤더 (데스크탑) | 높이 36~40px |
| 글로벌 헤더 (모바일) | 높이 28px — **타이포만 쓰는 변형** |
| 로그인 / 회원가입 | 폭 240px |
| 관리자·대시보드 좌상단 | 높이 32px |

필요한 변형 3종: `A-full`(캐릭터+타이포) · `A-type`(타이포+리본만) · `A-dark`(아웃라인 흰색)

### B — 키비주얼 (캐릭터 중앙 + 쿠폰 부채꼴 + 반짝임)

쿠폰이 부채꼴로 펼쳐진 게 **"여러 쿠폰이 있다"를 그림으로 말한다.**
**콘텐츠**로 취급한다 — "지금 이 순간이 특별하다"고 말할 때만 나온다.

| 쓸 곳 | 크기 |
|---|---|
| 랜딩 히어로 | 폭 600~800px |
| 발급 성공 모달 | 폭 280px |
| 쿠폰함 빈 상태 | 폭 200px |
| OG 이미지 / 공유 카드 | 1200×630 |

### 금지

- **B 를 헤더에 쓰지 마라.** 32px 로 줄이면 쿠폰 부채꼴이 정체불명 얼룩이 된다
- **B 를 대시보드에 쓰지 마라.** 차트가 안 읽힌다. 거긴 A 만
- **둘 다 파비콘으로 쓰지 마라** → **캐릭터 얼굴 원형 크롭**을 따로 만든다
- **3D 아웃라인 레터링(`쿠폰 야~호` 스타일)은 로고 안에서만.** 버튼·헤딩·라벨에 쓰면 즉시 촌스러워진다
- **반짝임은 B 에 딸린 것.** UI 에 따로 뿌리지 않는다. 발급 성공 애니메이션에서만 재사용

## 3. 디자인 토큰 — 프론트 구현값이 정본

색은 **oklch** 로 정의돼 있다. hex 로 바꾸지 마라.

```css
--radius: 0.75rem;                        /* 12px */
--background: oklch(0.98 0.005 250);
--foreground: oklch(0.22 0.055 265);
--primary:    oklch(0.26 0.075 264);      /* 네이비 — 텍스트·헤더·주요 CTA */
--accent:     oklch(0.56 0.095 250);      /* 스카이 — 링크·강조 */
--muted:      oklch(0.945 0.01 250);
```

**다크모드는 전 화면 지원한다** (사용자 화면 포함). `.dark` 블록에 대응값이 있다.

### 의미색 — 액센트와 분리

```
success (정상) · warning (주의) · destructive (위험) · muted (비활성)
```

대시보드 임계 표현에 쓴다. 액센트(스카이)와 절대 섞지 않는다.

### 등급색 4종

```
grade-vip · grade-gold · grade-silver · grade-welcome
```

**골드는 VIP·GOLD 배지에만 극소량.** 넓은 면에 쓰면 싸구려가 된다.

### 브랜드 고유색 12종

파스텔 팔레트 대신 **브랜드마다 고유색이 시드에 박혀 있다.** 카드·캘린더 배지에 이 색을 쓴다.

```
모카빈 #8b5e3c · 씨네플러스 #c0392b · 버거하우스 #e67e22 · 프레시마트 #27ae60
북스토리 #2d6cb5 · 필름아레나 #8e44ad · 스포츠존 #16a085 · 뷰티랩 #d81b60
딜리버리고 #f39c12 · 트래블온 #0097a7 · 게임패스 #5b3fd6 · 헬스클럽 #455a64
```

### 타이포

한글 산세리프(Pretendard 계열). **웨이트 대비를 크게.**
**숫자는 반드시 `tabular-nums`** — 카운트다운·재고·p99 가 1초마다 갱신되는데 폭이 흔들리면 화면이 떨린다.

### ⚠️ 쿠폰 티켓 컴포넌트가 아직 없다

프론트 계획엔 *"점선 절취선, 반원 노치"* 가 명시돼 있는데 **`coupon-card.tsx` 가 존재하지 않는다.** shadcn `Card` 를 그대로 쓰고 있다.

**이게 브랜드 정체성의 핵심이라 만들어야 한다.**

```
┌─────────────────────────┐
│                         │
◗  40% 할인 (최대 2만원)   ◖   ← 좌우 반원 노치
│  ☕ 모카빈               │
│ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ │   ← 점선 퍼포레이션
│  ~2026.08.31    [받기]   │
└─────────────────────────┘
   라운드 12px · 그림자 옅게 · 좌측에 브랜드 고유색 레일
```

상태별 처리:

| 상태 | 처리 |
|---|---|
| 발급 가능 | 선명, `받기` 활성 |
| 이미 받음 | 흐리게 + `발급완료` 리본 |
| 매진 | 회색조 + `SOLD OUT` |
| 등급 미달 | 자물쇠 + 필요 등급 표시 |
| 사용됨 | 채도 낮춤 + `USED` 대각선 스탬프 |
| 취소됨 | 회색조 + 점선 테두리 |
| 만료됨 | 회색조 + 우상단 모서리 접힘 |

## 4. API 계약 — 백엔드가 반드시 맞춰야 하는 것

**프론트가 이미 이 전제로 동작한다.** 못 맞추는 게 있으면 지금 말해야 한다. `src/lib/api.ts` 는 "실제 연동 시 함수 본문만 fetch 로 교체" 하도록 격리돼 있다.

### 4.1 엔드포인트 (PRD §11.1)

공통 헤더 `X-User-Id` · `X-User-Grade` · **상태 변경은 `Idempotency-Key` 필수**
관리자 API는 추가로 `X-User-Role: ADMIN`을 요구한다. 이 헤더들은 인증 토큰이 아니라
회원·등급·역할을 구분하기 위한 요청 값이며 JWT는 사용하지 않는다.

| Method | Path | 프론트 함수 |
|---|---|---|
| GET | `/api/v1/brands` | `getBrands()` |
| GET | `/api/v1/campaigns` | `getCoupons()` |
| GET | `/api/v1/campaigns/me` | 내 등급 참여 가능만 |
| POST | `/api/v1/campaigns/{id}/entry` | `postEntry()` |
| GET | `/api/v1/campaigns/{id}/queue` | `getQueue()` — **폴링 1초** |
| POST | `/api/v1/campaigns/{id}/issue` | `postIssue()` — **Entry-Token 필수** |
| POST | `/api/v1/coupons/{id}/use` | `postIssuanceAction('use')` |
| POST | `/api/v1/coupons/{id}/cancel-use` | `postIssuanceAction('cancel-use')` |
| POST | `/api/v1/coupons/{id}/cancel` | `postIssuanceAction('cancel')` |
| CRUD | `/api/v1/admin/brands` · `/schedules` · `/campaigns` | `adminList*` / `adminSave*` |
| POST | `/api/v1/admin/verify` | 검증 배치. JSON body `{asOf, dataset, scope}` → **202 + runId** |
| GET | `/api/v1/admin/stats` | 통계 |
| GET | `/api/v1/admin/metrics?window=` | 관제 시계열 — **폴링 1초** |
| GET | `/api/v1/admin/benchmarks` | 버전별 측정 |
| GET | `/actuator/admission-capacity` | 입장 여력 |

검증 실행은 브라우저가 Batch를 직접 호출하지 않는다. 브라우저는 API의
`POST /api/v1/admin/verify`만 호출하고, API가 내부 네트워크에서 Batch 업무 포트
`9091`의 verify 트리거에 같은 `{asOf, dataset, scope}` 명령을 전달한다. `asOf`를 query
parameter로 보내지 않는다. Batch Actuator는 관리 포트 `9092`에만 열며 Prometheus가
내부에서 접근한다.

**★ 신규 2종**

| Method | Path | 용도 |
|---|---|---|
| GET | `/api/v1/calendar?from&to` | 캘린더 — 기간 내 브랜드데이 회차 |
| GET·POST | `/api/v1/admin/engine` | 엔진 전환 · `{version, redisCB, dbCB, kafkaCB}` |

### 4.2 에러 코드 11종 — 문자열이 정확히 일치해야 한다

프론트에 **코드별 한국어 안내 문구가 매핑**돼 있다. 오타 하나면 안내 대신 기본 메시지가 뜨는데 **에러가 안 나서 아무도 모른다.**

| code | HTTP | 언제 | 추가 필드 |
|---|---|---|---|
| `STOCK_EXHAUSTED` | 409 | 재고 소진 | |
| `ALREADY_ISSUED` | 409 | 이미 발급받음 (1인 1매) | |
| `GRADE_NOT_ELIGIBLE` | 403 | 등급 미달 | `requiredGrades[]` |
| `NOT_OPENED` | 409 | 오픈 전 | `openAt`, `retryAfterSeconds` |
| `COUPON_CLOSED` | 409 | 마감됨 | |
| `COUPON_EXPIRED` | 409 | 만료된 쿠폰 | |
| `INVALID_TRANSITION` | 409 | 불가능한 상태 전이 | |
| `ENTRY_TOKEN_EXPIRED` | 403 | 입장 토큰 만료 | |
| `NO_ENTRY_TOKEN` | 403 | 입장 절차 없이 발급 시도 | |
| `IDEMPOTENCY_KEY_REUSED` | 409 | 멱등키 충돌 | |
| `TEMPORARILY_UNAVAILABLE` | 503 | 일시적 지연 | `retryAfterSeconds` |
| `UNAUTHORIZED` | 401 | 로그인 필요 | |

**응답 형태**

```ts
ApiError {
  status: number
  code: string
  message: string
  retryAfterSeconds?: number
  openAt?: number
  requiredGrades?: Grade[]
}
```

### 4.3 등급 — INT 비트마스크

```
WELCOME=1 · SILVER=2 · GOLD=4 · VIP=8

MASK_ALL       = 15   전체 등급
MASK_SILVER_UP = 14   실버 이상
MASK_GOLD_UP   = 12   골드 이상
MASK_VIP       =  8   VIP 전용
```

**`eligible_grades_mask` 컬럼이 `INT` 여야 한다.** 프론트가 `mask & GRADE_BIT[grade]` 로 판정한다. ERD 확인 필요.

### 4.4 마스킹은 서버 책임

```ts
interface Issuance { userId, maskedUserId, ... }   // 별도 필드
```

**프론트에서 자르는 게 아니라 서버가 마스킹된 값을 따로 내려주는 계약이다.** 과제가 명시적으로 요구하는 유일한 보안 요건이므로 이걸 프론트에 맡기면 안 된다.

형식: `user123456` → `user****56`

### 4.5 입장 → 대기열 → 발급

```
POST /campaigns/{id}/entry
  → { admitted: true,  entryToken }                    즉시 입장
  → { admitted: false, queueToken, position, etaSeconds }  대기열 배정

GET /campaigns/{id}/queue        (1초 폴링)
  → { position, etaSeconds, admitted }
  → position 0 도달 시 { admitted: true, entryToken }

POST /campaigns/{id}/issue  + entryToken
  → 토큰 검증 후 **1회 소모(삭제)**
  → 없거나 만료면 NO_ENTRY_TOKEN / ENTRY_TOKEN_EXPIRED
```

**`entryToken` 은 한 번 쓰면 소모된다.** 프론트가 그 전제로 동작한다.

### 4.6 상태 전이 — 역방향이 있다

```
        ──사용──→
ISSUED            USED
        ←사용취소──          ← 역방향 허용 (구매 취소)

ISSUED ──발급취소──→ CANCELLED
ISSUED ──만료배치──→ EXPIRED
```

**`USED → ISSUED` 는 편의 기능이 아니라 멱등성 검증의 재료다.** PRD 원문:

> 역방향 전이가 있어야 재고가 양방향으로 움직이고, **"사용취소 중복 요청 → 재고 이중 복원"** 같은 실제 버그가 성립합니다. 멱등성 요구가 장식이 아니게 됩니다.

더미데이터에 `USED` 중 20% 가 사용 → 사용취소 → 재사용 이력을 갖는다.

**UI 에서 사용취소와 발급취소를 구분해야 한다** — 다른 버튼, 다른 엔드포인트, 다른 결과.

### 4.7 할인 정책 3종

| type | 표시 | 필드 |
|---|---|---|
| `RATE_CAP` | `20% 할인 (최대 20,000원)` | `value`(%) + `cap`(원) |
| `FLAT` | `5,000원 할인` | `value`(원), `cap=null` |

### U2 — 브랜드데이 캘린더 `/events` ★ 신규

### ★ 2계층 구조 — 주간 배경 + 수요일 하이라이트

**이게 T멤버십 실물의 구조이고 프로토타입이 그대로 옮겼다.** 단순 월 그리드로 만들면 안 된다.

```
┌────────────────────────────────────────────────────────┐
│ 브랜드 데이                     [🗓 달력] [≡ 목록]      │
│ ◀  2026년 8월  ▶          내 등급만 ☑   카테고리 ▾     │

│                 ┌──────┐                               │

│                 │ 3개  │                               │
│                 └──────┘                               │
│          라운드베이커리 (주간)          D-2             │

**한 주가 한 행이다.** 월~금 5칸 그리드에 주를 관통하는 가로선을 깔고(`top:66%`, `opacity .55`), **수요일 셀만 위아래로 튀어나오게** 한다(`margin:-14px 0`, 흰 배경, `zIndex:2`).

| 계층 | 무엇 | 선착순? |
|---|---|---|
| **주간 브랜드** | 월~금 5일 내내. 행 하단에 라벨 + 틴트 배경 | ❌ **표시 전용** |
| **수요일 브랜드** | 특정 시각 하루. 3개. 솟은 셀에 표시 | ✅ **경쟁 대상** |

**주간 브랜드에는 재고·발급이 없다.** 5일 내내 열려 있으면 경쟁이 안 생기고, 우리가 증명할 것은 "같은 순간에 20,000명"이다. **배경이 있어야 하이라이트가 산다** — 발표에서 *"주간 브랜드는 여유롭게, 수요일 14시 이 세 개가 진짜 경쟁입니다"* 라고 말할 수 있다.

주마다 `accent` 와 `tint` 가 다르다 — 초록 `#F1F7F3` · 파랑 `#EDF3FA` · 붉은색 `#FBF1F3`. **다가올수록 붉어지는 게 아니라 주를 구분하는 용도다.**

```
weekly_features            선착순 대상 아님. 재고·발급 없음
  year_month   VARCHAR     '2026-08'

`CouponTemplate` 은 **건드리지 않는다.** 수요일 하이라이트는 `nthWeek ∈ {2,3,4} × dayOfWeek = 3` 으로 이미 표현된다.

> **5주차 처리 주의** — 매월 N번째 X요일이 달에 따라 없을 수 있다(5번째 수요일 등). `nthWeekdayOf()` 와 **같은 규칙**을 백엔드가 써야 한다. 안 그러면 캘린더와 실제 오픈 날짜가 어긋난다.

### ★ 엔진 전환 관찰 — 전 화면 공통

**전환 UI 는 이미 있다** (`admin.system.tsx`). 없는 건 **전환 전후가 지표로 드러나는 것**이다.

```
[ v1 · DB 비관적 락  ]  [ v2 · Redis 원자 카운터 ]  [ v3 · Kafka 비동기 ]
  정확하지만 처리량 낮음     고성능 재고 차감            최대 처리량, 최종 일관성
                              ●사용 중
```

**전환 시각을 모든 차트에 세로 기준선으로 표시한다.** 라벨 `v1 → v2`. 이게 있어야 "구조를 바꿨더니 이렇게 달라졌다"가 눈에 보인다.

**버전별로 달라져야 하는 지표**

| | v1 · MySQL 락 | v2 · Redis Lua | v3 · Kafka |
|---|---|---|---|
| 처리량 TPS | 낮음 | 높음 | 높음 |
| p99 | **급증** | 낮음 | 낮음 |
| DB 풀 사용률 | **포화 90%+** | 낮음 | 낮음 |
| Redis 지연 | **패널 비활성** | 표시 | 표시 |
| Kafka lag | — | — | **표시** |
| 응답 `202` | 없음 | 없음 | **다수** |
| 19번 격차 | 비활성 | drift | lag |

> **19번 패널은 버전마다 임계가 달라야 한다.** v3 에 v2 임계를 그대로 쓰면 부하 중 내내 빨갛다 — 백로그가 쌓이는 게 정상이기 때문이다. **항상 빨간 패널은 아무도 안 본다.** v1 은 발급 경로에 Redis 를 안 쓰므로 패널을 비활성화하고 사유를 표시한다.

**신규 API** `GET·POST /api/v1/admin/engine` → `{version, redisCB, dbCB, kafkaCB}`

### D1 — 캠페인 운영 (비즈니스) · 8패널 `/admin`

**운영자가 판단에 쓰는 것만. `p99`·`DB풀`·`드리프트`는 여기 없다.**

```
잔여 재고     6,412 / 10,000
발급 진행률   35.9%      3,588장
초당 발급     1,847      peak 2,310
대기 인원     3,204      예상 12초
캠페인 상태   OPEN       14:00 오픈
사용률        41.2%      발급 대비
```

- **⑤ 캠페인별 재고 소진** — line, 여러 캠페인을 같은 축에 겹침
- **⑥ 상태별 보유량** — `ISSUED` `USED` `CANCELLED` `EXPIRED` 4계열
- **⑨ 발급 이벤트 스트림**
- **⑩ 상태 전이 스트림**

**⑨⑩ 이 운영자에게 가장 실질적인 패널이다.** "분명히 눌렀는데 안 됐다"가 선착순 최다 문의이고, 이 둘이 그 답을 직접 보여준다. **영상 촬영에서도 가장 잘 먹힌다.**

```
⑨ 발급 이벤트 스트림                          + 1,847건 생략
14:02:31.442  m_812934  모카빈  MOCA-8F2K  201 발급    VIP
14:02:31.443  m_119287  모카빈  —          409 소진
14:02:31.443  m_772341  모카빈  —          403 등급미달  WELCOME
14:02:31.444  m_004512  모카빈  —          202 대기 #1,847
14:02:31.445  m_338190  모카빈  MOCA-2J7Q  201 발급    GOLD

⑩ 상태 전이 스트림
14:05:12.001  MOCA-8F2K  ISSUED → USED       주문 #88213
14:05:44.882  MOCA-3B1P  USED   → ISSUED     주문 취소
14:06:02.114  MOCA-9K2X  ISSUED → CANCELLED  사용자 취소
14:10:00.000  MOCA-1A2B  ISSUED → EXPIRED    만료 배치
```

> ⚠️ **회원 식별자는 마스킹된 형태(`m_812934`)로만.** 이름·연락처·이메일을 화면에 절대 올리지 않는다. **과제가 명시적으로 요구하는 유일한 보안 요건이다.**
> 응답 코드(`201` `202` `403` `409`)를 임의로 바꾸지 마라. 부하 테스트 집계와 장애 주입 판정의 근거다.

### D2 — 시스템 관제 (엔지니어링) · 9패널 `/admin/system`

| # | 패널 | 형태 | 임계 |
|---|---|---|---|
| 11 | **초과 발급** | stat | **0 정상색 · >0 위험색 경보** |
| 12 | p99 응답시간 | stat | >500ms 주의 · >1000ms 위험 |
| 13 | Circuit Breaker | 배지 ×3 | `redisCB` `dbCB` `kafkaCB` |
| 14 | 응답 결과 rate | line ×5 | 201 · 202 · 409 · 403 · 5xx |
| 15 | 응답시간 분위 | line ×3 | p50 · p95 · p99 |
| 16 | 리소스 사용률 | line ×4 다축 | in-flight · DB풀% · Redis 지연 · Kafka 랙 |
| 17 | 상태 전이 rate | line ×5 | 만료 배치가 스파이크로 튄다 |
| 18 | 대기열 | line ×2 + 배경 밴드 | 모드가 배경색으로 깔림 |
| 19 | **Redis ↔ DB 격차** | line ×2 + 임계선 | **아래 참조 — 2축이어야 한다** |

**11번이 이 프로젝트 전체에서 가장 중요한 패널이다.** 초과 발급 0건이 1순위 채점 지표이고 이 stat 하나가 그 증거다. 화면에서 가장 크고 눈에 띄어야 한다.

> ⚠️ **프론트의 `MetricPoint` 에 초과 발급 필드가 없다.** 지표를 추가해야 이 패널이 산다.

**19번을 2축으로 나눈다** — 단일 수치면 원인을 알 수 없다.

```
db_gap   = total − issued − redisStock      DB 측이 뒤처짐
list_gap = total − redisUsers − redisStock  Redis 사용자 목록이 뒤처짐

db_gap=0, list_gap=0   정상
db_gap>0, list_gap=0   DB 저장 실패 → DLT 재처리 대상
db_gap=0, list_gap>0   Redis users 누락 → 대사 자동 보정 대상
그 외                   자동 보정하지 않고 사람이 확인
```

**두 gap 의 부호 조합으로 원인이 특정된다.** 프론트는 현재 `drift` 단일 수치라 여기를 고쳐야 한다.

### D3 — 분석 · 비교 (발표) · 7패널 `/admin/analytics`

| # | 패널 | 형태 | 무엇을 말하나 |
|---|---|---|---|
| 20 | 버전별 재고 소진 곡선 | line ×3 | v1·v2·v3 를 같은 시간축에 겹침 |
| 21 | 버전별 p99 추이 | line ×3 | 부하 구간 전체의 지연 변화 |
| 22 | 버전별 DB 풀 사용률 | line ×3 | **v1 병목의 시각적 증거** |
| 23 | 버전 비교표 | table | **발표 슬라이드에 그대로 캡처** |
| 24 | 브랜드별 월별 발급 추이 | line ×12 | 12개월 시계열이라 막대가 아니라 선 |
| 25 | 요일 × 시간 히트맵 | heatmap 7×24 | **브랜드데이 요일이 도드라지는가** |
| 26 | 상태 전이 퍼널 | 퍼널 | 발급 → 사용 / 취소 / 만료 비율 |

20~22 가 발표 영상의 정적 그래프 출처다. **26 만 시간축이 없어 다른 형태를 쓴다.**

> 25번 히트맵은 **캘린더(U2)와 같은 데이터의 다른 표현이다.** 브랜드가 요일·시각에 흩뿌려져 있어서 패턴이 그려진다.

## 8. 구현 우선순위 — 못 끝내면 뒤에서부터 자른다

PRD 가 명시한 순서다. **임의로 바꾸지 마라.**

| 등급 | 패널 | 근거 |
|---|---|---|
| **필수** | ① · ⑤ · ⑥ · 11 · 19 | 과제 핵심 조건(초과 발급 0 · 재고 불변식 · 정합성)의 **증거** |
| 권장 | ⑨ · ⑩ 이벤트 스트림 · 14 · 18 | 이벤트 스트림이 영상에서 가장 잘 먹힘 |
| 보통 | ②~④ · 12 · 13 · 15~17 | 화면을 채우는 맥락 지표 |
| 여유 | 20~23 버전 비교 | 정적 캡처로 대체 가능 |
| 최후 | 24~26 분석 | 전부 포기해도 과제 조건에 영향 없음 |

**필수 5개만 남겨도 과제 요건은 충족한다. 자를 땐 D3 부터.**

**사용자 화면 순서** — U3(발급) → U2(캘린더) → U4(쿠폰함) → U1(랜딩).
**U3 없이는 아무것도 시연할 수 없다.** 캘린더가 두 번째인 이유는 서비스 정체성이라 발표 첫 화면이 되기 때문.

## 9. 성능 — 설계 단계에서 잡아야 한다

**24패널을 1초마다 전체 렌더링하면 브라우저가 버벅인다.** PRD 가 리스크로 명시했다.

- 차트 애니메이션 제거 (`update('none')`)
- 데이터 포인트 **300점 롤링**
- **값이 바뀐 패널만 갱신** — 전체 리렌더 금지
- 그래도 끊기면 갱신 주기를 2~5초로 완화 (Grafana 기본도 5초라 손실이 작다)

이벤트 스트림은 **커서 폴링 + 링버퍼**. 전량 렌더링하면 브라우저가 먼저 죽는다.
일시정지는 커서를 멈추는 것으로 구현되고, 재개하면 그사이 누락 건수(`dropped`)가 표시된다.

## 10. 반응형 · 접근성

| | |
|---|---|
| U1~U4 | 모바일 우선. 실사용 대부분이 모바일 |
| **U2 캘린더** | 모바일에서 셀이 좁다 — **이모지만** 표시하고 탭 시 하단 시트 |
| A1~A6 | **데스크탑 전용.** 대시보드를 모바일로 짜지 마라 |
| 다크모드 | **전 화면 지원** (프론트 구현 상태) |

- 상태를 **색으로만** 구분하지 마라. 뱃지·아이콘·텍스트를 함께 (매진/이미받음/등급미달이 색만 다르면 구분 불가)
- 키보드 포커스 상태를 명시적으로
- `prefers-reduced-motion` 존중 — 반짝임 애니메이션에 특히
- 넓은 표·차트는 각자 `overflow-x: auto` 안에서 스크롤. **페이지 본문이 가로로 밀리면 안 된다**
- 캘린더는 **날짜 셀에 `aria-label`** 로 "8월 3일 화요일, 모카빈 브랜드데이 14시 오픈"

## 11. 하지 말 것

- 보라-파랑 그라데이션 히어로
- 이모지를 **섹션 마커**로 사용 (브랜드 이모지는 데이터라 괜찮다)
- 모든 요소 가운데 정렬
- 상시 반짝임 (발급 성공 순간에만)
- 대시보드에 브랜드 색 남발 (데이터 가독성 우선)
- **화면에 회원 이름·연락처·이메일 표시** — 마스킹된 `member_id` 와 쿠폰 코드 앞자리만
- **응답 코드 임의 변경** — 측정과 장애 판정의 근거다
