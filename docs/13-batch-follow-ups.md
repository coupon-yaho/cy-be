# 배치 — 남은 일

여기저기 주석과 문서에 흩어져 있던 "다음에 할 것"을 한곳에 모은다. **각 항목은 언제 하는지가
조건으로 적혀 있다** — "나중에" 가 아니라 무엇이 열려야 의미가 생기는지다.

각 항목의 형식은 같다: **무엇이 안 잡히나 · 지금 왜 못 잡나 · 무엇이 필요한가 · 언제.**

---

## 1. 알림 — "죽었나" 는 보는데 "맞게 했나" 는 안 본다

지금 규칙 셋은 전부 **잡의 생사**만 본다.

| 규칙 | 보는 것 |
|---|---|
| `BatchJobFailed` | 잡이 `FAILED` 로 끝났나 |
| `BatchJobNotRunning` | 15분 동안 한 번도 안 돌았나 |
| `BatchJobRunningTooLong` | 300초를 넘겼나 |

**셋 다 통과하면서 아무것도 안 하는 상태가 있다.** 잡은 `COMPLETED` 로 끝나고 5분마다
꼬박꼬박 돌지만 기한 지난 발급건이 계속 쌓인다. 그게 이 잡의 가장 나쁜 실패 모드다 —
재고를 되돌리는 유일한 배치가 조용히 일을 안 한다.

### 1a. 만료 누락 — 가장 큰 구멍

**무엇이 안 잡히나.** 성공적으로 끝난 실행 뒤에도
`status='ISSUED' AND expires_at < now` 인 행이 남아 있는 상태. 원인은 여럿이다.

- 오염 회차 하나가 매 주기 같은 자리에서 막는다(`STOCK_UNDERFLOW`) — 그 뒤 id 가 영구히 밀린다
- `asOf` 가 크론 슬롯과 다른 좌표계로 계산돼 몇 시간 과거를 가리킨다
- `chunk-size` 가 0 이라 `LIMIT 0` 이 오류 없이 0건을 돌려준다(지금은 기동 때 막지만, 같은 모양의 실수는 또 난다)

**지금 왜 못 잡나.** 만료 누락은 **검증 finding 이 아니다** — 설계에서 관측 지표로 뺐다
(`docs/11`). 그런데 그 관측 지표가 없다. 즉 **양쪽 다 안 본다.**

**무엇이 필요한가.** 만료 잡이 끝날 때 남은 대상 수를 게이지로 낸다.

```
cy_expire_pending_total     기한이 지났는데 아직 ISSUED 인 발급건 수
```

> **스크레이프 때 세면 안 된다.** 300만 행에 `COUNT(*)` 를 15초마다 때리는 꼴이다.
> 잡이 끝나는 시점에 한 번 세서 게이지에 넣는다 — 그 시점에 이미 같은 창을 훑고 있다.

```yaml
- alert: ExpireLeavesWorkBehind
  expr: cy_expire_pending_total > 0
  for: 15m          # 세 주기. 한 주기 밀리는 것은 정상이다
  severity: critical
```

### 1b. 처리량 — "돌기는 도는데 안 줄어든다"

**무엇이 안 잡히나.** 잡이 매번 0건을 넘기면서 `COMPLETED` 로 끝나는 것. 1a 와 겹치지만
이쪽이 **원인에 가깝다** — 남은 대상이 있는데 이번 실행이 0건이면 진도가 막힌 것이다.

**지금 왜 못 잡나.** `writeCount` 가 메트릭에 없다. Micrometer 가 자동 등록하는 것은
`spring_batch_job_seconds_count`(횟수)와 `..._active_seconds_max`(진행 중)뿐이다.
`BATCH_STEP_EXECUTION.WRITE_COUNT` 에는 남지만 **알림이 SQL 을 못 읽는다.**

**무엇이 필요한가.**

```
cy_expire_processed_total   카운터. 청크마다 넘긴 건수를 더한다
```

```yaml
- alert: ExpireProcessesNothingWhileBacklogGrows
  expr: increase(cy_expire_processed_total[30m]) == 0 and cy_expire_pending_total > 0
  for: 5m
  severity: critical
```

두 조건을 **AND 로 묶는 것이 핵심**이다. 처리량 0 자체는 정상이다 — 만료할 게 없는 날이
대부분이다. 남은 대상이 있는데 0 인 것이 사건이다.

### 1c. 실패 원인을 알림이 못 가른다

**무엇이 안 잡히나.** 잡이 스스로 멈추는 자리가 넷인데(`EXPIRATION-001~004`) 알림은
그 넷을 **한 덩어리**로 본다. 그런데 대응이 서로 다르다.

| 코드 | 대응 |
|---|---|
| `EXPIRE_HISTORY_COUNT_MISMATCH` · `STOCK_UNDERFLOW` | 데이터가 이미 어긋났다. 사람이 본다 |
| `EXPIRE_ASOF_IN_FUTURE` | 넘긴 파라미터가 틀렸다. 손 트리거에서만 열린다 |
| `STOCK_ROW_MISSING` | **다음 주기가 지나갈 수 있다.** 누가 재고 행을 만드는 중이면 자연 해소 |

**지금 왜 못 잡나.** `spring_batch_job_seconds_count` 에 **에러코드 라벨이 없다.**
`BatchJobFailed` 의 description 이 "다시 돌린다고 낫지 않는다" 로 단정하는데,
`STOCK_ROW_MISSING` 은 그것이 거짓이다 — 새벽에 헛호출이 나간다.

**무엇이 필요한가.**

```
cy_expire_failures_total{code="EXPIRATION-002"}   카운터. 가드가 던질 때 코드로 라벨링
```

`STOCK_ROW_MISSING` 만 `for: 10m`(두 주기)로 따로 가르면 자연 해소되는 것이 안 울린다.

### 1d. 오염 회차가 막고 있는 것

**무엇이 안 잡히나.** 재고가 어긋난 회차 하나가 그 뒤 id 전부의 만료를 막는 상태.
`BatchJobFailed` 가 울리기는 하지만 **어느 회차인지가 안 나온다** — 운영자가 찾는 쿼리를
직접 짜야 한다.

**무엇이 필요한가.** `STOCK_UNDERFLOW` 메시지에 `coupon_id` 를 싣고,
게이지 `cy_expire_blocked_coupons` 로 개수를 낸다.

### 1e. Prometheus 가 규칙을 아직 안 읽는다 — **위 전부의 선행 조건**

`infra/prometheus/rules/batch-alerts.yml` 은 있는데 **그것을 읽는 프로세스가 없다.**
`prometheus.yml` 이 그 사실을 스스로 적어 뒀다. 지금은 규칙이 저장소에 있을 뿐이다.

**언제** — compose 티켓. 그 전까지 위 알림을 아무리 잘 써도 아무도 안 본다.

## 2. 만료 배치 — 실측으로 대가를 남긴 것들

전부 `docs/12` 에 수치가 있다. 여기는 **언제 손대는지**만 적는다.

| 무엇 | 언제 | 왜 그때인가 |
|---|---|---|
| `EXPIRE_BATCH` 의 `ORDER BY`·`LIMIT` → 상한 방식 | **취소·사용 API 티켓** | 후보 ≫ `LIMIT` 이면 후보 전부를 X 락한다(5,000건 실측). 막히는 것은 취소·사용뿐인데 그 경로가 아직 없다. 붙는 순간 1205 가 실제로 난다 |
| 표식 → `run_id` 컬럼 | **배치 다중화 직전(차단 조건)** | 인스턴스가 하나면 닿을 수 없다. 두 대가 되면 `LAST_EXPIRED_ID` 의 상한이 남의 행에 밀려 뒤 다섯 문장의 창이 넓어진다 |
| 청크 실행 시간 실측 | **300만 건 적재 직후** | 락 보유 시간이 `innodb_lock_wait_timeout`(50초)을 넘는지가 "막힌다" 와 "1205 로 실패한다" 를 가른다. 지금은 상한(120초)만 안다 |
| 인덱스 둘의 쓰기 비용 | **세 번째 인덱스 얘기가 나올 때** | 지금 둘은 가용성과 5분 주기로 정당화됐고 쓰기 축은 본 적이 없다 |

## 3. 운영

| 무엇 | 언제 | 메모 |
|---|---|---|
| `BATCH_*` 정리 | **`cleanupJob` 티켓** | 배선 뒤로 실제로 쌓인다 — 하루 288 인스턴스. 3주 시연(약 3.6만 행)에서는 무시할 수 있다. `batch.metadata.keep-days` 자리를 설정에 예고해 뒀다 |
| 업무 포트 노출 | **compose 티켓** | compose 가 `BATCH_HOST_PORT` 로 호스트에 내보낸다. 커스텀 actuator 로 관리 포트에 올리거나 매핑을 없애거나 |

## 4. 검증 — 미결정

**통계 집계도 발급을 막을 수 있다.** `StatsJdbcAdapter` 의 두 문장이 만료와 같은 모양이고,
5,000행에서 락 5,023 · 발급 INSERT 1205 가 실측됐다(`docs/12` §9).

**처방은 만료와 같을 수 없다.** 통계는 `dataset_fingerprint` 와 함께 판정 근거가 되므로
격리를 내리면 집계 중에 원본이 바뀔 수 있다.

**결정할 것** — 검증 중에는 발급도 멈추는 운영 규율로 갈지, 통계 Step 도 격리를 내릴지.
발급 경로가 아직 저장소에 없어 지금은 *"막힐 수 있다"* 까지만 확인됐다.

지금 막아 주는 것은 `rejectRunningSchedulers` 인데 **배치 JVM 의 플래그만 본다** —
발급 API 프로세스는 그것으로 안 멈춘다.
