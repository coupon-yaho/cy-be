# 우리가 만들 것

> 입력: `PRD-v4.15.md`
> 이 문서는 PRD를 검수한 결과가 아니라, **PRD를 읽고 우리가 실제로 뭘 어떻게 지을 건지**를 정리한 것.

---

## PRD를 어떻게 읽을 것인가

PRD v4.15는 **잘 만든 방향 문서**다. 계약서가 아니다.

"미결 사항 0건"이라고 적혀 있지만 실제로 코드를 짜기 시작하면 정해야 할 게 계속 나온다. 그건 PRD가 부실해서가 아니라 원래 그런 거다. 설계 문서가 구현의 모든 분기를 미리 알 수는 없다.

그래서 이 문서의 전제는 이렇다.

- PRD가 **정한 것**은 그대로 간다. 특히 이름·불변식·측정 기준은 바꾸면 안 된다
- PRD가 **안 정한 것**은 부딪히는 시점에 우리가 정한다. 미리 다 정하려고 시간 쓰지 않는다
- PRD와 **현실이 어긋나면** 현실을 따르고 문서를 고친다. 문서에 코드를 맞추지 않는다

---

## 한 문장

> **재고 10,000장에 20,000명이 몰려도 정확히 10,000장만 나가고, 그게 사실이라는 걸 300만 건 이력으로 스스로 증명하는 시스템.**

나머지는 전부 이걸 뒷받침하는 장치다. 브랜드 데이도, 등급도, 대시보드도, 대기열도. 판단이 애매할 때는 이 문장에 가까운 쪽을 고른다.

## 흔들리지 않는 축 6개

일정이 밀리면 여기부터 흔들리기 쉬운데, 흔들리면 프로젝트가 다른 프로젝트가 된다.

### 1. `active_count` — 재고는 누적이 아니다

```
coupon_stocks(campaign_id PK, total_quantity, active_count)
잔여 = total_quantity − active_count
active_count = 현재 ISSUED + USED 개수   (취소·만료 시 감소)
```

`issued_count`라고 쓰는 순간 누적 발급 수로 읽히고, 초과 발급 판정이 통째로 어긋난다. **더미데이터에 CANCELLED가 10%(30만 장) 있어서 누적으로 재면 정상 데이터가 대량 오탐된다.** 이름 하나가 검증 체계 전체를 좌우한다.

### 2. `UNIQUE(campaign_id, member_id)` — 최종 방어선

v1/v2/v3 어디에 버그가 있어도 1인 1매는 DB가 물리적으로 막는다. 나중에 이 제약이 불편해지는 순간이 오는데(→ 함정 1), **그때도 제약을 지우지 않는다.**

### 3. 상태 머신은 한 곳에만 존재한다

런타임 발급/사용/취소와 검증 배치의 이력 리플레이가 **같은 `CouponStateMachine` 클래스를 쓴다.** 두 벌로 갈라지는 순간 검증이 검증이 아니게 된다 — 같은 버그를 양쪽이 똑같이 재현하니까.

### 4. 측정은 클라이언트가 성공 응답을 받은 시점 기준

v3를 Redis 선점 시점으로 재면 부당하게 빨라 보인다. 세 버전을 같은 자로 재는 게 비교의 전부다.

### 5. 오염 데이터셋 — 검증을 검증한다

"검증 결과 0건"만으로는 검증이 잘된 건지 아무것도 안 보는 건지 모른다. **이게 이 프로젝트에서 제일 잘 잡힌 아이디어다.** 일정이 밀려도 이건 살린다.

### 6. 측정 환경 L1/L2/L3 분리

노트북 수치가 비교표에 섞이면 v1/v2/v3 비교 전체가 무의미해진다. L1은 정합성 전용, 비교표는 L2에서만.

## 만드는 순서

PRD의 D1~D15와 어긋나지 않되, **의존 관계 기준**으로 다시 본 빌드 경로.

```
[기반]  스키마 + 상태머신 + 더미데이터 생성기
   │     ↑ 여기서 정한 이름과 제약이 끝까지 간다. 제일 신중하게
   ▼
[정확성]  v1 (DB 비관적 락) + 멱등성 + UNIQUE 제약
   │     ↑ 초과 발급 0건을 여기서 처음 증명한다
   ▼
[증명]  검증 배치 + 오염셋
   │     ↑ ★ 이게 v2보다 먼저다. PRD는 같은 주(D6~D10)에 두지만 순서가 중요
   ▼
[비교]  v2 (Redis) → v3 (Kafka)
   │     ↑ 검증 배치가 있어야 Redis 도입으로 생긴 불일치를 발견할 수 있다
   ▼
[보여주기]  대시보드 + k6 + Chaos + 영상
```

**검증 배치를 v2보다 먼저 세우는 이유**: v2는 Redis와 DB라는 두 저장소를 쓰기 시작하는 시점이다. 여기서 드리프트가 처음 생긴다. 검증 수단 없이 v2로 넘어가면 불일치가 생겨도 모른 채로 v3까지 간다.

PRD 일정상 ②(v2)와 ④(검증)가 병렬이라 순서를 강제할 수는 없지만, **④가 ②보다 먼저 끝나도록** 조율한다.

## 부딪힐 걸 알고 가는 함정 8개

미리 다 해결하지 않는다. **부딪히는 시점을 알고 있으면 그때 30분이면 정리된다.** 모르고 부딪히면 하루가 날아간다.

### 함정 1. 오염셋을 넣으려는 순간 DB가 막는다 — 기반 단계

오염 유형 5(동일 쿠폰 두 유저)와 6(동일 유저 2건)은 `code UNIQUE`와 `uk_campaign_member`에 정확히 걸린다. INSERT가 거부된다.

**우리 결정**: 오염 전용 스키마를 제약 없이 따로 만든다. `verification_runs.dataset = CLEAN/CORRUPT`가 이미 있으니 개념은 준비돼 있다. 검증 배치가 **대상 스키마를 파라미터로 받게** 설계한다.

```
verify(asOf, dataset)     ← PRD의 POST /admin/verify?asOf= 에 dataset 추가
```

기반 단계에서 스키마를 두 벌로 잡아두면 나중에 고칠 일이 없다. **나중에 발견하면 검증 배치를 다시 짜야 한다.**

### 함정 2. `asOf`에 과거를 넣으면 검증이 터진다 — 증명 단계

이력은 `created_at <= asOf`로 자를 수 있는데 `coupons.status`는 현재 상태다. `updated_at`도 `version`도 없다(낙관적 락이 범위 밖이라 의도적으로 뺐다). 과거 시각을 넣으면 이력만 잘려서 정상 데이터가 전부 불일치로 나온다.

**우리 결정**: `asOf`는 **"실행 순간을 고정해서 재실행 결정성을 만드는 값"**이다. 과거 조회 기능이 아니다.

```
asOf >= max(coupon_histories.created_at)
실행 시:   서버가 시작 시각을 찍어 고정
재실행 시: 직전 run의 asOf를 그대로 재사용 → 같은 결과 나오는지 확인
```

그리고 결정론 판정은 **`(finding_type, coupon_id)` 쌍의 정렬 리스트 일치**로 본다. PRD의 "finding_type 집합 동일"은 어떤 쿠폰이 걸렸는지를 안 보므로 약하다.

### 함정 3. 만료된 `USED`를 사용취소하면? — 정확성 단계

더미데이터에 EXPIRED 15%(45만 장)와 "USED 중 20% 복원"이 동시에 있어서 **반드시 발생한다.**

**우리 결정**: 전이표는 **5행으로 고정**하고, 만료된 `USED`도 예외 없이 `ISSUED`로 되돌린다.

```
(없음) ──ISSUE──→ ISSUED
ISSUED ──USE──→ USED
USED   ──CANCEL_USE──→ ISSUED     만료 여부와 무관
ISSUED ──CANCEL──→ CANCELLED      종단
ISSUED ──EXPIRE──→ EXPIRED        종단
```

**전이표는 시각을 인자로 받지 않는다.** `expires_at`을 보고 결과가 갈리면 같은 이력을 다시 접을 때마다 판정이 달라져 재실행 결정론이 무너진다. 리플레이는 `asOf` 이하 이력만 보고 상태를 재구성하는데, 전이 자체가 시각에 의존하면 그 재구성이 불가능하다.

`ISSUED`로 돌아온 만료 쿠폰은 **다음 `expireJob`이 `EXPIRED`로 옮긴다.** 그 사이의 간극은 결함이 아니라 배치 주기의 함수라, `finding`이 아니라 별도 관측 지표로 둔다(`11-batch-implementation.md` 9절 "검증하지 않는 것").

`USED ──EXPIRE──→ EXPIRED`는 전이표에 없다. 이미 쓴 쿠폰은 만료되지 않는다.

### 함정 4. 20초 뒤 대기열이 얼어붙는다 — 보여주기 단계

재고 10,000 / 입장 500명당초 → **20초면 소진.** 그 시점에 대기열엔 최대 10,000명이 남아 있다. 캠페인이 `CLOSED`가 됐을 때 `GET /queue`가 뭘 반환하는지가 PRD에 없다.

**우리 결정**: `CLOSED` 전이 시 대기열을 일괄 해제한다.

```
GET /queue → 200 { status: "CLOSED", reason: "STOCK_EXHAUSTED" }
대기열 키 삭제 + 잔여 entryToken 무효화
```

시연 영상에서 바로 드러나는 부분이라 늦게 발견하면 재촬영이다.

### 함정 5. 멱등 동시 요청의 "완료 대기" — 정확성 단계

PRD는 *"나머지는 완료 대기 후 저장된 응답 반환"*이라고만 적혀 있다. 이게 멱등성 구현에서 제일 까다로운 부분이고, 테스트 시나리오 4가 정확히 이걸 요구한다.

**우리 결정**: 표준 2단계 커밋 패턴. `idempotency_records`에 **`status` 컬럼을 추가한다**(현재 스키마엔 없다).

```
1. INSERT (idem_key, request_hash, status=IN_PROGRESS)
2. 중복키 예외 → 기존 행 조회
     DONE         → 저장된 response_body 를 200 으로
     IN_PROGRESS  → 50ms 간격 최대 3초 재조회
     타임아웃     → 409 CONFLICT_IN_PROGRESS   ← 응답 코드 표에 추가
     해시 불일치  → 422 IDEMPOTENCY_KEY_REUSED
3. 본 처리 → UPDATE status=DONE, response_body
```

### 함정 6. Redis를 죽이면 v1도 죽는다 — 보여주기 단계

PRD가 "Redis 다운 시 v1은 정상 동작"이라고 세 곳에서 말하는데, `/issue`가 Entry-Token을 요구하고 그 토큰은 Redis에 있다. 대기열 OFF여도 마찬가지다 — 토글되는 건 대기열 로직이지 토큰이 아니다.

**우리 결정**: 코드를 고치지 않고 **서사를 사실에 맞춘다.**

정합성(초과 발급 0)은 **진짜로 무손상**이다. Redis가 죽으면 발급이 안 될 뿐 잘못된 발급이 나가지는 않는다. Chaos 통과 기준의 "무조건" 항목은 그대로 지켜진다.

> 발표 서사: ~~"Redis가 죽으면 v1만 살아남는다"~~
> → **"의존성 구조가 다르면 무너지는 지점도 다르다. v1은 재고 카운터를 Redis에 두지 않아 데이터는 무손상이지만, 입장 토큰이 Redis라 발급 자체는 함께 멈춘다."**

두 번째가 사실이면서 더 정확한 이야기다. Q&A에서 반박당하지 않는다.

### 함정 7. k6가 403을 구분 못 한다 — 보여주기 단계

403이 세 종류인데 k6 집계는 두 갈래로 갈린다.

```
403 GRADE_NOT_ELIGIBLE    → 정상 실패
403 ENTRY_TOKEN_EXPIRED   → 정상 실패
403 NO_ENTRY_TOKEN        → 에러       ← 상태 코드만으로 구분 불가
```

**우리 결정**: `NO_ENTRY_TOKEN`을 **400 Bad Request로 분리한다.** 의미상으로도 이쪽이 맞다 — 등급 미달과 토큰 만료는 "지금은 권한이 없음"(403)이지만, 토큰 미첨부는 "요청이 잘못됨"(400)이다.

이러면 k6가 20,000 VU 전 요청에서 JSON 본문을 파싱하지 않아도 된다.

### 함정 8. JWT 20,000개를 누가 언제 만드나 — 정확성 단계

전 API가 사전 발급 JWT를 요구하는데 발급 파이프라인이 PRD에 없다. `/entry`→`/issue` 흐름 테스트의 선행 조건이다.

**우리 결정**: 시드 모듈이 CSV로 뽑고 k6가 `SharedArray`로 읽는다. 런타임 서명은 시크릿이 스크립트에 노출돼서 안 쓴다.

```
seed → jwt_tokens.csv (member_id, grade, token)
k6   → SharedArray 로 로드
```

`exp`를 절대 시각으로 박으면 **오픈 시각을 상대 시각(시드+5분)으로 만든 이유가 무너진다.** 시드 재실행 시 토큰도 같이 재발급되게 한다.

## 용어를 먼저 고정한다

같은 걸 다르게 부르면 코드가 갈라진다. PRD 안에서 이미 흔들리는 세 가지.

| 대상 | 고정할 용어 | 이유 |
|---|---|---|
| 쿠폰 300만 장 / 이력 약 520만 건 | 둘을 절대 "300만"으로 뭉치지 않는다 | PRD가 `coupons 300만행`과 `이력 300만 건`을 동시에 쓴다. 검증 배치 설계·리포트 문구가 여기 걸린다. 이력 520만이면 과제 요건은 초과 달성 |
| **누적 발급률** = 누적 ISSUE / total_quantity (79%) | 통계·비즈니스 지표 전용 | `campaign_stats`, 브랜드 전환율 |
| **재고 점유율** = active_count / total_quantity (59%) | 불변식·초과 발급 판정 전용 | 패널 ⑤, 잔여 재고 stat |
| 대시보드 패널 **26종** | 14도 24도 아니다 | 실제 열거가 26 (화면① 10 + ② 9 + ③ 7). **역할 분담표의 "14차트"가 특히 위험** — ⑤ 담당자가 작업량을 절반 이하로 오해한다 |

## 잘라야 할 때 자르는 순서

일정은 밀린다. 밀렸을 때 즉흥적으로 자르면 핵심이 날아간다.

```
1순위 포기 · 통계 패널 24~26        전부 버려도 과제 요건 무영향
2순위 포기 · 버전 비교 패널 20~23   정적 캡처로 대체 가능
3순위 포기 · ADAPTIVE 대기열 모드    OFF/ALWAYS 2모드로 서사 유지. 비교표는 원래 OFF 3행
4순위 포기 · Chaos 추가 시나리오     DB 커넥션 끊기 1종만 남김
─────────── 여기부터는 과제 요건 훼손 ───────────
5순위 · v3 Kafka                     설계·PoC 발표로 전환 (PRD의 D8 판단 지점)
절대 사수 · v1 · v2 · 검증 배치 · 오염셋 · 더미데이터 · k6 S1
```

**대기열 ADAPTIVE를 v3보다 먼저 자른다.** PRD는 v3에만 판단 지점을 붙였는데, 실제로 ③ 영역 공수가 부족해지면 둘 중 하나를 골라야 한다. 근거는 명확하다 — **대기열은 비교표에도 영상에도 안 쓰인다.** 비교표 3행이 전부 OFF고 촬영 조건도 OFF다. 산출물이 발표 슬라이드 2분뿐이다.

설계 자체는 훌륭하고(순번 역전 방어 2지점, 인바운드/아웃바운드 계층 분리) 발표에서 제일 돋보일 부분이라 버리자는 게 아니다. **순서를 미리 정해두자는 것.**

## 부하가 몰리는 곳

PRD의 5영역 분담에서, 실제 공수가 한쪽으로 쏠린다.

**③ 인프라·비동기**가 가장 무겁다.

```
v3 Kafka 비동기
적응형 대기열 3모드 + IDLE/QUEUEING/DRAINING 상태 전이
Resilience4j CB 3개 + 버전별 게이트 분기
/entry + Entry-Token + GETDEL 원자성
순번 역전 방어 2지점
```

여기에 동시성 테스트 13개 중 **8개(6~13번)가 전부 ③ 영역**이고, 함정 6(v1의 Redis 의존)도 ③에 떨어진다.

PRD는 ⑤(시각화·측정)에 대해서만 리스크(R9) + 부하 재균형표 + 가정 A2로 3중 관리를 걸어뒀는데, ③은 R1(v3 미완) 하나뿐이다. **③에도 같은 수준의 조기 신호를 붙인다.**

```
조기 신호: D8에 대기열 3모드 중 ADAPTIVE 미착수
대응:      위 "자르는 순서" 3순위 발동
```

## 착수 전에 정할 것

D1에 앉아서 30분이면 끝나는 것들. 안 정하고 시작하면 나중에 되돌리는 비용이 크다.

| # | 정할 것 | 안 정하면 생기는 일 |
|---|---|---|
| 1 | 오염셋 스키마 분리 + `verify(asOf, dataset)` 시그니처 | 검증 배치를 다시 짬 |
| 2 | `asOf` 의미 = 실행 순간 고정 (과거 조회 아님) | 정상 데이터가 전부 불일치로 나옴 |
| 3 | `CouponStateMachine`을 런타임·배치 공용 모듈로 | 검증이 검증이 아니게 됨 |
| 4 | ~~만료된 `USED`의 `CANCEL_USE` 전이 2행~~ → **전이표 5행 고정. 시각을 인자로 받지 않는다** | 재실행마다 판정이 달라짐 |
| 5 | `idempotency_records.status` 컬럼 + 409 `CONFLICT_IN_PROGRESS` | 테스트 시나리오 4를 못 통과 |
| 6 | `NO_ENTRY_TOKEN` → 400 | k6가 매 요청 JSON 파싱 |
| 7 | JWT 시드 → CSV → k6 파이프라인 | `/entry`→`/issue` 테스트 자체가 막힘 |
| 8 | 용어 3종 고정 (쿠폰/이력, 발급률/점유율, 패널 26) | 코드가 갈라짐 |
| 9 | L2 기준 머신 물리 스펙 + k6 분리 여부 | 비교표 수치를 못 믿게 됨 |
| 10 | 캠페인 `CLOSED` 시 대기열 해제 규칙 | 영상 재촬영 |

**1·2·3번이 제일 중요하다.** 나머지는 나중에 발견해도 반나절이면 고치는데, 이 셋은 검증 체계 전체를 다시 만들어야 한다.
