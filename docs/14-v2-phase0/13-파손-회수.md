# 13 · 파손 값 회수

파손은 선점 `-8` · 완료·보상 `-3` 으로 **읽히기만 하고 아무도 지우지 않는다.**
선점 시점에 `stock` 은 이미 깎였으므로 그 자리는 영구히 잠기고 재고가 한 장 증발한다 —
만료로도 배치 복원으로도 안 풀린다. 되돌릴 경로가 하나는 있어야 한다.

> 값 형식은 `01`, 완료·보상은 `03`, 인자 규약은 `12` 에 있다.

```lua
-- KEYS[1]=stock KEYS[2]=issued KEYS[3]=issued_ever
-- ARGV[1]=memberId ARGV[2]=복원여부 '1'(DB 에 발급 없음) | '0'(있음) ARGV[3]=총재고
if #ARGV < 3 then return -10 end
if #ARGV[1] == 0 or (ARGV[2] ~= '0' and ARGV[2] ~= '1') then return -10 end
if not isCanonicalInt(ARGV[3], false) then return -10 end   -- 판정은 12
local stored = redis.call('HGET', KEYS[2], ARGV[1])
if stored == false then return 0 end                       -- 이미 없다
local st, ms, tk, key = string.match(stored, '^([PD])|(%d+)|([^|]+)|(.+)$')
if st ~= nil and #ms <= 13 then return -1 end               -- 멀쩡하다. 건드리지 않는다
if ARGV[2] == '0' then                                     -- 자리만 푼다
    redis.call('HDEL', KEYS[2], ARGV[1])
    return 2
end
if not readableCounters(KEYS[1], KEYS[3]) then return -11 end
local left = tonumber(redis.call('GET', KEYS[1]))
if left + 1 > tonumber(ARGV[3]) then return -2 end         -- 짝 없는 INCR 은 초과 발급이다
redis.call('HDEL', KEYS[2], ARGV[1])
redis.call('INCR', KEYS[1])
redis.call('DECR', KEYS[3])
return 1
```

| 반환 | 뜻 |
|---|---|
| `1` | 지우고 `stock`·`issued_ever` 까지 되돌렸다 |
| `2` | **field 만 지웠다** — DB 에 발급이 있어 재고는 그대로 둔다 |
| `0` | field 가 없다 |
| `-1` | 파손이 아니다 — 살아 있는 선점 |
| `-2` | **상한 초과** — 되돌리면 총재고를 넘는다 |
| `-11` | 재고를 못 읽는다 |
| `-11` | 카운터를 못 읽는다(12) |
| `-10` | 인자 개수 · 빈 `memberId` · 복원 여부 플래그 · 총재고 인자(12) |

### 되돌리는 범위를 스크립트가 혼자 못 정한다

**파손된 값에는 원래 상태가 안 남아 있다.** `P` 였는지 `D` 였는지 모르는데 무조건
`stock` 을 되살리면, `D` 였던 경우 **DB 에는 발급이 있고 재고는 한 장 늘어난다** —
그 자리를 다른 회원이 가져가는 순간 초과 발급이다.

그래서 **호출부가 DB 를 조회해 답을 넘긴다.** 회수는 재구성·재동기화에서만 부르고
그때는 게이트가 닫혀 있으므로, 05 가 금지한 "조회와 커밋 사이의 창" 이 생기지 않는다.
**발급이 도는 중에는 이 스크립트를 부르지 않는다** — 그 전제가 깨지면 DB 조회 결과가
곧바로 낡은 값이 된다.

### 보상에는 상한이 없고 회수에는 있다

**보상은 짝이 증명된다.** `tk == ARGV[2]` 이고 `st == 'P'` 인 값만 되돌리는데, 그 값은
선점이 쓴 것이고 선점은 재고를 깎았을 때만 field 를 남긴다(못 깎으면 `-5`·`-11` 에서
되돌린다). 그래서 `INCR` 한 번은 반드시 앞선 `DECR` 한 번과 짝이다.

**회수는 다르다.** 선점은 인자 가드(`-10`) 때문에 **파손 값을 만들 수 없다.** 그러면
회수 대상의 출처는 재구성 재작성·수동 조작·구버전이고, 거기에는 "재고를 깎았다" 는
증거가 없다. 짝 없는 `INCR` 은 그대로 초과 발급이라 **상한을 본다.**

총재고를 `meta` 가 아니라 **인자로 받는다** — 회수는 재구성 절차 안에서만 도는데
그때 `meta` 는 1번 단계에서 이미 지워져 있다. 호출부는 DB 에서 총재고를 안다.

06 의 "단건 복원도 같은 상한을 지나야 한다" 는 **취소·사용취소**를 말한다. 그건 DB 에
발급이 남은 채 재고만 돌려주는 것이라 역시 짝이 없다.

**파손 판정은 다섯 스크립트가 같은 패턴 하나로만 한다.** 여기만 기준이 느슨하면
살아 있는 선점을 지우게 되고, 그것은 초과 발급 방향이다.

**자동으로 돌리지 않는다.** 05 의 자동 회수를 금지한 이유가 그대로 적용된다 —
파손이 아니라 정상 `P` 를 잘못 지우면 같은 사고다. 호출 지점은 아래 표에 있다.

## 호출 지점은 하나뿐이다

| 상황 | 회수 |
|---|---|
| 발급 경로가 `-8`/`-3` 을 받음 | **부르지 않는다.** `valueCorrupt` 를 올리고 경보(04) |
| 재구성 · 재동기화(07) | **여기서만.** 게이트가 닫혀 있어 원 요청과 경쟁하지 않는다 |

발급이 도는 중의 회수는 05 가 금지한 자동 회수와 같은 사고다.
DB 조회 결과(`ARGV[2]`)가 그 조회 시점에만 유효하기 때문이다.
