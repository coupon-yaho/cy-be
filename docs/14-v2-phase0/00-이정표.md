# Phase 0 · 이정표

v2 발급의 **정합성 결함을 코드로 막는** 작업이다. 성능은 건드리지 않는다.
설계 원문은 `docs/12-v2-redis-design.md` 하나다.
전체 Phase 순서는 이 저장소 밖 `~/Downloads/v2-작업순서.md` 에 있다.

## 왜 이게 먼저인가

초과 발급이 가능한 구성에서 잰 처리량은 **성능 데이터가 아니다.**
Phase 1 이후의 모든 측정이 이 작업의 완료를 전제한다.

## 읽는 순서

```
00 이정표
 └ 01 값 형식          ← 나머지 전부가 이 규격에 기댄다. 먼저 확정한다
     ├ 12 인자 가드     ← 5종이 공유하는 입력 규약. 스크립트보다 먼저 읽는다
     ├ 02 선점  ─┐
     ├ 03 완료·보상 ┤ Lua 5종. 같은 codec 과 같은 인자 규약을 공유한다
     ├ 13 파손 회수 ┤
     ├ 06 배치 복원 ─┘
     ├ 04 응답·지표    ← 02·03 의 반환 코드를 소비한다
     ├ 11 관제 반영    ← 04 의 이유 코드와 정합성 원천값이 v2 를 읽어야 한다
     ├ 05 PENDING 계측
     └ 07 재구성 락    ← 다중 인스턴스 전용. 나머지와 독립
08 테스트 → 09 완료 기준

실제 착수는 `10-작업분할.md` 부터. 어느 단위를 집을지 거기서 정한다.
```

## 손대는 범위

- Lua 스크립트 5종 신설·개정 — 선점(02) · 완료·보상(03) · 배치 복원(06) · 파손 회수(13)
- 발급 경로의 응답 매핑과 카운터
- 관측 이벤트의 엔진 버전 스탬프 · 이유 코드 · 정합성 원천값 리더(11)
- 만료 배치의 Redis 복원 호출부
- 재구성·재동기화 진입점

## 손대지 않는 범위

- **성능** — 배칭 · 캐시 · pool · 스레드 수는 Phase 1~2 다
- **서킷브레이커** — Phase 4 이후
- 조회 경로 · v1 발급 경로

## 전제

- **아키텍처는 확정됐다**(§0.1). 구조 변경 제안은 전부 반려됐고, 남은 조정은 설정값뿐이다.
  구현 중에 "이렇게 바꾸면 더 빠른데" 가 떠오르면 §0.1 의 재검토 조건부터 확인한다.
- **v2 발급 경로는 코드에 아직 없다.** 수정이 아니라 신규 구현이다(10 참조).
- api 는 **여러 대**로 뜬다. 요청토큰과 재구성 락이 여기에 기댄다.
- Redis 는 1대. Cluster 는 아직 아니지만 키 슬롯 규칙은 지킨다(`{r}`).
