# 06 · 배치 복원의 상한 원자 검사

단건 복원은 이미 상한을 본다. **만료 배치에는 그 검사가 없다.**

## 지금 무엇이 비어 있나

```
단건 복원  left >= total 이면 -2         ← v1 경로에만 있다. v2 용은 S6 이 만든다
만료 배치  INCRBY n                       ← 상한 검사 없음
```

`INCRBY` 를 그냥 쏘면 상한을 **한 번에 뛰어넘을 수 있다.**
§5.1 이 복원을 "늘리는 방향이라 안전"으로 분류한 것은 **한 장씩 상한을 지킬 때**의
이야기이고, 재고 카운터가 총재고를 넘는 순간 **초과 발급은 확정된다.**

## 배치 복원 스크립트

```lua
-- KEYS[1]=stock KEYS[2]=meta  ARGV[1]=건수
if #ARGV < 1 then return -3 end
if redis.call('EXISTS', KEYS[2]) == 0 then return -1 end       -- 게이트 미준비
local rawTotal = redis.call('HGET', KEYS[2], 'totalQuantity')  -- 형식까지 본다(12)
if not isCanonicalInt(rawTotal, false) then return -1 end
local total = tonumber(rawTotal)
local raw = redis.pcall('GET', KEYS[1])
if not isCanonicalInt(raw, true) then return -11 end           -- 재고를 못 읽는다. 인자 탓이 아니다
local left = tonumber(raw)
if not isCanonicalInt(ARGV[1], false) then return -3 end       -- 1e3 · 0x10 · " 3 " · 007 (12)
local n = tonumber(ARGV[1])
if n <= 0 then return -3 end
if left + n > total then return -2 end                         -- 상한 초과 = 이상 신호
redis.call('INCRBY', KEYS[1], n)
return 1
```

## 반환

| | 뜻 | 처리 |
|---|---|---|
| `1` | 복원함 | 정상 |
| `-1` | 게이트 미준비(재구성 중) | 건너뛴다. **건수를 카운터로 남긴다** |
| `-2` | **상한 초과** | 그 회차 만료 처리를 **멈추고 경보** |
| `-3` | 인자 이상 | 버그. 경보 |
| `-11` | **재고를 못 읽음**(비정수 포함) | 선점의 `-11` 과 같은 뜻. 운영 개입 + 경보. **`-2` 로 오진하면 원인이 뒤바뀐다** |

`-2` 가 나오면 그 시점에 이미 다른 곳이 깨져 있다는 뜻이라 **재동기화 대상**이다.

## 인자 검사가 `-3` 으로 끝나야 하는 이유

`EXISTS` 는 `meta` 가 **재구성 도중의 부분 상태**여도 1이다. `totalQuantity` 만 아직 없으면
`left + n > nil` 에서 Lua 런타임 에러가 나고, 그 회차 청크의 복원이 통째로 유실된다 —
재고 과소 방향이지만 원인이 로그에 "Redis 실패" 로만 남아 안 보인다. **`-1` 로 떨어뜨린다.**

건수도 같다. `n = 2.5` 는 `n <= 0` 을 통과하고 `INCRBY` 가 `not an integer` 로 터진다.
**`tonumber` 는 그보다 더 관대하다** — `1e3` 을 1000 으로, `0x10` 을 16 으로, `" 3 "` 을 3 으로
읽는다. 셋 다 정수라서 `math.floor` 검사도 통과한다. **1건 복원이 1000건이 된다.**
그래서 다른 네 스크립트와 같이 `^%d+$` 를 먼저 지난다.
아래 호출 규약대로 **Redis 실패는 전파하지 않으므로**, 이 예외는 장애로 오인돼 삼켜지고
복원만 사라진다. 정수가 아니면 스크립트 안에서 `-3` 으로 잡아 **버그로 드러낸다.**

## 복원은 스스로 멱등하지 않다 — S6 이 막는다

스크립트가 받는 것은 **건수 `n` 하나뿐**이라 같은 회차를 두 번 부르면 두 번 복원한다.
상한 검사가 `total` 을 넘는 이중 복원만 잡고, **넘지 않는 이중 복원은 통과한다.**
그건 과다 방향이고 초과 발급으로 이어진다.

`afterCommit` 은 커밋 뒤라 재시도를 하지 않는다(아래). 남는 위험은 **배치 회차 자체의
재실행**이다 — 프로세스가 복원 직후 죽고 같은 만료분을 다시 집는 경우.

**그래서 멱등의 책임은 DB 상태 전이에 있다.** 만료 배치는 `EXPIRED` 로 이미 전이된 건을
다시 세지 않아야 하고, **그것이 S6 의 완료 조건**이다. 상태 전이와 복원 호출이 같은
커밋 경계 뒤에 있으므로 여기서 닫힌다.

Redis 쪽 실행 로그(`SADD <실행ID>`)로 막는 방법도 있지만 채택하지 않았다 —
**키가 하나 늘고**, TTL 과 재구성 시 정리 규칙이 따라붙는다. 원천이 DB 인 사실을
Redis 에 한 번 더 적는 구조라 축이 늘어난다. **DB 에서 못 막는 것이 확인되면** 그때 연다.

## 호출 지점

| 서비스 | 방식 |
|---|---|
| `CouponCancelService` | 건별 단건 복원 |
| `CouponCancelUseService` | 건별 단건 복원 (상태 전이 규칙 재확인 필요) |
| `CouponExpirationService` | **회차별 건수를 모아 배치 복원 1회** |

`n` 은 **상태 전이가 실제로 성공한 건수**(affected rows)다. 대상 목록의 크기가 아니다 —
이미 취소된 건이 목록에 섞여 있으면 그만큼 이중 복원이 되고, `total` 을 안 넘으면
**경보도 안 뜬다.** 취소가 이미 되돌린 재고를 만료가 한 번 더 돌려주는 형태다.

세 곳 모두 **DB 커밋 이후**에 호출한다(`afterCommit`).
트랜잭션 안에서 부르면 롤백돼도 Redis 는 안 되돌아간다.

Redis 실패는 전파하지 않는다 — 취소는 이미 커밋됐고 복원 누락은 과소라 안전하다.
**실패 건수를 세고 재동기화가 회수한다.**

## S6 인계

- 반환 코드는 `IssuanceScriptCodes.Restore` 뿐이다. `-1` `-2` `-3` `-11` 을 한 덩어리
  "복원 실패" 로 뭉치지 않는다 — `-1` 은 재구성 수렴의 입력, `-2` 는 회차 중단 + 경보,
  `-3` 은 버그다. 셋의 처리가 다르다.
- **삼키는 것은 Redis 장애뿐이다.** 음수 반환은 장애가 아니라 답이므로 카운터로 남긴다.
- 단건 복원(취소·사용취소)도 같은 상한 검사를 지나야 한다. 배치만 고치면 축이 갈린다.
  **그 스크립트는 아직 없다** — 위 3번 표의 "← 있다" 는 v1 경로를 말한 것이고, v2 용은
  S6 이 만든다. `INCR stock` 한 줄로 때우면 상한 없는 복원 경로가 새로 생긴다.

## `-1` 을 세는 이유

재구성 창(게이트가 닫힌 구간) 동안 커밋된 복원분은 재구성 계산에 안 들어간다.
그만큼 재고가 적게 복구되므로, **`-1` 건수가 재구성 이후 수렴 확인의 입력**이 된다.
