# 07 · 재구성 동시 실행 차단 (다중 인스턴스)

설계 §6.2 재구성과 §9.7 재동기화는 **api 가 1대라는 전제**로 쓰였다.
지금은 여러 대이므로 **동시 실행 차단이 없으면 그 자체가 초과 발급 경로**다.

## 무엇이 깨지나

```
api-1  meta UNLINK → 집계 읽는 중
api-2                  meta UNLINK → 집계 읽는 중
api-1  issued 재작성 · stock 계산
api-2                              issued 재작성 · stock 계산   ← 겹쳐 쓴다
api-1  meta 작성 (게이트 오픈)
api-2                              stock 덮어쓰기               ← 발급이 도는 중에
```

**게이트가 열린 뒤에 다른 인스턴스가 카운터를 덮어쓴다.** 초과 발급 방향이다.
A1~A6 과 같은 급의 정합성 문제이고, **1대 전제 때문에 아무도 안 보던 자리**다.

## 두 가지 해법

### (a) batch 단독 책임으로 옮긴다 — 권장

batch 는 1대다. 재구성·재동기화를 batch 만 수행하게 하면 **락 자체가 필요 없다.**
api 는 트리거만 보내거나, 아예 운영 절차로만 돈다.

- 코드가 늘지 않는다
- "누가 재구성을 소유하는가"가 한 줄로 정해진다
- 대가 — api 기동 시 워밍업을 하려면 batch 를 거쳐야 한다

### (b) Redis 락

batch 로 못 옮기는 경로가 남으면 락을 쓴다.

```
SET cy:v2:rebuild:{r} <ownerToken> NX PX <넉넉한 TTL>
  실패 → 다른 인스턴스가 진행 중. 즉시 반환
  성공 → 아래 단계마다 소유 확인
```

**단계마다 소유를 다시 확인한다.** TTL 이 만료된 뒤에도 계속 쓰면 (a) 상황이 그대로 재현된다.

```
1. meta UNLINK        ← 소유 확인
2. DB 집계 읽기        ← 소유 확인
3. 파손 field 회수(13. DB 조회로 복원여부 결정) → issued 재작성 + issued_ever  ← 소유 확인
4. stock + active_count         ← 소유 확인
4'. meta 쓰기 직전 활성 집계 재조회 + issued 의 P 재계수 → stock 갱신
5. meta 작성          ← 소유 확인. 실패하면 게이트를 열지 않는다
6. 락 해제 — 자기 토큰일 때만 (03 의 CAS 와 같은 원리)
```

TTL 은 **최악의 재구성 시간보다 길게** 잡는다. 짧으면 진행 중인 소유자가 락을 잃는다.

## 어느 쪽이든 지켜야 하는 것

| | 이유 |
|---|---|
| `meta` 를 **가장 먼저 지우고 가장 마지막에 쓴다** | 재구성 중 아무도 낡은 카운터를 못 본다. 도중에 죽어도 게이트가 닫힌 채 남는다 |
| 3번에서 `issued_ever` 를 **절대 빠뜨리지 않는다** | 빠지면 그 순간 `LUA_GAP ≠ 0` — 재구성 자체가 정합성 사고가 된다 |
| 4′ 를 넣는다 | 재구성 창 동안 커밋된 취소가 조용히 유실된다 |
| 4′ 가 **`issued` 의 `P` 도 다시 센다** | 보상은 `meta` 를 안 보므로 창 동안에도 실행된다. 그 건은 DB 에 없어 활성 집계에 안 잡히는데, 재계산된 `stock` 은 이미 그걸 반영한 값이라 **보상의 `INCR` 이 얹히면 이중 복원**이다. 창 직전의 `P` 수를 세어 `stock` 을 보정한다 |
| 락 해제는 **자기 토큰일 때만** | 남의 락을 푸는 순간 (a) 상황이다 |

## 창이 완전히 닫히지는 않는다

4′ 로 보정해도 **보정 직후 `meta` 쓰기 직전에 도착한 보상**은 여전히 새어 나간다.
값에 재구성 epoch 를 실어 낡은 보상을 거절하는 방법이 있지만, 그건 01 의 4필드 형식을
다시 여는 일이라 **채택하지 않았다.** 창은 수 초이고 그 안에 "영속에 실패한 요청" 이
겹쳐야 하므로 빈도가 극히 낮다 — **남은 위험을 여기 적어 두는 것이 조건**이다.
`LUA_GAP` 이 그 편차를 잡고, 재동기화가 회수한다.

## S8 인계 — 게이트가 닫힌 창의 계약

| | |
|---|---|
| `meta` 를 **부분 상태로 남기지 않는다** | **다섯 필드**(`status`·`openAt`·`closeAt`·`gradeMask`·`totalQuantity`)를 한 번에 쓴다. 선점 Lua 가 다섯 개를 모두 요구하므로(02) 하나라도 빠지면 `-9` 다 — **발급만 돌고 만료 복원이 죽는 조합이 생기지 않는다** |
| 파손 회수(13)는 **여기서만** 한다 | 게이트가 닫혀 있어 원 요청과 경쟁하지 않는다. 발급 경로가 회수를 부르면 05 가 금지한 사고 그대로다 |
| 회수 전에 `issuances` 를 **조회한다** | 파손 값에는 원래 상태가 없다. DB 에 발급이 있으면 재고를 되살리지 않는다(`ARGV[2]='0'`) — 되살리면 초과 발급이다. 총재고는 `ARGV[3]` 로 넘긴다(`meta` 는 1번에서 이미 지웠다) |
| **복원 중단 표식(`restore_halt`)을 마지막에 푼다** | 배치 복원이 `-2` 를 내면 그 회차의 만료가 멈추고 표식이 선다(06). 그 표식을 푸는 것은 재구성뿐이다 — 지금은 시딩(`seedCounters`)이 함께 지운다. **게이트를 닫고 진행 중인 복원이 빠진 뒤에 시딩해야 한다** — 시딩이 표식을 푼 뒤 뒤늦은 `-2` 가 도착하면 표식이 되살아나고, **재고는 정상인데 그 회차 만료만 멈춘 채** 다음 재구성까지 남는다. 세대 번호로 코드가 닫으려면 `meta` 에 필드가 하나 늘고 Lua 5종과 12 의 표가 함께 움직이므로 위 "창이 완전히 닫히지는 않는다" 와 같은 선택을 했다 — **절차가 닫고, 남은 위험을 여기 적는다.** `V2IssuanceInterleaveConcurrencyTest` 가 그 창을 박아 두었다 |
| `-1`(복원 미준비) 건수와 `corruptFieldCount` 를 **입력으로 받는다** | 재구성 창에서 유실된 복원분과 회수 대상이 그 두 값이다(05 · 06) |

## 부수 사실

`RedisRuntimeConfigStore` 가 이미 Redis + CAS 로 런타임 설정을 공유한다.
**v1/v2 회차 토글은 인스턴스 간에 안전하다** — 여기는 손댈 필요가 없다.
