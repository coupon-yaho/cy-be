# 07 · 재구성 동시 실행 차단 (다중 인스턴스)

설계 §6.2 재구성과 §9.7 재동기화는 **api 가 1대라는 전제**로 쓰였다.
지금은 여러 대이므로 **동시 실행 차단이 없으면 그 자체가 초과 발급 경로**다.

## 무엇이 깨지나

```
api-1  meta UNLINK → 집계 읽는 중
api-2                  meta UNLINK → 집계 읽는 중
api-1  issued 재작성 · stock 계산
api-2                              issued 재작성 · stock 계산   ← 겹쳐 쓴다
api-1  meta 작성 (게이트 오픈)
api-2                              stock 덮어쓰기               ← 발급이 도는 중에
```

**게이트가 열린 뒤에 다른 인스턴스가 카운터를 덮어쓴다.** 초과 발급 방향이다.
A1~A6 과 같은 급의 정합성 문제이고, **1대 전제 때문에 아무도 안 보던 자리**다.

## 두 가지 해법

### (a) batch 단독 책임으로 옮긴다 — 권장

batch 는 1대다. 재구성·재동기화를 batch 만 수행하게 하면 **락 자체가 필요 없다.**
api 는 트리거만 보내거나, 아예 운영 절차로만 돈다.

- 코드가 늘지 않는다
- "누가 재구성을 소유하는가"가 한 줄로 정해진다
- 대가 — api 기동 시 워밍업을 하려면 batch 를 거쳐야 한다

### (b) Redis 락

batch 로 못 옮기는 경로가 남으면 락을 쓴다.

```
SET cy:v2:rebuild:{r} <ownerToken> NX PX <넉넉한 TTL>
  실패 → 다른 인스턴스가 진행 중. 즉시 반환
  성공 → 아래 단계마다 소유 확인
```

**단계마다 소유를 다시 확인한다.** TTL 이 만료된 뒤에도 계속 쓰면 (a) 상황이 그대로 재현된다.

```
1. meta UNLINK        ← 소유 확인
2. DB 집계 읽기        ← 소유 확인
3. issued 재작성 + issued_ever  ← 소유 확인. 둘은 반드시 함께
4. stock + active_count         ← 소유 확인
4'. meta 쓰기 직전 활성 집계 재조회 → stock 갱신
5. meta 작성          ← 소유 확인. 실패하면 게이트를 열지 않는다
6. 락 해제 — 자기 토큰일 때만 (03 의 CAS 와 같은 원리)
```

TTL 은 **최악의 재구성 시간보다 길게** 잡는다. 짧으면 진행 중인 소유자가 락을 잃는다.

## 어느 쪽이든 지켜야 하는 것

| | 이유 |
|---|---|
| `meta` 를 **가장 먼저 지우고 가장 마지막에 쓴다** | 재구성 중 아무도 낡은 카운터를 못 본다. 도중에 죽어도 게이트가 닫힌 채 남는다 |
| 3번에서 `issued_ever` 를 **절대 빠뜨리지 않는다** | 빠지면 그 순간 `LUA_GAP ≠ 0` — 재구성 자체가 정합성 사고가 된다 |
| 4′ 를 넣는다 | 재구성 창 동안 커밋된 취소가 조용히 유실된다 |
| 락 해제는 **자기 토큰일 때만** | 남의 락을 푸는 순간 (a) 상황이다 |

## 부수 사실

`RedisRuntimeConfigStore` 가 이미 Redis + CAS 로 런타임 설정을 공유한다.
**v1/v2 회차 토글은 인스턴스 간에 안전하다** — 여기는 손댈 필요가 없다.
