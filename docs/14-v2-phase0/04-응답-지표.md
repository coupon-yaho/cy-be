# 04 · 응답 매핑과 지표

## 반환 코드 → HTTP

| 코드 | HTTP | 본문 | 카운터 |
|---|---|---|---|
| `0` | **201** | 발급 결과 + 잔여 재고 | `issueSuccess` |
| `-1` `-2` | 4xx | 마감 / 미오픈 | `rejectClosed` `rejectNotOpened` |
| `-3` | 4xx | 등급 미달 | `rejectGrade` |
| `-4` | 4xx | **"이미 발급받으셨습니다"** | `dupPerMember` |
| `-5` | 4xx | 매진 | `soldOut` |
| `-6` | **최초와 동일한 응답** | DB 에서 저장된 JSON 복원 | `replayDone` |
| `-7` | **409** + `Retry-After` | 처리 중 | `replayPending` |
| `-8` | 500 + 경보 | 값 파손 | `valueCorrupt` |
| `-9` | 503 + `Retry-After` | 게이트 미준비 · meta 부분 상태 | `gateNotReady` |
| `-10` | 500 + 경보 | **인자 이상 — 호출부 버그** | `badArgument` |
| `-11` | 503 + 경보 | **카운터를 못 읽음 — 운영 개입** | `counterUnreadable` |

## `-4` 와 `-6` 을 절대 같은 응답으로 만들지 않는다

멱등이 존재하는 이유는 **재시도를 안전하게 만드는 것**이다.
응답을 못 받고 다시 누른 클라이언트에게 "이미 받으셨습니다"를 주면
그건 멱등이 아니라 **고장**이다.

```
-4  다른 시도가 이미 그 회원으로 받았다      → 거절이 맞다
-6  같은 멱등키의 재시도, 이미 완료           → 처음 응답을 그대로 준다
-7  같은 멱등키의 재시도, 아직 처리 중        → 409. 기다리지 않는다
```

**세 카운터를 분리한다.** 합쳐두면 `-4` 급증이 재시도에 묻혀 이상 신호를 놓친다.

## `-6` 이 DB 를 읽는 것은 정상이다

최초 응답 JSON 은 `idempotency_records` 에 있고 Redis 에 없다.
그래서 replay 경로는 `Redis 1회 + DB 1회` 다.

**"멱등을 Redis 로 옮겨 DB 조회가 사라졌다"는 최초 요청에만 해당한다.**

이 왕복을 줄이려고 응답 JSON 을 Redis 에 올리면 **Redis 가 또 하나의 원본**이 되어
정합성 축이 늘어난다 — 하지 않는다.

## `-7` 은 폴링하지 않는다

v1 은 이 자리에서 폴링하며 기다렸다(`IdempotencyExecutionService` 의 wait-timeout·poll-interval).
스파이크에서 폴링은 톰캣 워커를 그대로 갉아먹는다.
즉시 409 + `Retry-After: 1` 로 떨어뜨리고, 다시 오면 대개 `D` 라 `-6` 으로 갈린다.

## 이상 카운터 — 정상 운영에서 전부 0

| 카운터 | 언제 오르나 | 뜻 |
|---|---|---|
| `valueCorrupt` | `-8` / 완료·보상 `-3` | codec 이 깨졌다. **자리 잠김 + 재고 1장 증발** |
| `badArgument` | 선점·완료·보상·회수 `-10` | 파손 값을 쓸 뻔했다. 전적으로 호출부 버그 |
| `counterUnreadable` | 선점·보상·회수 `-11` | `stock` 또는 `issued_ever` 가 canonical 정수가 아니다. **매진과 절대 합치지 않는다** |
| `stockMissing` | 복원 `-11` | 복원은 `stock` 하나만 본다 — **이름이 곧 점검 범위다** |
| `completeCasMiss` | 완료 `-1` `-2` | **보상과 커밋이 겹쳤다** |
| `compensateOnDone` | 보상 `-1` | 완료된 건에 보상을 시도했다 |
| `dbUniqueViolation` | DB unique 위반 | Redis 중복 판정을 통과했다 |

**하나라도 0이 아니면 경보한다.** 이 값들이 0이 아니면 02·03 이 제대로 안 걸린 것이므로,
**구현 검증 지표로도 쓴다.**

## 이유 코드도 같이 갈라야 한다

위 카운터를 분리해 놓고 관측 이벤트의 `ReasonCode` 를 뭉개면 **관제에서 되돌아온다.**
현재 enum 에는 `-6` `-7` `-8` `-9` `-10` `-11` 에 대응할 값이 없다 — 11 참조.

## 지표는 인스턴스별로 나눈다

api 가 여러 대다. 합산만 보면 "한 대만 이상하다"를 볼 수 없다.
수집 방식은 Phase 1 에서 정한다.

## `-8` 에서 회수를 부르지 않는다

파손 field 는 그 자리를 영구히 잠그고 재고를 한 장 증발시킨다(13). 그래도 **응답 경로가
회수 스크립트를 부르지 않는다** — 발급이 도는 중의 회수는 05 가 금지한 자동 회수와 같은 사고다.
`valueCorrupt` 경보 → 재구성·재동기화(S8)가 게이트를 닫고 회수한다(13).

**즉 `valueCorrupt` 는 "언젠가 보면 되는 값" 이 아니다.** 0이 아닌 동안 재고가 계속 묶인다.

## S5 인계 — 파손 예외·로그

- codec 파손 예외은 `IllegalArgumentException`의 하위 타입이 아니다. 기존의
  `catch (IllegalArgumentException)` → 400 관용구에 잡히면 `-8`/`-3`의 500·경보 계약이 조용히 깨진다.
- 파손 예외·경보 로그에 `IssuedValue` 전체나 멱등키 원문을 남기지 않는다. 멱등키는
  클라이언트 입력이라 주문번호·회원 식별자가 섞일 수 있다.
- 위 두 항목은 `-8` 응답 매핑과 `valueCorrupt` 카운터 테스트에서 함께 검증한다.
- **이상 카운터는 4종이 아니라 8종이다** — `valueCorrupt` `completeCasMiss`
  `compensateOnDone` `dbUniqueViolation` 에 `badArgument` `gateNotReady`
  `counterUnreadable` `stockMissing` 이 붙는다.
  `gateNotReady` 만 성격이 다르다: 재구성 창에서는 정상이고, **그 창 밖에서 0이 아니면 이상**이다.

## S1 에서 넘어온 것 — 파손 예외의 매핑

`IssuedValueCodec.decode` 는 파손 값에 `IssuedValueCorruptException` 을 던진다.
**이 예외는 `IllegalArgumentException` 계열이 아니다** — 일부러 그렇게 뒀다.

`IllegalArgumentException` 을 "잘못된 요청 → 400" 으로 뭉뚱그리는 핸들러가 있으면,
**Redis 에 있는 파손 값이 호출자 탓으로 둔갑하고 파손 카운터가 안 올라간다.**
`IssuedValueCorruptException` 은 `-8`/`-3` 과 파손 이상 카운터로만 간다.
