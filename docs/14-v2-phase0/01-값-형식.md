# 01 · `issued` Hash 값 형식

`cy:v2:issued:{r}` 의 field 는 `memberId`, value 는 아래 **4필드 고정**이다.
Lua 3종과 응답 매핑이 전부 이 규격을 공유하므로 **여기부터 확정**한다.

## 형식

```
<상태>|<선점시각>|<요청토큰>|<멱등키>

상태     P | D          한 글자. P=선점됨, D=영속 완료
선점시각  epochMillis   숫자만. **상태와 무관하게 선점 시각이다** — 승격이 덮지 않는다
요청토큰  이 선점이 누구 것인가. '|' 금지
멱등키    클라이언트가 준 값. '|' 를 포함할 수 있다
```

완료 시각을 여기 두지 않는 이유는 **원본이 DB(`issuances`)이기 때문**이다.
Redis 에만 있는 정보는 선점 시각뿐이라 그쪽을 지킨다(03).

**멱등키를 맨 뒤에 둔 이유** — 키 안에 `|` 가 들어와도 앞 세 필드가 흔들리지 않는다.
파싱은 `'^[PD]|...'` 가 아니라 Lua 캡처 패턴 `'^([PD])|(%d+)|([^|]+)|(.*)$'`로
한 번에 나눈다(실제 Lua 문자열에서 `|`는 그대로 쓴다). 마지막 캡처가 키 전체다.
`%a`로 두면 `X`도 형식상 정상으로 읽어 Java codec과 파손 판정이 갈리므로,
**상태 문자는 파서 단계에서부터 `[PD]`로 제한**한다.

## 상태는 둘뿐이다

`RECLAIMED` 같은 값을 **추가하지 않는다.**
`HLEN` 에는 계속 잡히는데 보상은 `issued_ever` 를 내리므로 `LUA_GAP` 이 즉시 어긋난다 —
**감지 장치가 스스로 오작동을 만든다.** 흔적이 필요하면 TTL 붙은 별도 키에 남긴다.

## 요청토큰

**"이 선점이 누구 것인가"만 가리킨다.** 같은 멱등키로 두 번 들어온 요청도 토큰은 다르다.

```
<인스턴스ID>-<기동nonce>-<스레드ID>-<카운터>
```

- **전역 유일성은 필요 없다.** 같은 field 안에서만 겹치지 않으면 된다
- **인스턴스ID 는 필수다** — api 가 여러 대라 스레드ID·카운터만으로는 겹친다
- `|` 를 포함하면 안 된다. 포함 가능한 값을 쓰지 않는다
- UUID 를 써도 되지만 요청당 생성 비용이 붙는다. 위 형태로 충분하다

**S4 인계** — 설정의 인스턴스 ID 만 그대로 쓰면 프로세스 재시작 후 스레드 ID·카운터가
다시 겹칠 수 있다. 생성기는 기동당 한 번 만든 nonce 를 인스턴스 ID에 섮고, S4 조립 시
api 인스턴스당 하나의 빈으로만 등록한다. 요청마다 UUID 를 만드는 것과는 다르다.

## codec 요구사항

| | 규칙 |
|---|---|
| 인코딩 | 네 필드를 `|` 로 잇는다. 앞 세 필드에 `|` 가 없음을 **인코딩 시점에 검증** |
| 디코딩 | 위 패턴으로 한 번에 분해. 실패하면 **값 파손**으로 다루고 `-8`·`-3` 반환 |
| 키 비교 | **접두가 아니라 전체 일치.** `abc` 와 `abcdef` 는 다른 키다 |
| 완료 판정 | 첫 필드가 `D` 인지로만 본다. `'|DONE|'` 같은 문자열 탐색 금지 |

## 반드시 넣을 테스트

- 인코딩 → 디코딩 round-trip. 멱등키에 `|` 를 포함한 입력 포함
- 앞 세 필드에 `|` 를 넣으려는 시도가 인코딩에서 거부되는지
- 접두가 겹치는 두 키(`abc` / `abcdef`)가 서로 다르게 판정되는지

## 왜 고정 오프셋을 안 쓰나

파싱 비용은 현재 병목에서 무시할 수준이고, **UUID 나 timestamp 길이가 바뀌면 깨진다.**
목표는 성능이 아니라 **접두 충돌이 불가능한 명확한 codec** 이다.

## S1 에서 확정한 것 — 후속 단위가 맞춰야 한다

S1(값 codec) 구현 중 Java codec 과 위 Lua 패턴의 **판정이 갈리는 입력 3종**이 나왔다.
Java 쪽은 아래대로 확정했다. **S2 의 Lua 3종이 같은 답을 내야 한다.**

### ① 빈 멱등키는 파손이다

본문 패턴의 마지막 캡처 `(.*)` 는 빈 문자열을 통과시킨다.
그러나 멱등키가 빈 값인 `IssuedValue` 는 **존재할 수 없다**(값 객체 생성 시 거부).
`P|1|api-1|` 을 Lua 는 정상, Java 는 파손으로 읽으면 두 축이 영구히 어긋난다.

**→ Lua 패턴의 마지막 캡처는 `(.*)` 가 아니라 `(.+)` 다.** 본문 패턴을 이것으로 대체한다.

**공백만 있는 키는 빈 키가 아니다.** Java 를 `isBlank()` 로 막으면 `" "` 를 파손으로 보는데
Lua `(.+)` 는 길이 1이라 정상으로 읽는다. 판정을 맞추려고 **Java 는 `isEmpty()` 로 낮췄다.**
멱등키는 클라이언트가 준 불투명 값이고, 공백을 거부할 자리는 codec 이 아니라 입력 검증이다.

**요청토큰도 같다.** 캡처가 `([^|]+)` 라 Lua 는 `"   "` 를 정상으로 읽는다.
토큰의 codec 계약은 **"비어 있지 않다" 와 "`|` 가 없다" 둘뿐**이고, 공백뿐인 토큰을
거부할 자리는 생성기다(`RequestTokenGenerator` 가 `instanceId`·`nonce` 를 이미 막는다).

### ② 개행이 든 멱등키는 정상이다

멱등키에 금지된 문자는 `|` 하나뿐이다. 개행은 금지 목록에 없고,
Lua 의 `.` 와 `[^|]` 는 개행에 매칭된다.
Java 정규식은 기본값이 반대이므로 `Pattern.DOTALL` + `\A`/`\z` 앵커로 맞췄다
(`$` 는 마지막 줄 종결자 앞에서도 매칭된다).

**→ `order-1\ntrace-2` 같은 키는 양쪽 모두 정상 선점이다.** 파손 경보를 울리면 안 된다.

### ③ 선점시각은 13자리까지다

Lua `%d+` 는 21자리도 캡처하고 `tonumber` 가 부동소수로 받는다.
Java 는 `Long.parseLong` 이 실패해 **파손**으로 떨어진다.
이 상태가 되면 Lua 는 "아직 만료 안 된 정상 PENDING" 으로 붙들고
Java 계측·배치는 같은 field 를 파손으로 세어 `LUA_GAP` 이 0 으로 수렴하지 못한다.
만료로도 안 보이니 배치 복원으로도 안 풀린다.

**→ 선점시각 필드는 `1~13자리`다.** Lua 는 캡처 후 `#ts > 13` 이면 파손으로 반환한다.

### 요청토큰은 불투명 문자열이다

토큰은 `-` 로 조각을 잇지만 **조각 경계는 규약이 아니다.**
`instanceId` 에 `-` 가 들어가면(`api-1` 같은 흔한 형태) 경계가 흔들린다.
유일성은 "같은 field 안에서만" 이면 충분하므로 **토큰을 다시 파싱하지 않는다.**
로깅·디버깅 목적으로도 `split("-")` 를 쓰지 마라.
