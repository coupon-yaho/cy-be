# Claude Design 작업 요청 — 쿠폰 야~호 프로토타입 2차

> 이 문서는 **Claude Design 에 그대로 붙여넣는 브리프**다. 프로젝트 내부 문서를 안 읽어도 되도록 자체 완결로 썼다.
> 팀 내부 근거는 `05-design-handoff.md`(사양) · `06-prototype-refactoring.md`(결정 근거)에 있다.

---

`쿠폰야호 프로토타입.dc.html` 을 만들어줬고, 그걸 실제 백엔드에 붙이기 위해 검토했다. **구조는 대부분 맞았고, 특히 캘린더 2계층 구조는 그대로 간다.** 아래는 확정된 결정과, 그에 따라 고치거나 새로 그려야 하는 것들이다.

프로토타입의 변수명(`WEEKS` `DAY_GROUPS` `PASTEL` `ICONS` `stateSwitcher` `ENDED`)을 그대로 참조한다.

---

## 0. 프로젝트가 무엇을 증명하려는 것인가

**대규모 트래픽 선착순 쿠폰 발급 시스템**이다. 통신사 멤버십 브랜드데이를 소재로 삼았다.

핵심은 화면이 예쁜 게 아니라 **이것**이다.

```
쿠폰 10,000장에 20,000명이 같은 순간에 몰려도
  · 초과 발급 0건
  · 1인 1매 위반 0건
  · 300만 건 이력의 정합성 100%
```

그리고 그걸 **MySQL 락 → Redis Lua → Kafka** 세 버전으로 갈아끼우며 지표 차이를 눈으로 보여준다.

**그래서 화면의 목적은 "이 시스템이 안 깨진다"를 보이는 것이다.** 재고 게이지·응답코드 스트림·초과발급 카운터가 장식이 아니라 주인공이다.

## 1. 확정된 결정 5개

### ① 일정 모델 — 바꾸지 않는다

`DAY_GROUPS`(Day1/2/3)와 `WEEKS`(브랜드 위크 ①②③)가 **같은 회차의 두 뷰**라는 걸 확인했다.

```
DAY_GROUPS d1 (08월 12일 수, D-2)  ↔  WEEKS week① (wed:12, D-2)
d2 (8/19, D-9)  ↔  week②     ·     d3 (8/26, D-16) ↔ week③
```

전부 **매월 2·3·4주차 수요일**이다. 백엔드가 `nthWeek × dayOfWeek` 로 이미 표현하고 있어서 **모델 변경이 없다.** 리스트 뷰(Day 섹션)와 캘린더 뷰(주 행)를 **토글**로 오가게만 해주면 된다.

### ② 브랜드 색 — 상수 배열에서 데이터로

`PASTEL` 6색 상수 배열 + `pastel: 0~5` 인덱스 방식을 **버린다.** 브랜드는 운영자가 관리자 화면에서 추가하는 데이터고, 7번째 브랜드부터 색이 겹친다.

```
brands.color   운영자가 색상 피커에서 고르는 hex 값
```

**`PASTEL` 6색은 로고에서 뽑은 팔레트니까 시드 브랜드의 기본값으로만 남긴다.** 컴포넌트는 `brand.color` 를 받아 쓰는 형태로 바꿔달라.

### ③ 색 표기 — 테마는 oklch, 브랜드 색만 hex

프로토타입은 hex(`#2B3A55`), 실제 프론트엔드는 oklch(`oklch(0.26 0.075 264)`)를 쓴다. **같은 색이다.**

- **테마 토큰(배경·전경·강조·의미색)** → oklch. 다크모드 대응이 여기 걸려 있다
- **`brands.color`** → hex. 운영자가 피커에서 고르는 데이터라 층이 다르다

### ④ 주간 브랜드는 선착순 대상이 아니다 ★

`weekBrand`(월~금 5일 내내)와 `wedBrands`(수요일 특정 시각)의 **성격이 완전히 다르다.**

| | `weekBrand` 주간 | `wedBrands` 수요일 |
|---|---|---|
| 기간 | 월~금 5일 | **특정 시각 하루** |
| 성격 | 배경·분위기 | **선착순 경쟁** |
| 재고 | **없음** | 10,000장 |
| 대기열 | 없음 | 필수 |

**주간 브랜드는 표시 전용이다.** 재고 게이지도, 잔여 수량도, `받기` 버튼도 붙이지 마라. 5일 내내 열려 있으면 경쟁이 안 생기고, 우리가 증명할 건 "같은 순간에 20,000명"이다.

**배경이 있어야 하이라이트가 산다** — 발표에서 *"주간 브랜드는 여유롭게, 수요일 14시 이 세 개가 진짜 경쟁입니다"* 라고 말하기 위한 대비 장치다.

### ⑤ 아이콘 — 브랜드가 아니라 카테고리에 붙는다

`ICONS`(cafe/shop/ride/film) 4종을 **그대로 쓴다.** 이모지로 바꾸지 마라 — OS마다 모양이 달라서 발표 자료에서 통제가 안 되고, 캘린더 셀 크기(16px)에서 뭉개진다.

```
brands.category  ENUM(CAFE, SHOP, DELIVERY, CULTURE)  →  ICONS 4종에 1:1
```

브랜드가 6개든 60개든 아이콘을 새로 그릴 일이 없게 **카테고리 단위**로 붙인다.

## 2. 프로토타입에서 고칠 것

### 2-1. 반응형 — 사용자 화면만

지금 `min-width:1280px` 데스크탑 전용이다.

| 화면 | 반응형 |
|---|---|
| **U1 발급 · U2 캘린더 · U3 쿠폰함** | **필요.** 모바일이 실사용이다 |
| A1 관리자 · D1/D2/D3 대시보드 | **불필요.** 데스크탑 전용이 맞다 |

캘린더는 모바일에서 5칸이 안 들어간다 — **주 단위 세로 카드**로 무너뜨리고, 수요일만 강조한 형태로.

### 2-2. 다크모드 — 전 화면

프로토타입에 다크모드가 0건이다. 실제 프론트엔드는 전 화면을 지원한다. **모든 색을 토큰으로 빼고 두 테마를 다 설계해달라.**

특히 캘린더의 `tint` 3색(`#F1F7F3` `#EDF3FA` `#FBF1F3`)은 다크에서 그대로 쓰면 안 된다. 어두운 배경 위 저채도 틴트로 다시 잡아달라.

### 2-3. 쿠폰 카드 컴포넌트 — 아직 없다

프로토타입도 실제 프론트엔드도 **일반 카드**를 쓰고 있다. 쿠폰이 주인공인 서비스인데 쿠폰처럼 안 생겼다.

```
┌─────────────┬╮
│  ☕  모카빈  │ │  ← 좌측: 브랜드 색 레일
│ 아메리카노   │ │
│    무료      ├╯  ← 반원 노치 (배경색으로 파냄)
│ · · · · · · ·│   ← 점선 절취선
│ 8/12 ~ 8/18  │
│ ▓▓▓▓▓░░ 6,412│   ← 재고 게이지
└──────────────┘
```

노치는 배경색 원 두 개를 양쪽에 겹쳐서 파내는 방식으로. **재사용 컴포넌트 하나**로 만들어서 U1·U2·U3에서 다 쓴다.

### 2-4. 쿠폰 정보 3종 — 데이터에 추가됐다

프로토타입이 이미 들고 있던 `benefit` `desc` `period` `terms[]` 를 **정식 데이터 모델로 승격**했다. 카드·상세에서 확실히 보이게 배치해달라.

```
benefit_title  '아메리카노 무료'
benefit_desc   '브랜드데이 하루만, 전 매장 픽업 주문'
usable_from    사용 시작        ← 발급 마감과 다르다
usable_until   사용 종료
terms[]        ['앱 픽업 주문 시 사용 가능 (1인 1매)', '키오스크 · 배달 주문 제외']
```

**발급 마감 ≠ 사용 만료다.** 8/12에 받아서 8/18까지 쓴다. 이 둘이 화면에서 헷갈리면 안 된다.

### 2-5. `m_812934` 헤더

마스킹 형식은 맞다. 하드코딩만 걷어내고 **세션에서 받는 형태**로.

> 개인정보는 화면·로그 어디에도 원본이 노출되면 안 된다. 마스킹은 **서버가 해서 내려준다** — 프론트에서 문자열을 자르는 게 아니다.

## 3. 새로 그려야 하는 화면

프로토타입에 있는 건 6개다. `U1 발급 · U3 쿠폰함 · A1 캠페인관리 · D1 운영 · D2 관제 · D3 분석`

### 3-1. 랜딩

히어로 · 브랜드 그리드 · 등급 안내 4종 · 3단계 이용 설명 · `ENDED`(지난 혜택) 목록.

`ENDED` 는 **"이 서비스가 꾸준히 돌아왔다"를 보여주는 장치**라 랜딩 하단에 두면 좋다.

### 3-2. U2 캘린더의 월 이동 + 뷰 토글

**주 단위 행 구조는 이미 만들어놨으니 그대로 쓴다.** 관통선(`top:66%`, `opacity .55`)과 솟은 수요일 셀(`margin:-14px 0`, 흰 배경, `zIndex:2`) 그대로.

없는 것만 추가:

- `◀ 2026년 8월 ▶` **월 이동** — 과거 월도 탐색 가능. 지난 회차는 회색조
- `[🗓 달력] [≡ 목록]` **뷰 토글** — 목록 뷰가 지금의 Day 섹션
- **필터** — `내 등급만` 토글 · 카테고리 드롭다운
- **등급 미달 셀** — 자물쇠 + 필요 등급 표시

지난 주(`kind:'past'`) 구조도 그대로 — 관통선 없이 날짜마다 브랜드가 흩어지고, `영 위크`(만 13~34세) 서브섹션이 붙는다.

### 3-3. A5 브랜드데이 일정 관리

캘린더가 "운영되는 것"으로 보이려면 이 화면이 필요하다. **오픈 시각 예약이 과제 요건**이라 보여줄 화면이 있어야 한다.

- 템플릿 목록 — 브랜드 · 매월 N번째 X요일 · 시각 · 지속시간 · 회차당 재고 · 참여 등급 · 활성
- 생성/수정 다이얼로그 — `nthWeek(1~4)` `dayOfWeek` `startTime` `durationHours` `stockPerOccurrence` · 등급 체크박스 4개
- **다음 3회차 미리보기** — 저장 전에 실제 날짜가 언제인지 보여준다. 이게 핵심 UX다

### 3-4. A6 브랜드 CRUD

결정 ②·⑤가 여기로 들어온다.

- 이름 · **카테고리 셀렉트(4종)** · **색상 피커** · 활성 여부
- 색을 고르면 **쿠폰 카드 미리보기**가 즉시 그 색으로 바뀌게

### 3-5. 발급 결과 모달 3종

프로토타입은 `modal` 상태만 있고 분기가 없다. **결과마다 화면이 완전히 달라야 한다.**

| 결과 | 화면 |
|---|---|
| **성공** | 쿠폰 카드가 튀어나오는 연출 + `쿠폰함 보기` |
| **매진** | 담백하게. 다음 회차 D-day 안내 + `알림 받기` |
| **이미 발급** | 실패가 아니다. **보유 중인 그 쿠폰을 보여준다** |

> "이미 발급"을 에러처럼 보이게 만들지 마라. **멱등성이 동작한 결과**라서, 같은 요청을 여러 번 보내도 같은 쿠폰 하나가 나오는 게 정상이다.

### 3-6. 로그인 · 회원가입

**목(mock)이다.** 실제 인증을 안 만든다 — 가상 회원 정보를 가정하는 과제라서.

등급별 데모 계정(WELCOME/SILVER/GOLD/VIP)을 **원클릭 버튼**으로 두면 시연이 편하다.

## 4. 대시보드 — 구멍 2개

프로토타입이 그린 지표는 대부분 맞다. **두 개가 빠졌는데, 둘 다 이 프로젝트의 채점 축이다.**

### 4-1. 초과 발급 카운터 — 없다 ★★★

프로토타입에도, 실제 프론트엔드에도 **어디에도 없다.**

**이게 1순위 지표다.** `0` 이어야 정상이고, `0` 이 아니면 프로젝트가 실패한 거다. D2 관제 화면에서 **가장 크게, 가장 위에** 그려달라.

```
┌──────────────────────────┐
│      초과 발급            │
│                          │
│           0              │   ← 아주 크게
│                          │
│  10,000장 / 20,000 요청   │
└──────────────────────────┘
```

`0` 일 때 초록, `1` 이상이면 즉시 빨강 + 경고. **부하 테스트 내내 이 숫자를 띄워놓고 발표한다.**

### 4-2. 격차를 2축으로 — 지금은 단일 수치

프로토타입의 `격차(건)` 는 단일 계열이라 **원인을 알 수 없다.**

```
db_gap   = total − issued − redisStock       DB가 뒤처짐    → 재처리 대상
list_gap = total − redisUsers − redisStock   Redis 목록 뒤처짐 → 자동 보정 대상
```

**두 값의 부호 조합으로만 원인이 특정된다.** 단일 수치로는 "뭔가 어긋났다"까지밖에 못 말한다. 별도 계열 2개로 그려달라.

## 5. 엔진 전환을 눈으로 보이게 ★

**이게 발표의 클라이맥스다.**

`stateSwitcher`(SCHEDULED/OPEN/SOLD_OUT/CLOSED/QUEUE)를 만들어준 것과 같은 발상으로, **엔진 버전 전환 컨트롤**을 나란히 둔다.

```
엔진   [ v1 MySQL 락 ]  [ v2 Redis Lua ]  [ v3 Kafka ]  ← 사용 중 배지
상태   [SCHEDULED] [OPEN] [SOLD_OUT] [CLOSED] [QUEUE]
```

**전환 시각을 모든 차트에 세로 기준선으로 긋는다.** `v1 → v2` 라벨을 붙여서, 그 선을 기준으로 지표가 확 바뀌는 게 보이게.

| | v1 MySQL 락 | v2 Redis Lua | v3 Kafka |
|---|---|---|---|
| 처리량 | 낮음 | 높음 | 높음 |
| p99 | **급증** | 낮음 | 낮음 |
| DB 커넥션풀 | **포화 90%+** | 낮음 | 낮음 |
| Redis 지연 | 패널 비활성 | 표시 | 표시 |
| Kafka 랙 | — | — | **표시** |
| 응답 `202` | 없음 | 없음 | **다수** |

**버전마다 비활성화되는 패널이 있다.** v1에서 Redis 지연 패널은 회색으로 죽어 있어야 하고, v3에서만 Kafka 랙이 살아난다. 그 자체가 "지금 어떤 엔진인지"를 말해준다.

## 6. 건드리지 말 것

| | 왜 |
|---|---|
| **캘린더 2계층 구조** | 관통선 + 솟은 수요일. 이게 이 화면의 정체성이다 |
| **`ICONS` 4종** | 톤이 맞다. 이모지로 바꾸지 마라 |
| **재고 게이지 임계 3단** | `≥70 초록 · ≤30 주황 · 0 회색` — 사양과 정확히 일치한다 |
| **`stateSwitcher`** | 시연 도구로 그대로 쓴다 |
| **로고 A/B 역할 분리** | A(가로형)는 헤더·푸터, B(심볼)는 파비콘·모바일·로딩 |

> `stateSwitcher` 에 `QUEUE` 가 같이 있는 게 눈에 띈다. 대기열은 캠페인 상태가 아니라 **사용자별 상태**인데 시연 편의로 한 줄에 둔 것으로 이해했다. 그대로 둬도 되지만, 시각적으로 한 칸 띄워주면 좋겠다.

## 7. 우선순위

일정이 밀리면 아래에서부터 자른다.

```
1  초과 발급 카운터 + 격차 2축        ← 채점 축. 이게 없으면 프로젝트가 성립 안 함
2  엔진 전환 + 세로 기준선            ← 발표 클라이맥스
3  쿠폰 카드 컴포넌트                 ← 전 화면이 이걸 쓴다
4  U2 월 이동 · 뷰 토글               ← 캘린더 완성
5  발급 결과 모달 3종
6  A5 일정 관리 · A6 브랜드 CRUD
7  랜딩
8  다크모드
9  로그인·회원가입 (목)
```

**1·2번이 안 되면 나머지가 다 예뻐도 의미가 없다.** 반대로 1·2번만 있어도 프로젝트는 성립한다.
