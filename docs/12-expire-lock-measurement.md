# 만료 배치 인덱스 도입 — 실측 근거

보조 인덱스를 **일부러 빼 둔 채로** 만료 배치를 만들고, 무엇이 얼마나 나빠지는지 수치로 잰 뒤
인덱스를 도입한 기록이다. 재현 명령이 함께 있다.

| | 결과 |
|---|---|
| **① 인덱스 없이 재 봤더니** | 만료가 도는 동안 **발급·사용이 둘 다 막혔다**(오류 1205). 락 5,020 |
| **② 인덱스를 도입했더니** | 락 5,020 → **2**. 사용은 풀렸는데 **발급은 여전히 막혔다** |
| **③ 원인을 파고 보니** | 막는 것이 스캔 범위가 아니라 **보조 인덱스의 gap 락**이었다 |
| **④ 그래서 격리 수준까지** | `인덱스 + READ COMMITTED` → 락 **0**, 발급·사용 **둘 다 통과** |

---

## 0. 재현

```bash
bash docs/measurements/expire-lock-scope.sh
```

- MySQL **26.7.0**(`mysql:latest`, 테스트 컨테이너와 같은 이미지), 기본 격리 **REPEATABLE READ**
- `issuances` **5,000행**, `LIMIT 1000`
- 만료 트랜잭션을 **커밋하지 않은 채** 열어 두고, 다른 커넥션이
  **신규 발급 INSERT** 와 **사용 UPDATE**(만료 대상이 아닌 행)를 시도한다
- `innodb_lock_wait_timeout = 2` 초. 통과하면 `통과`, 막히면 `1205`

운영은 300만 행이라 락 수는 그만큼 커진다. **발급 INSERT 통과 여부는 행 수와 무관하다** —
막는 것이 행 개수가 아니라 잠긴 위치이기 때문이다(§3).

---

## 1. 인덱스를 뺀 채로 재 봤다

`issuances` 에는 보조 인덱스가 없다. 300만 건에서 느린 쿼리를 직접 겪고 개선폭을 수치로 재서
도입 시점을 정하려고 비워 둔 자리다(`cy-seed/ddl/90_perf_indexes_optional.sql`).

만료 배치의 첫 문장이 이것이다.

```sql
UPDATE issuances SET status = 'EXPIRED', updated_at = :committedAt
 WHERE status = 'ISSUED' AND expires_at < :asOf AND id > :afterId
 ORDER BY id LIMIT :limit
```

`status`·`expires_at` 에 인덱스가 없으니 PK 를 id 순으로 훑는다. 그러면서 **지나간 행을 잠근다.**

### 나온 수치

| 만료 대상 | 락 | 발급 INSERT | 사용 UPDATE |
|---|---:|---|---|
| **0건** (하루 288회 중 대부분) | **5,020** | **1205** | **1205** |
| **300건** (`LIMIT` 미달) | **5,020** | **1205** | **1205** |
| 1,000건 (`LIMIT` 충족) | 1,004 | 통과 | 통과 |

**`LIMIT` 이 차느냐가 갈림길이었다.** 차면 그 자리에서 멈추므로 락이 청크 크기에 머문다.
안 차면 테이블 끝까지 훑고 **supremum**(마지막 행 다음 자리)까지 잠근다. 그것이 잠기면
auto-increment 로 뒤에 붙는 **신규 발급이 갈 곳을 잃는다.**

만료 대상이 `LIMIT` 보다 적은 실행이 그 경우다 — 0건 실행이 그렇고, 대상이 많은 날도
**마지막 청크는 반드시** 그렇다. **모든 실행이 최소 한 번은 이 상태를 지난다.**

> 성능이 문제일 줄 알았는데 **가용성**이 먼저 터졌다. 선착순 발급이 본체인 프로젝트에서
> 만료 배치가 5분마다 발급을 막는다는 뜻이다.

## 2. 인덱스를 도입했다

```sql
CREATE INDEX `idx_issuance_status_expires` ON `issuances` (`status`, `expires_at`);
```

이름과 컬럼 순서는 시드 처방전(`cy-seed/ddl/90_perf_indexes_optional.sql`)이 예정해 둔 그대로다.

### 나온 수치

| 만료 대상 | 락 (전) | 락 (후) | 발급 INSERT | 사용 UPDATE |
|---|---:|---:|---|---|
| 0건 | 5,020 | **2** | **1205** | 통과 ✅ |
| 300건 | 5,020 | **905** | **1205** | 통과 ✅ |
| 1,000건 | 1,004 | 1,004 | 통과 | 통과 |

**락이 5,020 → 2 로 떨어졌다.** 0건 실행이 5,000행을 훑던 것이 2건으로 줄었고,
운영 300만 행이면 그 차이가 그대로 커진다. 사용 UPDATE 봉쇄도 풀렸다.

**그런데 발급 INSERT 는 여전히 막혔다.** 락이 2개뿐인데도.

---

## 3. 왜 인덱스로도 발급이 막혔나

막고 있는 락을 직접 떴다.

```
요청: idx_issuance_status_expires   X,GAP,INSERT_INTENTION   'USED', …
차단: idx_issuance_status_expires   X                        'USED', …
```

인덱스는 `(status, expires_at)` 순으로 정렬돼 있고 문자열 순서로 `'ISSUED' < 'USED'` 다.
`status='ISSUED'` 를 찾다가 범위 끝에서 **다음 값인 `'USED'` 의 첫 항목에 next-key 락**을 잡는데,
그 락이 품는 gap 이 **정확히 새 `'ISSUED'` 항목이 들어갈 자리**다.

그래서 발급만 막히고, 인덱스와 무관한 사용 UPDATE 는 통과한다.

> **인덱스는 스캔 비용의 문제를 풀지 잠금 위치의 문제를 풀지 않는다.**
> 이것이 이 측정에서 가장 뜻밖이었던 부분이다.

## 4. 격리 수준까지 낮췄다

REPEATABLE READ 는 팬텀을 막으려고 gap 을 잠근다. READ COMMITTED 는 **gap 락을 안 잡고,
매치되지 않은 행의 락을 즉시 놓는다.**

만료 배치의 Step 에만 적용했다.

```java
stepTimeout.setIsolationLevel(TransactionDefinition.ISOLATION_READ_COMMITTED);
```

### 나온 수치

| 만료 대상 | 인덱스만 | **인덱스 + RC** | 발급 INSERT | 사용 UPDATE |
|---|---:|---:|---|---|
| 0건 | 2 | **0** | **통과** ✅ | **통과** ✅ |
| 300건 | 905 | **600** | **통과** ✅ | **통과** ✅ |
| 1,000건 | 1,004 | **1,000** | 통과 | 통과 |

**넘긴 건수만큼만 잠근다.** 안 넘긴 행은 하나도 안 잠근다.

### 정합성이 깨지지 않는지 확인했다

만료 배치는 뒤 문장들이 **표식**(`updated_at = committedAt`)으로 방금 넘긴 집합을 되찾고,
다섯 값을 서로 대조해 어긋나면 멈춘다. RC 에서는 문장마다 스냅샷이 갱신되므로 그 구조가
깨질 수 있어 전체 테스트를 돌렸다.

| | 결과 |
|---|---|
| 만료 기능 테스트 전부 | **통과** — 청크 이어짐 · 재시작 · 이력 짝 · 재고 짝 · 락 순서 · 만료×취소 경합 |
| 락 범위 테스트 2건 | **의도된 실패** — 락이 200→9, 190→32 로 떨어져 "현재 비용" 단언이 뒤집혔다 |
| 스키마 파리티 2건 | **의도된 실패** — 인덱스가 생겨 시드 DDL 과 갈렸다 |

RC 는 **만료 배치 Step 에만** 걸었다. 검증 배치(`verifyJob`)는 그대로 REPEATABLE READ 다 —
그쪽은 판정 시점을 얼려야 하므로 격리 수준이 낮아지면 안 된다.

## 5. 다른 길은 없었나

발급 봉쇄를 푸는 방법이 격리 수준만은 아니다. 두 가지를 더 재 봤다.

### 후보를 먼저 뽑아 PK 로 때리면? — **안 된다**

```sql
SELECT id FROM issuances WHERE status='ISSUED' AND expires_at < ? ORDER BY id LIMIT n;
UPDATE issuances SET status='EXPIRED' WHERE id IN (…) AND status='ISSUED';
```

| 인덱스 있음 · RR · 만료 300건 | 락 | gap 락 | 발급 INSERT |
|---|---:|---:|---|
| 조건부 UPDATE 한 문장 | 905 | — | **1205** |
| 후보 SELECT → `WHERE id IN (…)` | 904 | **600** | **1205** |

PK 를 콕 집어 때려도 gap 락을 600개 잡는다. **`status` 를 바꾸는 순간 보조 인덱스 항목이
이동하기 때문**이다 — `('ISSUED', …)` 에서 지워지고 `('EXPIRED', …)` 에 삽입되는데, 그
삭제·삽입이 gap 을 건드린다. **어떤 경로로 행을 찾았는지와 무관하다.**

### `SKIP LOCKED` 는? — **방향이 다르다**

그것은 *잠긴 행을 만났을 때 건너뛰는* 기능이다. 우리 문제는 반대다 — 만료가 잠긴 걸 만나
기다리는 것이 아니라 **만료가 남을 잠가서 발급이 기다린다.** (그리고 `UPDATE` 문에는 못 붙는다.)

### 인덱스를 빼고 스캔 창으로 가면? — **된다. 다만 우리한테는 안 맞는다**

인덱스가 없으면 보조 인덱스 gap 도 없다. `AND id <= :afterId + N` 으로 supremum 만 피하면
발급이 통과한다(§1 표의 "스캔 창" 행). 그래서 실제 선택지는 둘이었다.

| 기준 | 왜 우리한테 중요한가 | **인덱스 + RC** | 인덱스 없이 스캔 창 |
|---|---|---|---|
| 발급 안 막힘 | 프로젝트 본체 | 통과 | 통과 |
| **5분 주기 유지** | 넘기면 크론 슬롯이 통째로 사라진다. 로그도 안 남는다 | 훑을 게 없어 짧다 | **300만 행을 매 실행 훑는다** |
| **부하 시연** | 20,000명 동시 발급 중에 만료가 돈다 | 넘긴 만큼만 | 창마다 1,004 × 3,000회 |
| 코드 복잡도 | 종료 조건이 바뀌면 재시작·멱등성을 다시 검증해야 한다 | 그대로 | **`0 = 대상 없음`이 깨진다** |
| 검증 배치와의 관계 | V1~V6 도 같은 테이블을 훑는다 | 인덱스를 같이 쓴다 | 만료만 해결 |
| 설명 비용 | 팀이 이해해야 한다 | **격리 낮춤 설명 필요** | 없음 |

**5분 주기가 갈랐다.** 스캔 창은 발급 봉쇄를 풀지만 300만 행 스캔을 그대로 남긴다.
한 실행이 5분을 넘기면 그 사이 크론 슬롯이 사라지고 **로그에 한 줄도 안 남는다** —
"발급은 안 막지만 만료가 조용히 밀리는" 상태가 된다. 부하 시연이 이 잡의 값어치를 보이는
자리인데 거기서 창마다 잠그는 것도 맞지 않는다.

스캔 창이 나았을 상황은 **인덱스 도입을 더 미뤄야 하거나 팀이 격리 변경을 못 받아들이는**
경우다. 둘 다 지금은 해당하지 않는다 — 수치화 목적은 이 문서로 달성됐다.

## 6. 결론

**인덱스와 READ COMMITTED 를 둘 다 넣는다.** 서로 다른 문제를 풀기 때문이다.

| | 푸는 문제 | 근거 |
|---|---|---|
| **인덱스** | 0건 실행이 300만 행을 훑는 **스캔 비용** | 락 5,020 → 2 |
| **READ COMMITTED** | 만료가 발급을 막는 **가용성** | 발급 INSERT 1205 → 통과 |

인덱스만 넣으면 발급이 계속 막히고, RC 만 넣으면 300만 행을 계속 훑는다.

**격리를 낮춰도 되는 근거** — 이 잡은 팬텀 보호를 쓰지 않는다. 잡이 도는 중 새로 발급된 건은
`expires_at` 이 미래라 애초에 대상이 아니고, 놓친 것이 있어도 5분 뒤 다음 주기가 가져간다.
멱등성은 스냅샷이 아니라 `EXPIRE_BATCH` 의 `status='ISSUED'` 조건이 지킨다.
그래서 **필요 없는 보호가 발급을 막고 있던 것**이고, 만료 Step 에만 껐다.
`verifyJob` 은 판정 시점을 얼려야 하므로 REPEATABLE READ 그대로다.

## 7. 같은 패턴이 통계 집계에도 있다

만료만의 문제가 아니었다. `StatsJdbcAdapter` 의 두 문장이 같은 모양이다.

```sql
INSERT INTO coupon_stats (…) SELECT … FROM issuances …   -- 잠금 읽기
```

실측(5,000행, REPEATABLE READ):

| | issuances 락 | 발급 INSERT |
|---|---:|---|
| 통계 집계가 도는 중 | **5,023** | **1205** |

**처방은 만료와 같을 수 없다.** 통계는 `dataset_fingerprint` 와 함께 판정 근거가 되므로,
격리를 내리면 집계 중에 원본이 바뀔 수 있다. 그쪽에는 `DATASET_MUTATED_DURING_RUN` 가드가
있어서 <b>조용히 틀리는 대신 검증이 명시적으로 죽는</b> 쪽으로 설계돼 있는데, 그것이 더 나은지는
검증 결정론 쪽 판단이다.

**지금 막아 주는 것**은 검증 잡의 `rejectRunningSchedulers` 다 — 스케줄러가 켜져 있으면 검증을
거부한다. 다만 그 가드는 <b>배치 JVM 의 플래그만 본다</b>. 발급 API 프로세스는 그것으로 멈추지
않으므로, 발급 경로가 생기는 시점에 이 축을 다시 봐야 한다.

**결정할 것** — 검증 중에는 발급도 멈추는 운영 규율로 갈지, 통계 Step 도 격리를 내릴지.
발급 경로가 아직 저장소에 없어 지금은 *"막힐 수 있다"* 까지만 확인된 상태다.

## 8. 이후 할 일

**처리했다**

- 스키마 파리티 — `cy-seed` 의 처방전에서 이 인덱스만 `10_constraints_common.sql`(적재 **후**
  적용)로 승격했다. 300만 건 적재 성능은 그대로다. **cy-seed 커밋이 따로 필요하다**
- 락 범위 테스트 — "현재 비용을 못 박는" 방향에서 **"개선된 상태를 지키는"** 방향으로 뒤집었다
- 발급 INSERT 통과를 **직접 단언하는 테스트** — 별도 커넥션에서 실제로 INSERT 를 던진다.
  락 개수는 대리 지표라, supremum 하나만 잠겨도 개수로는 안 드러난다
- **인덱스를 지키는 테스트** — RC 로 내린 뒤로는 인덱스가 없어도 락이 0 이라 락 단언으로는
  못 잡는다(실제로 `V11` 을 지우는 돌연변이가 통과했다). `Handler_read_*` 로 **읽은 행 수**를
  재는 축을 따로 뒀다 — 인덱스 없음 5,004행 → 있음 0행

**아직 안 쟀다** — 이 문서의 표에 없는 것은 아직 모르는 것이다

- **300만 행에서의 실제 실행 시간.** 여기서는 락 범위만 쟀다. 인덱스가 스캔 비용에 주는 효과를
  시간으로 확인하려면 `EXPLAIN ANALYZE` 로 따로 재야 한다
- **여러 청크가 이어질 때의 누적 효과.** 청크 하나만 열어 두고 쟀다
- **RC 에서 만료 × 발급이 실제로 동시에 도는 부하 시험.** 단위 테스트는 통과했지만
  300만 행 + 동시 발급 부하는 아직 안 돌렸다
- **`stockRowCount`(스냅샷 읽기) ↔ `releaseStock`(최신 읽기)의 격리 차이가 RC 에서 어떻게
  되는지.** REPEATABLE READ 에서 두 문장이 다른 버전을 볼 수 있다는 지적이 있었는데,
  RC 가 그것을 완화하는지 악화하는지 아직 안 쟀다

## 9. 실측이 뒤집은 것

작업 중에 코드와 리뷰에 이렇게 적혀 있었다. 둘 다 그럴듯했고 둘 다 틀렸다.

> *"`id <= :lastId` 를 걸면 락이 1,004 로 줄고 **발급이 통과한다**"*

**절반만 맞았다.** 그 상한은 뒤 문장들에만 걸렸고 첫 문장에는 걸 수 없었다.
게다가 그때의 측정이 **만료 대상을 앞쪽에 몰아 둔 조건**이라 `LIMIT` 이 일찍 차서
supremum 에 닿지 않았다 — 그래서 문제가 안 보였다.

> *"인덱스를 붙이면 락이 사라지고 INSERT 가 통과한다"*

**락은 줄지만 INSERT 는 여전히 막힌다**(§3).

두 문장 모두 실행해 보기 전에는 맞는 말처럼 읽혔다. 그래서 이 문서가 있다.
