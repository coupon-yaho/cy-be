프로덕션RedisRuntimeConfigStore를 자동설정한다. API는 runtimeOnly project(':infra:redis')로 어댑터 구현을 컴파일 시점에 직접 참조하지 않는다.
로컬·테스트 계약InMemoryRuntimeConfigStore는 CAS 가능한 테스트 구현, ReadOnlyRuntimeConfigStore는 저장 없는 거짓 성공을 금지하는 구현이다.

저장 JSON은 웹 전역 ObjectMapper와 분리된 전용 매퍼를 사용한다. API 응답 naming 설정이 바뀌어도 Redis 영속 포맷이 함께 바뀌지 않는다.

4. 읽기와 Last Known Good

상황반환이유
Redis 정상·JSON 정상VALIDRedis를 권위값으로 읽고 LKG를 갱신
Redis 장애·LKG 있음STALE마지막 정상 스냅샷으로 읽기 가용성 유지
Redis 장애·LKG 없음503기동 직후에는 반환할 검증된 값이 없음
JSON 손상500일시 장애로 숨기지 않고 손상으로 노출

로컬 revision 하한을 제거한 이유

LKG는 각 인스턴스 메모리이므로 A는 rev12, 새로 기동한 B는 LKG 없음일 수 있다. 이를 Redis 전역 revision의 하한으로 쓰면 동일한 Redis rev3을 A는 500, B는 정상으로 처리한다. 따라서 LKG는 장애 폴백에만 사용하고 정상 연결 상태에서는 Redis를 권위값으로 삼는다.

동시성 보호는 유지: 느린 과거 읽기가 그 사이 완료된 최신 update의 LKG를 덮지 않도록, 읽기·쓰기 시작 시 참조값을 기준으로 compareAndSet한다.

5. 감사 로그와 불확실한 쓰기

감사 로그 한 건은 “사용자 요청 전체”가 아니라 성공한 런타임 설정 변경 한 번을 뜻한다.

7개 필드previousRevision, newRevision, beforeConfig, afterConfig, changedBy, changedAt, requestId
보존 정책RPUSH 후 LTRIM -1000 -1로 최근 1,000회 변경만 유지

응답이 유실된 쓰기 확정

Redis가 커밋한 뒤 네트워크 응답만 사라질 수 있다. 예외 타입만으로 실행 전·후를 판별하지 않고, 최근 감사 로그에서 동일한 requestId와 기대 결과를 찾아 성공 여부를 확인한다.

if (requestId.equals(audit.requestId())
        && expected.equals(audit.afterConfig())) {
    return audit.afterConfig();
}
throw UPDATE_OUTCOME_UNKNOWN;
보수적 판정: Redis 연결 획득 전에 실패해 실제로 미실행된 경우도 실행 시점을 증명할 수 없으면 UPDATE_OUTCOME_UNKNOWN이다. 잘못된 “미적용” 확정보다 안전한 방향을 택했다.
남은 원자성 경계: Redis Lua는 격리 실행되지만 명령 오류를 롤백하지 않는다. SET 성공 후 RPUSH가 OOM이면 설정만 바뀔 수 있다. 순서를 뒤집으면 반대로 거짓 감사 기록이 생기므로 단순 재정렬로 해결하지 않았다.

GlobalExceptionHandler는 RuntimeConfigRevisionConflictException일 때만 currentRevision을 채운다. 일반 BusinessException에서는 null이며 전역 NON_NULL 설정으로 JSON에서 생략된다.
