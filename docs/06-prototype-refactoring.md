# 프로토타입 → 구현 리팩토링 지침

Claude Design 프로토타입(`쿠폰야호 프로토타입.dc.html`, 1,532줄)을 실제 프론트엔드에 반영할 때 **무엇을 가져오고 무엇을 버리는지**, 그리고 갈라진 지점 5개를 **어떻게 결정했는지**를 정리한 문서다.

**대상 세 가지가 지금 서로 다른 방향을 보고 있다.**

| | 무엇 | 상태 |
|---|---|---|
| **프로토타입** | `claude.ai/design` · `쿠폰야호 프로토타입.dc.html` | 화면 6개, 데스크탑 전용, 목 데이터 |
| **프론트 레포** | `world-to-code/coupon-magic-96` | 라우트 11개, 반응형, 다크모드, 목 API 레이어 |
| **핸드오프** | `docs/05-design-handoff.md` | 사양서. 24패널·우선순위·API 계약 |

**결정 5개는 전부 닫혔고 `05-design-handoff.md` 에 반영됐다** (7절 요약). 이 문서는 *왜 그렇게 정했는지*의 근거고, 넘기는 사양서는 핸드오프 쪽이다.

## 1. 세 갈래로 갈라진 지점

### 결정 ① 브랜드 일정 모델 — **충돌이 아니었다**

처음엔 프로토타입의 `DAY_GROUPS`(Day1/2/3)와 `WEEKS`(브랜드 위크)가 서로 다른 모델이라고 봤는데, **코드를 대조해보니 같은 이벤트의 두 뷰다.**

```
DAY_GROUPS  d1: 08월 12일(수) D-2  ┐
                                   ├── 같은 회차. 리스트 뷰 / 캘린더 뷰
WEEKS       week①: wed:12   D-2   ┘

d2 ↔ week② (8/19, D-9) · d3 ↔ week③ (8/26, D-16)
```

즉 프로토타입의 일정은 **매월 2·3·4주차 수요일** 이고, 이건 `nthWeek ∈ {2,3,4} × dayOfWeek = 3` 으로 **`CouponTemplate` 이 그대로 표현한다.**

그리고 PRD 의 근거와도 어긋나지 않는다:

> 요일·시각을 흩뿌린 이유는 통계 화면의 **요일×시간 히트맵이 의미 있는 패턴**을 그리도록 하기 위함입니다.

요일을 수요일에 **편중**시키되 시각을 흩뿌리면(14:00·15:00·16:00) 히트맵에 세로 띠가 생겨 오히려 패턴이 선명하다.

**결정: `nthWeek × dayOfWeek` 유지.** 표현만 `Day1/Day2/Day3` 라벨로 묶는다. 데이터 모델 변경 없음.

### 결정 ② 브랜드 색 — 상수인가 데이터인가

**브랜드 개수(6 vs 12)는 결정 사항이 아니다.** 시드 데이터이고, `/admin/brands` 에서 운영자가 추가하는 순간 무의미해진다. 실제로 결정해야 하는 건 **색을 어디에 두느냐**다.

| | 프로토타입 | 프론트 레포 |
|---|---|---|
| 방식 | `PASTEL` 상수 배열 + `pastel: 0~5` 인덱스 | 브랜드마다 `color` 값 |
| 확장 | **7번째 브랜드부터 색이 겹침** | 무한 |

```js
// 프로토타입 — 상수 배열에 묶임
const PASTEL=['#C8E6E0','#F5E6C8','#D5D8EE','#F0C4CC','#F5D5B8','#BDD5EA'];
{brand:'모카빈', pastel:0}
```

**결정: 색을 브랜드 데이터로 둔다.**

```
brands
  color   VARCHAR   카드 배경 · 캘린더 배지 · 좌측 레일
```

**파스텔 6종은 로고에서 뽑은 팔레트**(쿠폰 티켓 부채꼴의 색)이므로 **시드 브랜드의 기본값**으로만 쓴다. 상수로 고정하면 브랜드가 늘어나는 순간 색이 재사용되어 구분이 안 되고, `/admin/brands` 에서 색을 고를 수도 없다.

> 시드에 브랜드를 몇 개 넣을지는 **아무 때나 바꿀 수 있다.** 캘린더 2계층 구조상 한 주에 `주간 1 + 수요일 3 = 4개`가 필요하고 3주면 12슬롯이니, 브랜드 6개면 재사용이 자연스럽다(실제 T멤버십도 그렇다). 다만 이건 설계가 아니라 취향이다.

### 결정 ③ 색 표기 — oklch

| | |
|---|---|
| 프로토타입 | hex — `#2B3A55` `#7BA7D7` `#C9A961` |
| 프론트 레포 | oklch — `oklch(0.26 0.075 264)` |

**둘은 같은 색이다.** 프로토타입이 내 원래 핸드오프의 hex 를 그대로 썼고, 레포가 oklch 로 변환했다.

**결정: 레포의 oklch 를 유지한다.** Tailwind v4 토큰 체계가 이미 그걸로 짜여 있고, hex 로 되돌리면 다크모드 토큰이 깨진다. 프로토타입의 hex 는 **참조용 원본**으로만 본다.

단 **`brands.color` 는 예외** — 운영자가 `/admin/brands` 색상 피커에서 고르는 값이라 hex 로 저장한다. 테마 토큰(oklch)과 브랜드 데이터(hex)는 층이 다르다.

## 2. 프로토타입에서 반드시 가져올 것

### ① 쿠폰의 "이용 조건"과 "사용 기간" — 데이터 모델에 없다

프로토타입은 쿠폰마다 이걸 들고 있다.

```js
{
  benefit: '아메리카노 무료',
  desc:    '브랜드데이 하루만, 전 매장 픽업 주문',
  period:  '2026년 8월 12일(수) ~ 8월 18일(화)',
  terms:   ['앱 픽업 주문 시 사용 가능 (1인 1매)', '키오스크 · 배달 주문 제외']
}
```

**발급 시각과 사용 가능 기간이 다르다.** 8/12 에 발급받아 8/18 까지 쓴다. 그리고 `terms[]` 는 실제 쿠폰의 핵심 정보인데 **프론트 레포에도 우리 ERD 에도 없다.**

**해야 할 것**

```
coupon_templates 에 추가
  benefit_title    VARCHAR   '아메리카노 무료'
  benefit_desc     VARCHAR   '브랜드데이 하루만, 전 매장 픽업 주문'
  usable_from      DATETIME  사용 시작
  usable_until     DATETIME  사용 종료 (발급 마감과 별개)
  terms            JSON      이용 조건 문자열 배열
```

`Issuance.expiresAt` 하나로는 표현이 안 된다. **발급 마감 ≠ 사용 만료**다.

### ② 브랜드 카테고리 + 아이콘 4종

```js
ICONS = { cafe, shop, ride, film }   // SVG path, stroke 1.6, 24×24
카테고리: 카페/디저트 · 쇼핑 · 배달 · 영화/문화
```

**결정: 이모지 대신 선 아이콘.** 프론트 레포는 이모지(`☕🛒🎬`)를 쓰는데, 프로토타입의 SVG 아이콘이 톤에 맞고 **캘린더 셀 크기(16px)로 줄여도 안 뭉개진다.** 이모지는 OS 마다 모양이 달라서 스크린샷·발표 자료에서 통제가 안 된다.

**아이콘은 브랜드가 아니라 카테고리에 붙는다.** 카테고리는 도메인 enum 이라 개수가 고정이고, 브랜드가 몇 개로 늘어나도 아이콘을 새로 그릴 일이 없다.

```
brands.category   ENUM(CAFE, SHOP, DELIVERY, CULTURE)   → ICONS 4종에 1:1
brands.color      VARCHAR                                 → 운영자가 자유롭게
```

**해야 할 것** — `ICONS` 4종을 그대로 컴포넌트로 옮긴다.

### ③ 지난 혜택 목록 (`ENDED`)

```js
ENDED = [ {brand:'씨네하우스', benefit:'일반관 관람권 50% 할인'}, ... ]
```

**"이 서비스가 꾸준히 돌아왔다"를 보여주는 장치다.** 캘린더의 과거 월 탐색과 같은 목적이고, 구현이 훨씬 싸다. 랜딩이나 캘린더 하단에 넣는다.

### ④ 캘린더 2계층 구조 — 주간 배경 + 수요일 하이라이트 ★

프로토타입 캘린더의 핵심이고, **이게 T멤버십 실물의 구조다.**

```js
{kind:'week', days:[10,11,12,13,14], label:'브랜드 위크 ① 8/10~14',
 weekBrand:'라운드베이커리',                    // 그 주 5일 내내
 wed:12,                                        // 주 안의 하이라이트 날
 wedBrands:[모카빈, 그린마트, 버터핏(VIP)],     // 그날 하루만
 dday:'D-2', accent:OK, tint:'#F1F7F3'}
```

렌더링이 계층을 그대로 표현한다 — 5칸 그리드에 `top:66%` 로 **주를 관통하는 가로선**을 깔고, **수요일 셀만 `margin:-14px 0`** 으로 위아래로 튀어나오게 한 뒤 흰 배경 + `zIndex:2` 를 준다.

```
 8/10    8/11    8/12    8/13    8/14
                ┌──────┐
                │  수  │            ← 솟아오름 (흰 배경, zIndex 2)
━━━━━━━━━━━━━━━┥  12  ┝━━━━━━━━━━━  ← 주 관통선 (accent, opacity .55)
                │ 3개  │
                └──────┘
         라운드베이커리 (주간)         D-2
   ─────────── tint 배경 ───────────
```

주마다 `accent` 와 `tint` 가 다르다 — 초록(`#F1F7F3`) · 파랑(`#EDF3FA`) · 붉은색(`#FBF1F3`). **다가올수록 붉어지는 게 아니라 주를 구분하는 용도**다.

지난 주(`kind:'past'`)는 구조가 다르다 — 관통선 없이 각 날짜에 브랜드가 흩어지고, **`영 위크`(만 13~34세 전용) 서브섹션**이 붙는다. 여기 브랜드가 초심·롱블랙·팀홀튼·던킨·다운타우너·씨유·이마트24·NOL티켓 — **업로드된 T멤버십 PDF 의 실제 제휴사다.**

#### 주간 브랜드는 선착순 대상이 아니다 — 결정 ④

`weekBrand` 와 `wedBrands` 는 **성격이 완전히 다르다.**

| | 주간 브랜드 (`weekBrand`) | 수요일 브랜드 (`wedBrands`) |
|---|---|---|
| 기간 | 월~금 5일 | **특정 시각 하루** |
| 성격 | 배경·분위기 | **선착순 경쟁** |
| 재고 | 사실상 무제한 | 10,000장 |
| 동시성 | 없음 | **우리 채점 축** |
| 대기열 | 불필요 | 필수 |

**5일 내내 열려 있으면 재고 경쟁이 안 생긴다.** 우리가 증명할 것은 "10,000장에 20,000명이 **같은 순간**에 몰려도 초과 발급 0건" 이고, 그건 하루 특정 시각 오픈이어야 성립한다.

**결정 — 주간 브랜드는 표시 전용으로 만든다.**

```
weekly_features            선착순 대상 아님. 재고·발급 없음
  year_month   VARCHAR     '2026-08'
  week_index   INT         1 · 2 · 3
  brand_id     FK
  starts_on    DATE        월요일
  ends_on      DATE        금요일
  accent       VARCHAR     캘린더 관통선·틴트 색
```

**이유 둘.**

**하나** — 캘린더의 시각적 완성도를 거의 다 가져오면서 `CouponTemplate` 을 안 건드린다. 관통선과 솟은 수요일 구조가 그대로 나온다.

**둘** — 발표에서 **대비가 생긴다.** *"주간 브랜드는 여유롭게 받으시고, **수요일 14시 이 세 개가 진짜 경쟁입니다**"* 라고 말할 수 있다. **배경이 있어야 하이라이트가 산다.**

> 주간 브랜드에도 재고·발급을 붙이는 안(같은 모델에 `kind: DAY|WEEK`)은 채택하지 않는다. 동시성 로직을 태워야 하는데 정작 경쟁이 안 일어나서 얻는 게 없다.
> 주간 브랜드를 아예 빼는 안도 채택하지 않는다. 5칸 중 1칸만 채워져 캘린더가 밋밋해진다.

### ⑤ 캠페인 상태 전환 컨트롤 (시연용)

```js
stateSwitcher = [SCHEDULED, OPEN, SOLD_OUT, CLOSED, QUEUE]
```

**5가지 상태를 버튼으로 즉시 전환**해 화면을 바꾼다. 시연·발표에서 "오픈 전 → 발급 중 → 매진" 을 몇 초 만에 보여줄 수 있다.

**엔진 전환(v1/v2/v3) 컨트롤과 같은 역할이다.** 둘을 나란히 두면 발표 조작 패널이 된다.

> `QUEUE` 가 상태 목록에 함께 있는 게 눈에 띈다. 대기열은 캠페인 상태가 아니라 **사용자별 상태**인데, 시연 편의로 같은 줄에 뒀다. 실제 구현에서는 분리해야 한다.

### ⑥ 재고 게이지 임계 3단

```js
gaugeColor = remain>=70 ? OK : remain<=0 ? MUTED : remain<=30 ? WARN : SKY;
```

핸드오프와 정확히 일치한다. **그대로 쓴다.**

## 3. 프로토타입에서 버릴 것

| | 왜 |
|---|---|
| **데스크탑 전용** (`min-width:1280px`) | 사용자 화면(U1·U3)은 **모바일이 실사용**이다. 프로토타입은 시연용이라 데스크탑만 그렸다. 관리자·대시보드는 데스크탑 전용이 맞다 |
| **다크모드 없음** (0건) | 레포는 전 화면 지원한다. 프로토타입 기준으로 되돌리지 마라 |
| **인라인 스타일 전면** | `style="..."` 로 전부 박혀 있다. 프로토타입 문법이라 그런 것이고, 구현은 Tailwind 토큰으로 옮긴다 |
| **`m_812934` 하드코딩 헤더** | 마스킹 형식은 맞지만 세션에서 와야 한다 |

목 데이터 배열(`DAY_GROUPS` `WEEKS` `MY` `CAMPAIGNS` `series()`)도 전부 버린다 — 7절 참조.

> `브랜드 위크` 라벨은 **버리지 않는다.** 한때 `Day1/2/3` 과 충돌한다고 적었으나 오독이었다 — 둘은 같은 회차의 두 뷰이고, 주간 브랜드는 `weekly_features` 로 살린다. 결정 ①·④ 참조.

## 4. 프로토타입에 없어서 따로 만들어야 하는 것

프로토타입 화면은 **6개**다. `U1 발급 · U3 쿠폰함 · A1 캠페인 관리 · D1 운영 · D2 관제 · D3 분석`

| 없는 것 | 어디에 정의돼 있나 |
|---|---|
| **랜딩** | 레포 `/` — 히어로·브랜드 그리드·등급 안내·3단계 설명 |
| **U2 캘린더의 월 이동** | 주 단위 행은 프로토타입에 **이미 있다**(2절 ④). 없는 건 `◀ 2026년 8월 ▶` 과 과거 월 탐색, 뷰 토글 |
| **A5 브랜드데이 일정** | 핸드오프 6절. API 는 레포에 이미 있음 (`adminListTemplates`) |
| **A6 브랜드 CRUD** | API 는 레포에 있음 (`adminListBrands`). 여기에 **색·카테고리 입력**이 붙는다 (결정 ②·⑤) |
| **로그인·회원가입** | 레포 `/login` `/signup` |
| **발급 결과 모달 3종** | 핸드오프 U3 절 — 프로토타입은 `modal` 상태만 있고 3종 분기가 없다 |

**U2 캘린더는 새로 만드는 게 아니라 이어붙이는 것이다.** 관통선 + 솟은 수요일 구조가 이미 있고, `Day1/2/3` 세로 섹션이 사실상 리스트 뷰다. **월 이동과 뷰 토글만 추가하면 된다.**

---

## 5. 대시보드 — 프로토타입이 실제로 그린 것

프로토타입에 존재하는 지표를 확인했다. **핸드오프 24패널과 상당 부분 일치한다.**

| | 프로토타입에 있음 |
|---|---|
| D1 운영 | 대기 인원 · 예상 대기(초) · 상태별 보유량(ISSUED/USED/CANCELLED/EXPIRED) · 브랜드별 소진 · 응답코드 스트림(201/409/403/202) |
| D2 관제 | p50·p95·p99 · 응답코드 rate(201/202/403/409/5xx) · in-flight · DB풀% · Redis 지연 · Kafka 랙 · **격차(건)** |
| D3 분석 | v1 · v2 · v3 비교 · 상태 전이 퍼널(발급/사용/취소/만료) |

### ⚠️ 여전히 빠진 것 둘 — 세 곳 모두에서

**① 초과 발급 stat (11번 패널)**

프로토타입에도 **없다.** 프론트 레포 `MetricPoint` 에도 없다.

**이 프로젝트의 1순위 채점 지표인데 어디에도 데이터 소스가 없다.** 백엔드가 `overIssued` 를 내려주고, D2 화면에서 **가장 크게** 그려야 한다.

**② 격차의 2축 분리 (19번 패널)**

프로토타입은 `격차(건)` 단일 계열이다. **원인을 알 수 없다.**

```
db_gap   = total − issued − redisStock      DB 측이 뒤처짐  → DLT 재처리 대상
list_gap = total − redisUsers − redisStock  Redis 목록 뒤처짐 → 자동 보정 대상
```

**두 gap 의 부호 조합으로만 원인이 특정된다.** 단일 수치로는 "뭔가 어긋났다" 까지밖에 못 말한다.

## 6. 리팩토링 순서

세 갈래를 합치는 작업이라 **순서가 중요하다.** 데이터 모델부터 잡지 않고 화면을 만지면 두 번 고친다.

```
0. 결정 5개 — ✅ 전부 닫힘 (7절)
   ↓
1. docs/05-design-handoff.md 를 결정에 맞춰 수정   ← ✅ 완료
   ↓
2. 데이터 모델 보강                terms · usable_from/until · benefit_title
                                   weekly_features · brands.color/category
   ↓
3. 프론트 레포에 반영
   3-1  아이콘 4종을 이모지 대신
   3-2  쿠폰 카드 컴포넌트 (노치 + 점선) — 아직 없다
   3-3  Day 섹션 → U2 캘린더
   3-4  상태 전환 컨트롤 (시연용)
   ↓
4. 대시보드 구멍 2개               초과발급 stat · 격차 2축
   ↓
5. 미구현 화면                     A5 스케줄 · A6 브랜드
```

**2번을 3번보다 먼저 한다.** `terms` 와 사용 기간이 데이터에 없으면 카드를 만들어도 채울 게 없다.

## 7. 결정 요약 — 남는 것과 버릴 것

**프로토타입은 전부 목 데이터다.** 그래서 결정을 두 종류로 갈라야 한다 — **개발 후에도 남는 것**과 **시드라 언제든 버릴 것.**

### 남는 것 — 전부 결정됨

| # | 무엇 | 근거 | 결론 |
|---|---|---|---|
| **①** | 일정 모델 | 1절 | `DAY_GROUPS` ↔ `WEEKS` 는 같은 회차의 두 뷰였다. **`nthWeek × dayOfWeek` 그대로**, 표현만 Day 라벨 |
| **②** | 브랜드 색의 위치 | 1절 | **`brands.color` 컬럼.** 상수 배열에 묶으면 확장이 막힌다 |
| **③** | 색 표기 | 1절 | 테마 토큰은 **oklch**, `brands.color` 만 hex. 층이 다르다 |
| **④** | 주간 브랜드 | 2절 ④ | **표시 전용** `weekly_features`. 재고·발급 없음. 선착순은 수요일 브랜드만 |
| **⑤** | 아이콘 | 2절 ② | **SVG 선 아이콘**을 `brands.category` enum 4종에 1:1 |

**5개 다 닫혔다.** 여기에 데이터 모델 4건이 붙는다 — `terms` · `usable_from/until` · `benefit_title` (2절 ①), `weekly_features` (2절 ④), `brands.color` · `brands.category` (위 ②⑤).

### 버릴 것 — 결정할 필요 없다

| 무엇 | 왜 |
|---|---|
| 브랜드 개수·이름·색 | `/admin/brands` 에서 운영자가 만든다. 시드는 언제든 교체 |
| `DAY_GROUPS` · `WEEKS` · `MY` · `CAMPAIGNS` 배열 | 목 데이터. API 로 대체 |
| 목 지표 시계열 (`series()`, `rnd()`) | `/api/v1/admin/metrics` 로 대체 |
| 하드코딩 날짜 (`8/12`, `D-2`) | 스케줄러가 계산 |
| `m_812934` 헤더 | 세션에서 온다 |

**시드 데이터를 놓고 회의하지 마라.** 3주짜리 프로젝트에서 브랜드를 6개로 할지 12개로 할지는 나중에 `INSERT` 문 한 줄이다.

> ①과 ④는 처음에 "충돌"로 적었으나 **오독이었다.** 프로토타입은 내부적으로 일관돼 있고, 2계층(주간 배경 + 수요일 하이라이트) 구조가 T멤버십 실물을 정확히 옮긴 것이다.
