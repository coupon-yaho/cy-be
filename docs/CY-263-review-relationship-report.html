최초 초기화와 Redis 키 소유권

B1 · m4 · C2 — 같은 문제를 서로 반대 방향에서 본 항목

새 Redisconfig:runtime 키가 없음
→
일반 compose 기동seed는 명시적 profile이라 실행되지 않음
→
API 접근GET·UPDATE 모두 STORE_MISSING

현재 코드로 성립 B1의 알맹이

업데이트 Lua는 키가 없으면 -2로 종료하고, 일반 API 기동은 seed 서비스 완료를 기다리지 않는다. 따라서 신규 환경은 seed 명령을 별도로 실행하기 전까지 사용할 수 없다.

정책 충돌 m4와의 관계

compose seed는 키를 직접 쓰므로 어댑터 캡슐화를 우회한다. 반대로 ApplicationRunner 자동 시드는 키 유실 후 앱 재기동만으로 revision 0을 다시 만들 위험이 있다. 둘을 모두 없애면 생성 경로가 사라진다.

근거 RedisRuntimeConfigStore.java:62-66, 85-90, 122-124 · compose.yml:78-93 · RuntimeConfigRedisAutoConfiguration.java:17-25

현재 합의와 맞는 정리: 자동 시딩이 아니라 명시적 1회 시딩을 유지한다. 따라서 남은 과제는 코드를 자동화하는 것이 아니라, 신규 환경 배포 절차가 profile 명령을 반드시 실행하도록 연결·검증하는 것이다.

감사 로그의 보존, 무결성, 개인정보

m1 · m5 · C5 · m4 — 감사 로그를 왜 남기는지부터 합의가 필요한 묶음

매 변경before/after 전체 JSON을 RPUSH
→
무제한 보존LTRIM·TTL·DB drain 없음
→
운영 위험noeviction에서는 결국 쓰기 실패 가능

용량 문제

AOF는 재시작 후 데이터를 복구하고 noeviction은 조용한 키 축출을 막지만, 감사 리스트의 성장을 제한하지 않는다. maxmemory가 설정된 운영 Redis라면 한계 도달 시 설정 변경 자체가 실패한다.

품질·보안 문제

beforeConfig는 원시 Redis JSON에서 만들어지고 updatedBy 형식은 이 계층에서 제한하지 않는다. 감사 로그가 장기 보존 기록이라면 유효성, ID 규약, 보존 기간을 한 묶음으로 결정해야 한다.

근거 RedisRuntimeConfigStore.java:58-66, 110-114 · compose.yml:57-71

독립 결정: “최근 N건만 Redis에 보존”과 “append-only 전체 이력”은 같은 요구가 아니다. 전자는 Lua 안 LTRIM으로 끝나지만, 후자는 Redis Stream/DB drain/AOF 백업 등 별도 수집 경로가 필요하다.

머지 전 판단 순서

서로 묶인 이슈를 중복 수정하지 않기 위한 권장 순서

  1. P0 — 신규 환경 시딩 절차: 명시적 profile 정책을 유지하고 배포 절차에서 1회 seed 실행을 보장한다. ApplicationRunner 자동 시드는 넣지 않는다.
  2. P0 — revision 역행 방어: Redis 값이 LKG보다 낮으면 정상 VALID로 반환할지, 계보 손상으로 거부할지 결정한다. 권장은 STORE_CORRUPTED 처리 후 높은 LKG 유지다.
  3. P1 — 장애 중 재시작 정책: 외부 LKG를 이번 PR에 추가할지 결정한다. 권장은 이번 범위를 키우지 않고, 재시작 인스턴스 503을 명시한 뒤 HA·외부 영속화 티켓으로 분리하는 것이다.
  4. P1 — 감사 로그 보존: 최근 N건 운영 로그인지 영구 감사 원장인지 먼저 정한다. 목적이 정해진 뒤 LTRIM 또는 drain을 선택한다.
  5. P2 — 관측·보안·포맷: STALE 게이지는 CY-264, Redis 인증은 배포 인프라, 저장 전용 ObjectMapper는 호환성 설계로 각각 분리한다.
