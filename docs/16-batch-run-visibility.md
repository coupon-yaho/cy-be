# 배치 실행을 GitHub Actions 에 남긴다 (착수 전 · 발표용)

> **아직 티켓이 아니다.** 발표에서 필요하다고 판단해 설계만 먼저 세워 둔다.
> 착수 조건과 결정할 것을 아래에 적었다.

## 왜

지금 배치 실행 이력은 **`verification_runs` 에 남고 관제 페이지가 히스토리로 보여준다.**
그것으로 기능은 충분하다 — 판정·검출 건수·지문·checksum 이 다 거기 있다.

**발표에서 아쉬운 것은 그것이 "우리 화면 안의 데이터" 라는 점이다.** 우리가 만든 페이지가
우리가 만든 테이블을 읽어 보여주는 구조라, 보는 사람에게 *"정말 돌았나"* 를 스스로
증명하지 못한다. 대시보드에 숫자를 하드코딩해도 같은 화면이 나온다.

**GitHub Actions 는 우리가 못 꾸미는 자리다.** 실행 기록·소요 시간·로그가 GitHub 쪽에
남고, 탭을 여는 것만으로 *"이 시각에 이 배치가 돌았고 결과가 이랬다"* 가 보인다.
그것이 발표에서 갖는 무게가 다르다.

## 무엇을 보여주고 싶은가

```
Actions
  ✅ 검증 배치 · CLEAN · PASS · 0건            2026-08-23 09:14   2m 31s
  ✅ 검증 배치 · CORRUPT · FAIL · 800건        2026-08-23 09:22   3m 07s
  ❌ 검증 배치 · CLEAN · 판정 못 냄            2026-08-23 09:31   0m 12s
```

세 번째 줄이 중요하다. **실패도 남아야 증거가 된다** — 성공만 남기면 "성공한 것만 골라
올린 것 아니냐" 는 질문에 답할 수 없다.

## 결정할 것 넷

### ① 무엇을 남기나 — 만료는 하루 288회다

`expireJob` 은 5분 크론이라 **하루 288번** 돈다. 그것을 전부 남기면 Actions 탭이 도배되고,
정작 보여주고 싶은 검증 실행이 그 사이에 묻힌다.

| 후보 | 대가 |
|---|---|
| 검증(`verifyJob`)만 | 발표에서 보여줄 것은 이쪽이다. 만료가 도는 것은 증명 못 함 |
| 검증 + 만료 중 **뭔가 한 일이 있는 것만** | 만료는 정상 상태에서 슬롯마다 약 22건을 처리한다(`docs/13` §6) — 하루 288회가 거의 전부 남으므로 첫째와 사실상 같다 |
| 전부 | 발표에서 못 쓴다 |

**첫째가 기본이다.** 만료는 이미 Prometheus 알림 축(`ExpireNotSucceeding`)이 있고, 그쪽이
"안 돌면 운다" 를 증명한다 — 두 수단이 같은 사실을 각자 증명할 필요가 없다.

### ② 어떻게 연결하나 — 배치는 Actions 밖에서 돈다

배치는 컨테이너(또는 로컬 JVM)에서 돌고 GitHub 은 바깥이다. 셋 중 하나다.

| 방법 | 어떻게 | 걸리는 것 |
|---|---|---|
| `repository_dispatch` | 배치가 끝나면 `POST /repos/{owner}/{repo}/dispatches` 로 이벤트를 쏘고, 그 이벤트를 받는 워크플로가 결과를 렌더한다 | **토큰이 배치 안에 있어야 한다** — 아래 ③ |
| `workflow_dispatch` | 사람이 Actions 에서 버튼을 눌러 배치를 **거기서** 돌린다 | DB 가 러너에서 닿아야 한다. 시연 DB 를 공개 러너에 노출할 수 없다 |
| 워크플로가 주기적으로 DB 를 읽어 요약 | `schedule` 크론이 `verification_runs` 를 읽어 커밋/요약 | 같은 문제 — 러너가 DB 에 못 닿는다 |

**첫째가 유일하게 성립한다.** 나머지 둘은 **러너가 우리 DB 에 접근해야** 하는데, 그 DB 는
compose 안에서 `127.0.0.1` 에만 묶여 있다(CY-368 이 그렇게 정했다).

### ③ 토큰을 어디에 두나 — 이 저장소는 PUBLIC 이다

`repository_dispatch` 는 `contents: write` 권한 토큰을 요구한다. 그것을 배치 컨테이너가
들고 있어야 하는데, **이 저장소는 공개**이고 CY-368 이 트리거 API 에 인증을 못 붙인
이유와 같은 제약을 받는다.

> ⚠️ **`.gitignore`·`.dockerignore` 는 이 문제를 안 푼다.** 그 둘이 막는 것은 *커밋·이미지에
> 섞여 들어가는 것*이고, 여기서 걱정하는 것은 **런타임에 살아 있는 자격증명**이다 —
> 환경변수는 `/proc/<pid>/environ` 과 액추에이터 `env` 엔드포인트에, 헤더는 로그에 남는다.
> 두 축을 섞어 적었던 것을 바로잡는다.

**그래서 장수 PAT 를 컨테이너에 두는 안은 버린다.** 남는 것은 둘이다.

| 방법 | 무엇이 달라지나 | 대가 |
|---|---|---|
| **GitHub App 의 installation token** | 1시간짜리 단기 토큰을 그때그때 발급받는다. 유출돼도 창이 짧다 | App 등록·private key 보관이 새로 생긴다 — 그 키가 다시 같은 문제다 |
| **중계 한 겹** | 배치는 우리 쪽 엔드포인트만 부르고, GitHub 자격증명은 거기서만 산다 | 서비스가 하나 는다. 발표용으로는 과하다 |

**착수할 때 정한다.** 지금 확정할 수 있는 것은 *"장수 `contents: write` PAT 를 배치
컨테이너에 넣지 않는다"* 까지다.

공통으로 지킬 것:
- 권한을 **최소로** — 그 저장소의 `contents: write` 하나. 만료일을 짧게
- **로그에 안 찍히게** — 그 호출을 남길 때 `Authorization` 헤더를 지운다
- 액추에이터 `env`·`configprops` 노출을 막는다(지금 설정이 그렇게 돼 있는지 확인한다)
- ⚠️ **발표 후 폐기**를 절차로 박는다. 데모용 자격증명이 살아 있는 것이 가장 흔한 사고다

### ④ 관제 히스토리와 두 벌이 되지 않게

`verification_runs` 가 원본이고 Actions 는 **그 복사본**이다. 두 곳이 각자 판정하면
언젠가 어긋난다 — 이 저장소가 반복해서 없애 온 모양이다.

**Actions 는 판정하지 않는다.** 배치가 이미 낸 결과를 그대로 실어 보내고, 워크플로는 그것을
**렌더만** 한다. 워크플로 안에서 다시 계산하거나 DB 를 읽지 않는다.

**그래서 payload 에 화면에 뜨는 것이 전부 들어가야 한다.** 위 화면 예시가 `CLEAN`/`CORRUPT`
와 시각·소요를 보여주는데, 그것을 워크플로가 조회할 방법이 없기 때문이다.

| 필드 | 어디서 | 왜 필요한가 |
|---|---|---|
| `runId` | `verification_runs.id` | 관제 히스토리와 맞대는 열쇠 |
| `dataset` | 잡 파라미터 | 화면의 `CLEAN`/`CORRUPT`. **없으면 두 실행이 같은 줄로 보인다** |
| `verdict` | `verification_runs.verdict` | `PASS`/`FAIL`. 판정을 못 냈으면 비어 있다 |
| `findingCount` | `verification_runs.finding_count` | 검출 건수 |
| `startedAt`·`durationMs` | `JobExecution` | 화면의 시각·소요. Actions 자체 시각은 **이벤트를 받은 시각**이라 다르다 |
| `executionId` | `JobExecution.getId()` | 아래 중복 제거 키 |

## 실패를 어떻게 남기나

**배치가 죽으면 누가 이벤트를 쏘는가** 가 핵심이다. 잡 안에서 쏘면 죽은 실행은 못 쏜다.

`JobExecutionListener.afterJob` 이 그 자리다 — 잡이 `FAILED` 로 끝나도 불린다.
다만 **JVM 이 통째로 죽으면(하드킬·OOM) 그것도 안 불린다.** 그 경우는 남지 않는다는 것을
알고 있어야 한다 — Actions 에 기록이 **없는 것**과 배치가 **안 돈 것**이 같은 모양이다.

**사건을 둘로 가른다.**

**돌다가 하드킬된 경우**는 CY-392 의 `BatchStuckExecution` 이 진다. 그때 실행 행이
`STARTED` 로 남고 `LAST_UPDATED` 가 죽은 순간에 얼어붙는데, 그것이 `stuck-job-after-ms`
(30분)를 넘으면 게이지가 1 이 되어 `for` 10분 뒤 울린다 — 잡 셀렉터가 없어 `verifyJob` 도
포함된다. 다만 **감지까지 최소 40분**이고, 그 행을 걷어내지 않으면 계속 울린다.

**아예 안 돈 경우**는 아직 아무도 안 진다. `VerificationMetricsUnknown` 은 게이지가 `NaN`
일 때만 뜨는데, 닫힌 FULL 실행이 한 번이라도 있으면 되읽기가 그 행을 계속 찾아 주므로
게이지가 값을 유지한다 — 즉 *"한 번도 안 돌았다"* 만 잡고 *"돌다가 멈췄다"* 는 못 잡는다.
`VerificationMetricsStale` 은 되읽기 실패만 보고, `ExpireNotSucceeding` 은 `expireJob` 전용이다.
그 축은 크론이 생기는 티켓(`docs/13` §6 의 C)이 세운다 — 크론이 없는 동안 SLA 를 걸면
영구 발화라서다.

**Actions 는 발표용 가시화이지 감시 수단이 아니다** — 그 선을 문서에 박아 둔다.

### 보낼 때 정해야 할 셋

`repository_dispatch` 는 **멱등 키를 안 받고 워크플로 실행 id 도 안 돌려준다.** 그래서
아래를 설계가 직접 져야 한다.

| | 무엇 | 왜 |
|---|---|---|
| **중복 제거** | payload 에 `executionId` 를 싣고, 워크플로가 같은 값이 이미 있으면 새 줄을 안 만든다 | 재시도하면 같은 실행이 두 줄로 남는다 — Actions 탭이 그 자체로 증거인데 거기에 없는 실행이 생기는 것보다 **있지도 않은 실행이 생기는 쪽**이 더 나쁘다 |
| **타임아웃** | 연결·응답 각 2초. 넘기면 포기하고 WARN | `afterJob` 은 잡의 종료 경로다. 여기서 늘어지면 **다음 크론이 밀린다** |
| **재전송** | 즉시 1회만. 그 뒤로는 안 한다 | 배치의 일은 판정이지 전송이 아니다. 실패해도 `verification_runs` 가 원본으로 남는다 |

**`afterJob` 이 안 불리는 갈래가 하나 더 있다** — `JobExecution` 이 만들어지기 **전**에
죽는 경우(파라미터 검증 실패, 컨텍스트 기동 실패). 그때는 Actions 에 아무것도 안 남고,
그것이 *"안 돌았다"* 와 같은 모양이다. 위의 하드킬과 같은 구멍이라 같은 답을 쓴다 —
**감시는 Prometheus 몫이다.**

## 착수 조건

- **CY-368 이 머지된 뒤.** 트리거 API 가 있어야 시연에서 검증을 손으로 돌릴 수 있고,
  그래야 Actions 에 기록이 쌓이는 것을 보여줄 수 있다
- **발표 시나리오가 정해진 뒤.** 무엇을 몇 번 돌려 보여줄지에 따라 ①의 답이 바뀐다
- 300만 적재 후가 낫다 — 소요 시간이 Actions 에 찍히는데, 축소 데이터의 숫자는
  발표에서 설명이 더 필요하다

## 안 하는 것

| 무엇 | 왜 |
|---|---|
| 만료 배치 기록 | 하루 288회. 알림 축이 이미 그것을 진다 |
| Actions 에서 배치를 **실행** | 러너가 우리 DB 에 못 닿는다. 닿게 만들면 그게 더 큰 구멍이다 |
| Actions 를 감시 수단으로 | 하드킬 시 기록이 안 남는다. 감시는 Prometheus 몫 |
