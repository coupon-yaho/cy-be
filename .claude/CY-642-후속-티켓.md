## CY-643 (T2) — 발송 파이프라인

**선행:** T1 머지. T3·T4와 병렬 착수 가능.

1. `docs/notification/pipeline.md`와 `decisions.md` D17·D19·D21·D22를 기준으로 구현한다.
   최초 발송 1회와 자동 재시도 3회로 최대 발송 호출은 총 4회다.
   프로토타입 payload는 `member:{memberId}`와 `coupon-issued:{issuanceId}`로 결정론적으로 만든다.
2. Outbox relay를 구현한다: DB 시계 lease claim → `coupon.notify` 발행(key=`memberId`) →
   fencing token으로 `PUBLISHED` 확정. 외부 발행 중 DB 락을 잡지 않는다.
3. lease 만료 회수와 명시적 발행 실패 모두 failure count를 올리고, 1초 뒤 재시도한다.
   프로토타입 상한 10회는 `DEAD`다.
4. `notify-dispatch` Consumer를 구현한다: `SENDING` → `NotificationSender.send()` →
   완료 attempt 기록 → 알림 상태 수렴. 같은 attempt의 완료 기록은 먼저 INSERT한 쪽이 권위다.
5. mock `NotificationSender`, 실패 주입 Fake, `app.notify.sent{result}` 미터, retry/DLT 관측을 붙인다.

완료 조건: `verification.md` 1~6 및 relay 동시 claim·lease 회수·완료 attempt 경쟁을 통합 테스트한다.

## CY-644 (T3) — 관리자 조회

**선행:** T1 머지. T2·T4와 병렬 착수 가능.

1. `admin-api.md`의 계산식으로 summary Service를 만든다.
2. `FAILED`·`DEAD` 목록은 PII 없는 `NotificationFailure` projection과

3. `GET /notifications/summary`, `GET /notifications/failures`의 501을 제거한다.
4. 응답의 `couponId`, `ObservedValue`, `sentRate`의 `N_A` 규칙과 관리자 권한 경계를 검증한다.

완료 조건: `verification.md` 7~12. 응답 JSON에 연락처·본문 필드나 값이 없어야 한다.

## CY-645 (T4) — 수동 재발송

**선행:** T1 머지. relay 구현(T2)을 기다리지 않고 `MANUAL` outbox 적재까지 구현할 수 있다.

1. 상태(D9), 3회 상한과 10분 멱등 창(D8)을 판정한다. 최근 **accepted** audit만 멱등 판정에 쓴다.
2. `status + attempt_count + resend_count` CAS, accepted/rejected audit, `MANUAL` outbox 저장을
   하나의 DB 트랜잭션으로 묶는다.
   거부 audit은 뒤이어 던지는 예외에 롤백되지 않도록 독립 트랜잭션에서 저장한다.
3. 없는 알림(ADMIN-005), 전이 충돌(ADMIN-006), 상한 초과(ADMIN-007)도 거부 audit로 남긴다.
4. `POST /notifications/{id}/resend`의 501을 202 접수 응답으로 교체한다. 202는 발송 완료가 아니다.
5. `NOTIFY-*`는 도메인 규칙, `ADMIN-*`는 관리자 유즈케이스 판정이다. API 경계의 응답 매핑을
   문서와 테스트로 하나로 고정한다.

완료 조건: `verification.md` 13~18. 동시 재발송은 하나만 접수되고, 거부 요청도 모두 감사된다.
