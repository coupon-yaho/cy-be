# CY-642 이후 작업 — T2 · T3 · T4 인계

T1(CY-642)이 무엇을 남겼고, 다음 티켓이 **무엇을 전제로 시작하는지**를 적는다.
설계 SSOT 는 `docs/notification/`, T1 진행 상태는 `.claude/CY-642.md`.

다음 티켓 시작할 때 이 파일을 먼저 읽힌다.

## 0. 먼저 읽을 것 — T1 이 설계도에서 벗어난 3가지

설계도(`docs/notification/`)를 그대로 믿고 T2 를 시작하면 어긋난다. 아래 셋은 T1 구현이
설계보다 **앞서 나간** 부분이고, 문서보다 코드가 정본이다.

### ① Outbox 가 생겼다 — D1(afterCommit 발행)을 대체한다

설계도는 "발급 커밋 이후 afterCommit 에서 Kafka 발행" 이었다. T1 은 대신
`notification_outbox` 테이블 + claim/lease 를 만들었다.

- `NotificationOutbox` · `NotificationOutboxStatus` · `NotificationOutboxClaim`
- `uk_notification_outbox_attempt (notification_id, attempt_seq)` — 중복 발행 방어
- `ix_notification_outbox_pending (status, next_attempt_at, id)` — relay 폴링 축
- `ix_notification_outbox_expired (status, claimed_at, id)` — lease 만료 회수 축
- `uk_notification_outbox_claim_token` — fencing token

**T2 에 주는 영향이 크다.** T2 는 afterCommit 훅이 아니라 **outbox relay** 를 만든다.
발급 트랜잭션은 `notifications(PENDING)` 과 `notification_outbox(PENDING)` 을 같이 쓰고,
relay 가 그것을 claim 해서 `coupon.notify` 로 발행한 뒤 `PUBLISHED` 로 넘긴다.

이 편이 옳다. afterCommit 은 발행 실패 시 알림이 영구 `PENDING` 으로 남고 회수 수단이
없었는데(설계도가 그걸 "범위 밖" 으로 닫았다), outbox 는 relay 가 다시 집는다.

> **설계도를 아직 안 고쳤다.** T2 착수 시 `docs/notification/pipeline.md` 의 트랜잭션 경계 절과
> `decisions.md` 의 D1 을 outbox 기준으로 고치는 것이 T2 의 첫 작업이다.

### ② 어휘가 `campaignId` → `couponId` 로 바뀌었다

이 리포는 회차를 `coupons`, 발급건을 `issuances` 로 부른다(`docs/10-batch-design.md` 의
어휘 정정 표). T1 이 그 관례에 맞춰 **관리자 DTO 필드명까지** 바꿨다.

- `NotificationSummaryResponse.campaignId` → `couponId`
- `NotificationFailureItem.campaignId` → `couponId`
- 인덱스도 `ix_notifications_coupon_status`

**이건 A 화면에 나가는 HTTP 계약 변경이다.** §4 의 A 인계 항목으로 남겼다.

### ③ core 전용 에러 코드가 따로 생겼다

`AdminApiErrorCode` 에 ADMIN-005/006/007 을 추가한 것 외에,
`core/notification/NotificationErrorCode` 가 별도로 생겼다.

| 코드 | HTTP | 의미 |
|---|---:|---|
| `NOTIFY-001` | 409 | 상태 전이 위반 |
| `NOTIFY-002` | 409 | 재발송 횟수 상한 초과 |
| `NOTIFY-003` | 503 | 발송 의존성 사용 불가 |
| `NOTIFY-004` | 422 | 수신처·본문 길이 초과 |

**T4 에서 역할을 갈라야 한다.** 도메인 규칙 위반은 `NOTIFY-*`, 관리자 HTTP 계층의 판정은
`ADMIN-*` 이다. 같은 상황에 둘 다 던지면 화면이 두 코드를 다 처리해야 한다.
어느 쪽을 응답에 내보낼지 T4 착수 시 한 번 정하고 문서에 박는다.

## 2. 후속 티켓

### T2 — 발송 파이프라인 (outbox relay · Consumer · 재시도 · DLT · 미터)

**선행** T1 머지 · **라벨** `infra` · **분기** `feature/CY-5`

산출물
1. `docs/notification/` 를 outbox 기준으로 개정 (①) — **코드보다 먼저**
2. 발급 트랜잭션에서 `notifications(PENDING)` + `notification_outbox(PENDING)` 동시 저장
3. Outbox relay — claim(fencing token) → `coupon.notify` 발행(key=`memberId`) → `PUBLISHED`
   - lease 만료 회수 경로 (`ix_notification_outbox_expired`)
   - 같은 이벤트 재수신 때 완료 attempt가 이미 있으면 발송을 반복하지 않고 그 결과로 알림 상태만 수렴
   - relay 주기·배치 크기·lease 시간을 문서에 값으로 박는다
4. `notify-dispatch` Consumer — 수신 → `SENDING` → `NotificationSender.send()`
5. `NotificationSender` 로그 구현체 + 실패 주입 Fake
6. 재시도 `ExponentialBackOffWithMaxRetries(3)` 1s·5s·20s, 재시도 불가는 `addNotRetryableExceptions`
7. `app.notify.sent{result}` 등록 — `MeterNames.NOTIFY_SENT` 는 T1 에서 이미 열어 뒀다
8. `KafkaConsumerGroups.DLT_REPROCESS` 미사용 주석 (D7)

완료 조건 — `verification.md` 검증 1~6 + relay 전용 2개
- relay 가 같은 outbox 행을 두 번 발행하지 않는다 (동시 claim 2건)
- lease 만료 행이 회수되어 다시 발행된다

주의
- 발송 외부 호출은 어떤 락도 들고 있지 않다
- 백오프가 컨슈머 스레드를 최대 26초 점유한다. concurrency 는 파티션 6 이하
- 재시도 3회 후 성공은 미터 `success` **1** 이다

### T3 — 관리자 조회 (요약 · 실패 목록)

**선행** T1 머지 (T2 와 병렬 가능) · **라벨** `admin-api`

산출물
1. 요약 집계 Service — `admin-api.md` 의 계산식 5개
2. 실패·DLT Keyset 목록 — `ix_notifications_failure_keyset` 사용, `id DESC`
3. `GET /notifications/summary` · `GET /notifications/failures` 의 `501` 제거
4. `couponId` 어휘 (②) 가 응답·쿼리·문서에서 일관되는지 확인

완료 조건 — 검증 7~12
- `ObservedValue` 상태 규칙: 0건 캠페인은 `NO_TRAFFIC`, 없는 회차는 `N_A`,
  조회 실패는 `UNAVAILABLE`. **미수집을 0 으로 채우지 않는다**
- `sentRate` 분모 0 이면 `N_A` (0.0 아님)
- 응답 JSON 에 연락처·본문이 필드로도 값으로도 없다
- `hasOlder` 는 `limit + 1` 조회로 판정

### T4 — 수동 재발송 (멱등 · 감사)

**선행** T1 머지, T2 의 발행 경로 · **라벨** `admin-api`

산출물
1. 재발송 판정 — 상태(D9) · 횟수(D8) · 멱등 윈도우 10분
2. 멱등 선점 — `uk_attempts_notification_seq` 또는 `uk_notification_outbox_attempt`
   (**둘 중 어디서 선점할지 T4 착수 시 정한다.** outbox 가 생기면서 선점 지점이 둘이 됐다)
3. `notification_resend_audits` — 거부 요청도 기록
4. outbox 에 `MANUAL` 명령 적재 → relay 가 발행
5. `POST /notifications/{id}/resend` 의 `501` 제거 → `202`
6. `NOTIFY-*` 와 `ADMIN-*` 의 역할 분담 확정 (③)

완료 조건 — 검증 13~18
- 동시 재발송 2건 → 1건만 202
- 4번째 재발송 → ADMIN-007 / `SENT` 재발송 → ADMIN-006 / 없는 알림 → ADMIN-005
- 거부 요청도 audit 에 `reject_code` 와 함께 남는다
- `202` 는 접수이지 발송 완료가 아니다

## 3. 하지 않는 것 (닫힌 결정)

`docs/notification/scope.md` 가 정본이다. 리뷰에서 지적되면 그 문서를 근거로 답한다.

실 벤더 연동 · DLT 자동 재처리 컨슈머 · 보관기간 정리 배치 · 멀티채널 ·
발급 외 알림 트리거 · 실패 사유별 미터 태그 · 관리자 화면 구현.

초기 발행 outbox가 `DEAD`가 되어 남은 `PENDING` 알림은 자동 회수하지 않는다. T3의 요약 관제가
`remainingCount`로 드러낸다.

`notification_outbox.failure_count` 상한은 프로토타입에서 10회 고정이다. 운영 중 조정이 필요해지면
애플리케이션 설정과 DDL CHECK를 함께 바꾸고, 한쪽만 바뀌면 안 되는 계약 테스트를 추가한다.

## 4. A 에 인계할 것

T3·T4 머지 후 A 가 확인한다. **새로 구현하지 않는다.**

- **`campaignId` → `couponId` 필드명 변경**(②) — 관리자 화면이 알림 응답을 파싱한다면 수정 필요.
  가장 먼저 알려야 한다
- 관리자 공통 권한 경계가 알림 API 3개에 적용되는지
- 기존 경로 3개를 그대로 호출할 수 있는지
- 다른 A 응답과 `ObservedValue` 상태 표현이 일치하는지
- 회차 상세에서 알림 화면으로 넘어갈 식별자가 맞는지

## 5. 개발 가이드라인

리포 전반 규약은 `AGENTS.md` 와 `README.md` 가 갖는다. 아래는 **알림 작업에서 특히 밟기 쉬운 것**만.

### 문서와 코드

- 설계에 없는 판단이 필요해지면 **코드보다 문서를 먼저 고친다.** T1 의 outbox 가 문서 없이
  들어와서 지금 이 인계 문서 §0 이 필요해졌다 — 같은 일을 반복하지 않는다
- 결정 번호(D1~D16)는 `decisions.md` 에 없는 번호를 인용할 수 없다. 새 결정은 번호를 붙여 추가한다
- 주석은 코드가 실제로 보장하는 것만 말한다. 못 지키면 TODO 와 후속 티켓으로 남긴다
- 방어를 추가하면 **그 방어가 만드는 반대 방향 실패**도 함께 적는다

### 테스트

- 전체 build 금지. 관여 모듈만 — `./gradlew :storage:test :core:test :api:test`
- 가드 테스트는 **일부러 깨뜨려 빨간불을 확인한다.** 초록불만 보고 넘어가면 안 도는 가드가 남는다
- 프레임워크 동작은 추측하지 말고 실측한다. 리뷰 반박도 프로브를 돌려 수치로 한다
  (프로브 자체는 커밋하지 않는다)
- 동시성 단언은 sleep 이 아니라 Awaitility 로 조건 폴링한다

### 커밋

- **커밋은 사람이 한다.** 에이전트는 하지 않는다
- `fix` 는 티켓 번호 없이, `feat` · `docs` · `chore` 만 스코프에 티켓을 단다
- 알림 무관 변경을 같은 커밋에 섞지 않는다 (§1 참조)

### 이 도메인에서 밟기 쉬운 함정

| 함정 | 무슨 일이 일어나나 |
|---|---|
| 발송 결과 확정 전에 미터를 올림 | 발행 성공을 발송 성공으로 세서 성공률이 항상 100%. 화면은 안 깨지고 숫자만 틀린다 |
| 재시도 한 건을 알림 한 건으로 합산 | 실패가 많을수록 발송 건수가 늘어난다. 고객 알림 1건 = 카운트 1건 |
| 미수집을 0 으로 채움 | `ObservedValue` 생성자가 던지긴 하지만, `VALID` 로 0 을 넣으면 안 던진다. "배치가 안 돌았다" 와 "실제 0건" 이 구분 안 된다 |
| DLT 파티션을 원본보다 적게 잡음 | `DeadLetterPublishingRecoverer` 가 같은 번호 파티션으로 보내서 격리 발행이 실패한다. 이미 6으로 맞춰져 있으니 **건드리지 않는다** |
| 관리자 응답 DTO 에 PII 를 넣고 마스킹 | 마스킹이 아니라 **필드 자체가 없어야 한다**(D10). 마스킹은 로그·직렬화 어딘가에서 새어 나간다 |
| 이벤트에 수신처·본문을 실음 | Kafka 보존 7일이라 보관기간 정책을 우회한다. Consumer 가 `notificationId` 로 DB 에서 읽는다 |
| outbox relay 를 트랜잭션 안에서 발행 | claim 트랜잭션이 Kafka 응답을 기다리며 커넥션을 잡는다. claim 과 발행을 분리한다 |
| 발송 실패로 발급 트랜잭션을 롤백 | 알림 때문에 쿠폰이 안 나간다. 알림은 발급의 부수 효과지 조건이 아니다 |
